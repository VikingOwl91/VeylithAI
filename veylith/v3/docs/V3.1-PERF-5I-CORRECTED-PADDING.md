# v3.1-PERF-5I corrected padded arm

Status 2026-10-27. One GPU execution, used. No production change, no checkpoint
change, no package change, no reset, no retry, no serialization, no push.

**Outcome: classification 2, valid corrected padded execution, faulted.**

The corrected harness restored the reference trajectory: all three of the
reference's printed values match exactly. The padded buffers were real and
verified. The fault still occurred, and its page does not lie in any padded
storage. Instead the fault page coincides exactly with the 4-byte tail of a
**stock** `(3075, 682)` bf16 tensor that two GEMMs read as an operand in the
faulting second: the SwiGLU product `silu(w1(x)) * w2(x)`, an elementwise output
this harness never padded.

So padding the `w3` input gradient does not remove the fault, and the boundary
evidence now points away from that buffer and toward an operand read of the
SwiGLU product.

## 4. Gate A, numerical identity

Displayed values, exactly as recorded by the reference and by this run:

| iteration | reference | this run |
|---|---|---|
| 0 | 10.4816 | **10.4816** |
| 25 | 10.4898 | **10.4898** |
| eval after 25 | 10.4923 | **10.4923** |

Every overlapping printed value is identical. Compare 5H, where all three
differed, which is the mechanism difference this stage was built to remove.

**Gate A is met at display precision and unmet at full precision.** The harness
captured the full-precision iteration-0 loss in memory, but the loop faulted
before the post-loop recompute, so it was never written down. No reference arm
has ever recorded a full-precision loss either, so even a persisted value would
have had no external comparand; the intended comparison was the in-run stock
recompute of the same batch, which never ran. The harness now prints
`FIRSTLOSS` with the full value at capture time so a fault cannot erase it. That
fix is CPU-tested, not GPU-verified.

Consequence for this report: numerical identity rests on three displayed values
plus the CPU whole-model bitwise gate, not on a device-level full-precision
comparison. Whole-trajectory bitwise identity is not claimed and cannot be.

## 7. Gate D, producer attribution and the fault page

### Padded versus stock producers at M = 3075

| producer | C descriptor | page gap | padded |
|---|---|---|---|
| forward output `(M, 682)` | `682 3075 682` | **4 bytes** | no |
| forward output `(M, 682)` | `682 3075 682` | **4 bytes** | no |
| `w3` backward input gradient | `682 3075 682` | 720,900 bytes | yes, 65,536 slack |
| `w3` forward output `(M, 256)` | `256 3075 256` | 522,752 / 654,848 / 200,704 bytes | no |

Two stock forward outputs still landed 4 bytes from a page boundary, as in
PERF-5H. The padded buffer did not: its tensor end sat 720,900 bytes from the
next 2 MiB boundary, with the protection coming from its 65,536 bytes of slack.

### The fault page

`0x00007ff321400000`, 4 fault records, no reset.

| test | result |
|---|---|
| fault page inside any padded storage | **0 of 2,068** |
| nearest padded storage to the fault page | 167,592 bytes away |
| padded tensor end within 64 bytes of the fault page | none |
| buffers whose 4 KiB-rounded end equals the fault page, all roles | 3 candidates |
| of those, a 4-byte tail (tensor end exactly page minus 4) | **1 buffer, read as an operand** |

The candidate:

```
role B (read), pointer 0x7ff321000000, descriptor rows 682 cols 3075 ld 682
tensor end 0x7ff3213ffffc, which is the fault page minus 4 bytes
padded view: no
dispatched at 16:52:15, twice, as the B operand of two different GEMMs
```

The two reads:

| A | B | C | transA / transB | operation |
|---|---|---|---|---|
| `(256, 3075)` | same buffer | `(256, 682)` | `OP_N` / `OP_T` | `w3` weight gradient, `grad_out^T @ t` |
| `(256, 682)` | same buffer | `(256, 3075)` | `OP_N` / `OP_N` | `w3` forward, `t @ W3^T` |

Both consume the same tensor `t`. That tensor is the SwiGLU product
`silu(w1(x)) * w2(x)`: a `mul` output, which is why it never appears as a GEMM
output and never entered the C-side wide-call statistics of PERF-5C to 5H.

So the access that faulted is a **read of a stock 4,194,300-byte bf16 operand
whose last element ends exactly at the page**, not a store into the buffer this
harness padded. This is the geometry PERF-5F ranked second: a Tensile operand
read past the end of the mapping.

Which of the two GEMMs faulted is not observed. Both were dispatched in the
faulting second, and the fault surfaced one iteration later, so both are
candidates. PERF-5D's trace tail (`silu_backward` then `aten::mm`) favours the
backward weight-gradient read.

## 8. Interpretation

| class | verdict |
|---|---|
| 1, valid corrected padded execution, clean | no |
| 2, valid corrected padded execution, faulted | **yes** |
| 3, invalid due to numerical mismatch | no, displayed values match exactly |
| 4, invalid due to GEMM or allocation mismatch | no, descriptors and storage verified |
| 5, inconclusive due to insufficient producer attribution | no, attribution is page-exact |

What this establishes:

1. The corrected harness reproduces the reference trajectory at display
   precision, so the mechanism no longer perturbs the model.
2. The intervention was real and verified: 2,068 padded allocations, one targeted
   `(3075, 682)` dispatch, 65,536 bytes of slack, no resize.
3. The fault recurs with that buffer protected, so boundary dependence of the
   `w3` input gradient is **not supported**. A faulting result refutes a critical
   buffer only if the buffer was demonstrably protected, and here it was: the
   fault page lies in no padded storage, and the nearest one is 167,592 bytes
   away.
4. The fault page is page-exact with the 4-byte tail of a stock SwiGLU-product
   operand, which revises the candidate ranking toward an operand read.

What this does not establish: the faulty kernel identity, which GEMM of the two
over-read, or that the SwiGLU product is the only boundary-sensitive buffer.
Proximity plus a same-second dispatch is strong correlation, not direct
observation.

## 9. Confounders

1. Both candidate reads were dispatched in the same second. Host dispatch order
   is not GPU execution order, so the specific faulting kernel is not observed.
2. `0x7ff321000000` was reused earlier in the same run by two of the harness's
   own padded allocations (`(2849, 682)` and `(2788, 682)`). Pointer-only
   attribution would have been wrong; this attribution uses the descriptor, the
   recorded shape and the timestamp together.
3. The padding changes the allocator layout, so stock buffer addresses in this
   run differ from a reference run. That is inherent to the intervention.
4. Full-precision numerical identity is unavailable for this run (section 4).
5. Kernel identity is unavailable in this build.

## 10. Recommended next bounded experiment

One run of the same corrected arm with the SwiGLU product itself placed in padded
storage: replace `SwiGLU.forward` so the product is written by
`torch.mul(silu(gate), up, out=<padded view>)`, keeping shapes, strides, dtype
and the two forward GEMMs identical, with the same 64 KiB slack. Gates: the
whole-model CPU gate must still pass bitwise; the product's descriptor group must
be unchanged; every allocation must show slack and no resize; the first loss must
match `10.4816` and print its full value immediately.

If that arm is clean while this one faults, the product's boundary is implicated
by a controlled comparison. If it still faults, the next discriminator is a
`--no_backward` run, which removes the weight-gradient read and leaves only the
forward read of the same operand.

One clean run remains preliminary: the fault is intermittent, and no run here
identifies the kernel.
