# v3.1-A architecture: 0.1B decoder-only MoE

Status 2026-10-26. Architecture design and CPU validation only. No GPU
training, no model checkpoint, no model quality claim. Baseline has **no
MTP**. Vocabulary 8192, context 512 (1024 optional).

## 1. Scope and relation to v2

v3.1-A is the first ~0.1B-parameter candidate for the multi-source corpus.
v2 remains the frozen historical reference. The design reuses the proven v2
components (RMSNorm, RoPE, GQA, SwiGLU, routed+shared experts, aux
load-balancing) and removes MTP from the baseline and the dense-combined-only
constraint from the architecture definition. The execution mode is a
separate flag (sparse default, dense fallback).

## 2. Review of the existing implementation

| component | v1 | v2 | v3.1-A |
|---|---|---|---|
| embedding | learned, untied | learned, untied | learned, untied (tied option tested) |
| output head | untied Linear | untied Linear | untied Linear (tied config exists) |
| norm | LayerNorm | RMSNorm | RMSNorm |
| positions | learned absolute | RoPE | RoPE, theta 10000 |
| attention | MHA full | GQA 8Q/2KV, SWA 128, full every 4 | GQA 8Q/2KV, SWA 256, full every 4 |
| MLP | GELU 4x | SwiGLU 8/3; MoE 8 experts top-2 + shared | SwiGLU; MoE 8 top-2, shared optional |
| router | none | linear gate, top-k softmax, Switch aux 0.01 | same, aux 0.01 |
| MTP | none | t+2, shared head, weight 0.5, 43 % of composite | **removed** |
| init | normal 0.02 | normal 0.02; no residual scaling | normal 0.02 |
| checkpoint | legacy | format 2, atomic, optimizer/RNG | format not implemented yet |
| GPU assumptions | bf16 autocast, manual attention | bf16, manual attention, dense-combined to avoid ROCm sparse fault | device-agnostic reference; SDPA/flash for the GPU trainer |

v2's `param_report` calls the dense-combined compute "active", which is not
the algorithmic active count. v3.1 accounting keeps the numbers separate
(section 4).

## 4. Exact parameter accounting

Method: analytical formulas per module, cross-checked by instantiating each
candidate on the PyTorch `meta` device and summing `parameters()`. Shared
weights are counted once. Active counts are checked with forward hooks on a
tiny CPU model (one token).

|---|---:|---:|---:|---:|
| token embedding | 4,194,304 | 4,194,304 | 3,145,728 | 4,194,304 |
| output head (untied) | 4,194,304 | 4,194,304 | 3,145,728 | 4,194,304 |
| attention | 5,242,880 | 6,553,600 | 4,423,680 | 5,242,880 |
| norms | 8,704 | 10,752 | 9,600 | 8,704 |
| dense FFN | 2,096,640 | 4,193,280 | 1,179,648 | 2,096,640 |
| router | 28,672 | 32,768 | 33,792 | 28,672 |
| routed experts | 82,575,360 | 78,643,200 | 74,612,736 | 77,070,336 |
| shared experts | 0 | 0 | 9,326,592 | 9,633,792 |
| **total** | **98,340,864** | **97,822,208** | **95,877,504** | **102,469,632** |
| active unique (sparse) | 36,409,344 | 38,839,808 | 39,917,952 | 35,033,088 |
| active dense-combined | 98,340,864 | 97,822,208 | 95,877,504 | 102,469,632 |
| active ratio | 0.370 | 0.397 | 0.416 | 0.342 |

Three numbers are kept separate:

1. **Total trainable**: all parameters, shared weights once.
2. **Unique parameters in one sparse forward**: embedding, untied head, all
   attention/norm/dense/router weights, top-k expert FFNs, shared expert.
   This is the algorithmic active count.
3. **Compute-equivalent active**: same as (2) for sparse execution; equal to
   total for the dense-combined fallback, because every expert runs.

The v2-style "compute per token" print is (3), not (2). Training FLOPs use
(3) with the chosen execution mode; see `V3.1-MEMORY-COMPUTE.md`.

Automated checks: `veylith/v3/tests/test_architecture.py` verifies the
analytical totals against meta-instantiated models and the active count
against forward hooks.

## 5. Structure

```
tokens -> embedding (8192 x 512)
  for each of 8 blocks:
    x = x + GQA(RoPE, causal/SWA mask)(RMSNorm(x))
    x = x + FFN(RMSNorm(x))          # dense for block 0, MoE otherwise
  RMSNorm -> untied head (512 x 8192) -> logits
```

MoE block (sparse default):

1. router logits = gate(x), fp32; top-k selection (k=2), softmax over the k
   logits; Switch aux from the full softmax.
2. For each expert, gather the tokens assigned to it, run SwiGLU, scatter-add
   with the router weights. Shared expert, when present, runs on all tokens.
3. Dense-combined mode runs every expert on every token and sums with the
   sparse routing weights. It is the fallback for the unresolved ROCm sparse
   fault and costs E/k times the expert compute.

Attention: causal mask, plus a sliding window of 256 for six of eight layers;
layers 3 and 7 are full. Context 512 means the full layers see the whole
prefix; the SWA layers see the last 256 tokens.

## 6. Attention and MoE decisions

- **GQA 8Q/2KV** instead of MHA 8/8: KV cache and projection parameters drop
  by 2.3M per model at this width; the v2 result and the reference configs
  support it. MHA would add parameters without a demonstrated benefit at this
  scale.
- **Hybrid SWA 256 + full every 4th layer**, as in v2: reduces attention
  compute and memory at context 512 while one full layer per group keeps
  global reach. Full attention everywhere would add roughly 25 % attention
  FLOPs and a 512 x 512 buffer per layer; the benefit at 0.1B is unproven.
  The first GPU run should keep the v2 pattern for comparability.
- **Top-2 routing** as primary: better load balance than top-1 and the
  configuration already validated in v2. Top-1 (candidate D) is cheaper
  (35.0M active) but more prone to collapse; the shared expert and aux loss
  are not a guarantee.
- **Shared expert optional**: A/B use routed-only to keep the active count
  and the architecture simple; C/D add one shared expert for stability and
  always-on capacity. The comparison is explicit, not a default.
- **Aux loss 0.01**: Switch-style, as in v2. It is a load-balancing pressure,
  not a quality feature. Capacity and token distribution are monitored by
  router entropy and expert share; no capacity factor is implemented
  (tokens are not dropped).
- **Context 512** primary; 1024 is supported by the config (block_size and
  RoPE) but doubles attention cost and activation memory; it is a later
  controlled change, not part of the baseline.
- **Untied head** primary: at 8192 vocabulary the embedding and head are
  4.19M each (8.4M total). Tying would save 4.19M total and active; it is
  left as a config option (`tie_embeddings`) for an ablation, not silently
  enabled.

## 7. Recommendation

**Primary A** (8 layers, 512 width, top-2, 98.34M total / 36.41M active).
It is the simplest configuration in the target range, keeps v2 comparability,
and has the best balance between capacity and active compute. **Fallback C**
(12 layers, 384 width, top-2 + shared, 95.88M / 39.92M) if routing
stability or the depth/width tradeoff needs a second point. B is a depth
ablation; D is the top-1/shared variant. No configuration is a claim about
quality before training.

## 8. MTP exclusion

Removed from v3.1-A:

- config fields `n_mtp` and `mtp_weight`;
- the shifted t+2 logits/CE in the loss and the `mtp_ce` metric;
- any MTP metadata in a future checkpoint or inference path.

MTP added no parameters in v2 (it reused the trunk and the untied head), but
it changed the training objective and the reported composite loss. v3.1-A
uses main next-token CE plus the router aux term only. Inference is
next-token only.

Historical v2 MTP code and checkpoints stay untouched in `veylith/v2/`.

Reintroduction as a controlled ablation: add `n_mtp=1` with the shared head
and a weight w, train the same data/seed/config with w=0.0 (baseline) and
w=0.2/0.5, then compare main CE and bits/char per source, MTP CE, train/val
gap, router entropy and generation. A benefit is only claimed if the main
objective improves on the frozen held-out split without a regression in
calibration or routing. No MTP code is part of v3.1-A.

## 9. Risks and unresolved questions

- **ROCm sparse fault**: the v2 sparse path faulted on this GPU; the
  dense-combined path worked. The design defaults to algorithmic sparse but
  the first GPU run must include a bounded sparse smoke test; if it faults,
  dense-combined is the fallback (higher compute, same architecture).
- **Routing stability** at 8 experts/top-2 with only ~96M tokens: monitor
  entropy and expert share; top-1 is riskier.
- **Data sufficiency**: 95.95M tokens is about 1 token per parameter; this is
  a single-pass baseline, not a compute-optimal model. See V3.1-DESIGN.md.
- **Synthetic data**: 15.9 % Cosmopedia; per-source evaluation is mandatory.
- **Attention kernel**: the reference uses manual attention; the GPU trainer
  must use SDPA/flash and verify the SWA mask equivalence.
- **Checkpoint format**: not implemented in v3.1-A; the first training
  implementation must define it, with optimizer/RNG and no MTP fields.
- **Hyperparameters**: LR, warmup, batch, dropout are not tuned; inherit v2
  (3e-4, 100, 64, 0.1) for the first run.
