# v3.1-PERF-5C faulting kernel attribution

Status 2026-10-27. Bounded GPU diagnostic, two executions. No production change,
no package change, no reset, no retry.

**Outcome: strong correlation without direct identification.** In two independent
runs the GPUVM fault address is exactly the end of a 4 MiB allocation holding a
682 x 3075 bf16 buffer (4,194,300 bytes, 4 bytes of slack), and in the
serialized run that buffer is the output C of the last backward GEMM dispatched
before the abort (M=682, N=3075, K=256). The kernel name itself is still not
captured: this build prints none on the fault path, and the instrumented run
aborted inside the autograd worker thread before the profiler trace could be
exported.

## 3. Strategy and what was executed

Plan: one reference run (no instrumentation beyond the hipBLASLt log and the
kernel log) to confirm the fault, then one attribution run with
`AMD_SERIALIZE_KERNEL=3` and a profiler whose trace is exported from a `finally`
block, relying on the serialization to make "last recorded kernel" equal
"faulting kernel", and on `External id` to name the `aten` op.

| # | case | instrumentation | result |
|---|---|---|---|
| 1 | baseline | hipBLASLt Trace log, kernel log | **faulted**, exit 1, catchable HIP illegal address at the next H2D copy |
| 2 | attribution | the same plus `AMD_SERIALIZE_KERNEL=3` and `torch.profiler` (CPU+GPU) | **faulted**, exit -6 (SIGABRT) inside the autograd worker thread; no trace written |

Both runs: 4 kernel-log page-fault records at one 2 MiB-aligned address, no
reset line, GPU idle and responsive afterwards, no KFD process left.

The second run's abort path is worth recording precisely:

```
terminate called after throwing an instance of 'c10::AcceleratorError'
  what():  CUDA error: an illegal memory access was encountered
... Exception raised from SetDevice at c10/hip/HIPFunctions.cpp:334
frame #5: torch::autograd::Engine::thread_main(...)
frame #6: torch::autograd::Engine::thread_init(...)
```

The sticky error was picked up by the **autograd worker thread** at its next
`SetDevice`, and the uncaught C++ exception terminated the process. The profiler
had started (`profiler_start` in stderr) but the export never ran, so the
dispatch list the profiler had collected was lost. That is the single reason
attribution stops at "correlated" rather than "identified".

## 4. Dispatch-to-fault evidence

Both runs' fault addresses were matched against every hipBLASLt call's C buffer
in the same run's own log (pointer from `C=0x...`, extent from `Cdesc` rows x
cols x 2 bytes):

| run | fault page | nearest C buffer | tensor extent | tensor end | gap to fault page |
|---|---|---|---:|---|---:|
| baseline | `0x7f3b44c00000` | `0x7f3b44800000` | 4,194,300 | `0x7f3b44bffffc` | **4 bytes** |
| attribution | `0x7fdb92000000` | `0x7fdb91c00000` | 4,194,300 | `0x7fdb91fffffc` | **4 bytes** |

In both runs the buffer is 682 x 3075 x 2 bytes, its base is 2 MiB-aligned, the
allocator rounded it to exactly 4,194,304 bytes, and the fault page begins 4
bytes after the tensor's last element, i.e. exactly at the end of the 4 MiB
block. The next-closest buffer in either run is 7,680 bytes away, so there is no
ambiguity about which allocation the fault page belongs to.

In the attribution run that buffer is the **C output of the last backward GEMM
dispatched before the abort**:

```
A=0x7fdb64e4ea00 Adesc rows=682 cols=256 ld=682
B=0x7fdb5bbebe00 Bdesc rows=256 cols=3075 ld=256
C=0x7fdb91c00000 Cdesc rows=682 cols=3075 ld=682   transB=OP_T
```

i.e. M=682, N=3075, K=256: the expert `w3` backward input-gradient GEMM for the
routing subset of 3,075 tokens in that iteration. The dispatch after it writes a
different C (`0x7fdbf29a4800`, 256 x 682) and touches neither the boundary buffer
nor the fault page.

## 5. Evidence classification

- **Directly identified faulting dispatch:** none. No kernel name, no dispatch
  id, and the trace was lost to the abort.
- **Strong correlation without direct identification:** the fault page is the
  end of a specific 4 MiB allocation, reproduced in two independent runs with
  different absolute addresses, and in the serialized run that allocation is the
  C output of the last backward GEMM before the abort. Nothing else in either
  log comes within 7 KiB of the fault page.
- **Candidate kernels, ranked:** (1) the expert `w3` backward GEMM that writes
  that C buffer; (2) the first consumer of that buffer between it and the next
  GEMM (an elementwise cast, routing-weight multiply, or accumulation), since the
  fault may be a read by a later kernel and the kernel log's `RW: 0x0` suggests
  a read rather than a store.
- **Unsupported attribution:** the historical 16E hipBLASLt K-tail over-read.
  That hypothesis predicts a fault past the end of the *B operand* inside a
  GEMM with a partial N tile; here the fault is at the end of a *C output* of a
  different shape class, in an 8E/top-2 run that never dispatches the 16E
  geometry. The two must stay separate; this stage does not test 16E.

## 6. Backend isolation findings

- `torch.backends.cuda.preferred_blas_library` accepts `hipblas` (not
  `rocblas`) in this build. PERF-5B already showed that route is **not
  independent**: rocBLAS delegated 23,091 calls to
  `rocblas_gemm_hipblaslt_backend`.
- `librocblas.so` contains `ROCBLAS_USE_HIPBLASLT`, and the pinned source
  excerpt (`rocblas_handle.cpp`, archive `rocm-libraries-cd957402`) reads it and
  sets `hipblasltEnvVar = 0` for any value other than `1`. That is a plausible
  genuine non-hipBLASLt path.
- It was **not verified in-run**, because that would need its own GPU execution
  and the budget is two reproductions. Backend independence therefore remains
  undemonstrated, and no backend comparison was run. This is a deliberate stop,
  not an oversight.

## 7. Confidence and limitations

- The address correlation is exact and reproduced twice; it is the strongest
  evidence obtained so far and narrows the faulting operation to the
  `w3` backward GEMM class for this configuration.
- It is not a kernel identification. The store-versus-read question and the
  GEMM-versus-consumer question are both open, and the fault could in principle
  be a few bytes of over-read by a vectorized elementwise kernel that consumes
  the same buffer.
- The profiler's presence did not prevent the fault but did change the failure
  mode (SIGABRT in the autograd thread instead of a catchable error on the main
  thread), so the two runs are not identical workloads.
- The 8E/top-2 reproducer and the historical 16E/top-4 capture remain distinct
  configurations with different dispatched geometries; nothing here transfers
  one attribution to the other.
- No statement is made about v3.1-E or v3.1-J beyond the shared fault signature.

## 8. Recommended next experiment

One bounded run, no shape sweep:

1. `torch.profiler` with a **cycling schedule** (`wait=1, warmup=1, active=1,
   repeat=-1`) and `on_trace_ready` writing `trace-<cycle>.json` on every cycle,
   so the trace of the faulting iteration is already on disk before the abort.
2. Keep `AMD_SERIALIZE_KERNEL=3` off in that run (it is what turned the catchable
   error into a SIGABRT) and instead rely on the per-cycle trace plus the
   address mapping, which is already proven reproducible.
3. Script the address-to-buffer mapping used in section 4 so the boundary buffer
   is identified automatically from the fault address.
4. Only then, and in a separate execution, verify `ROCBLAS_USE_HIPBLASLT=0`
   produces `rocblas_gemm_tensile_backend` records, which would make a backend
   comparison admissible.

Success for that run: a trace covering the faulting iteration whose last
`aten` op (via `External id`) names the kernel family that touches the boundary
buffer. Anything less stays "strong correlation".
