# v3.1-PERF-5M front-padded product control

Status 2026-10-27. One GPU execution, used. No production change, no checkpoint
change, no package change, no reset, no retry, no serialization, no push.

**Outcome: classification 3, inconclusive. The run is valid and clean, but no
product can be shown to end within a vector access of its mapped boundary, so it
cannot settle the layout-versus-protection comparison.**

The arm did produce the 4-byte *page* remainder on the faulting shape and both
`w3` consumers read it, 11 dispatches across 6 products. But a 64 KiB front pad
is a multiple of the page size, so it left the page remainder untouched while
moving the 2 MiB grid line, the place where a rounded allocation block would
end, 65,536 bytes away. Under either mapping model the operand was not as tight
as in the stock runs that faulted.

## 2. Implementation

New experimental mode 3, `PaddedMulFront`:

```python
raw  = torch.empty(tensor_bytes + 65536, dtype=torch.uint8)
view = raw[65536:65536 + tensor_bytes].view(dtype).view(shape)
torch.mul(a, b, out=view)
```

The view keeps the original shape, dtype and contiguous strides, ends exactly at
its backing storage end, and is written directly with no copy. `SwiGLU.forward`
is replaced per instance; `w3` is untouched, so the product gradient stays a
stock ATen allocation in both directions of the comparison. Modes 0, 1 and 2 are
unchanged and still pass their gates.

## 8. Gate D, boundary exposure

Two distances matter and the record keeps them apart:

- `page_dist`, the distance from the logical end to the next 4 KiB page end. In
  the stock runs this was 4 bytes, which is what faulted twice.
- `grid_2mib_dist`, the distance to the next 2 MiB line, which is where a
  rounded allocation block would end. In the stock runs this was also 4 bytes,
  because the allocation's own size rounded up to that line.

This run, page remainder over all product reads:

| page_dist | 0 | 4 | 8 | 12 | 16 |
|---|---|---|---|---|---|
| reads | 733 | **11** | 12 | 20 | 12 |

Products at page_dist 4, including the faulting shape, all read by both
consumers:

| shape | page_dist | grid_2mib_dist | trailing bytes | 2 MiB rounding gap |
|---|---|---|---|---|
| `(3075, 682)` at `0x7fbfe8810000` | **4** | 2,031,620 | 0 | 2,031,620 |
| `(2819, 682)` | 4 | 283,652 | 0 | 283,652 |
| `(4099, 682)` | 4 | 634,884 | 0 | 634,884 |
| `(4611, 682)` | 4 | 2,033,668 | 0 | 2,033,668 |
| `(5635, 682)` | 4 | 636,932 | 0 | 636,932 |
| `(7171, 682)` | 4 | 638,980 | 0 | 638,980 |

For the faulting shape the logical end was **4 bytes** before its 4 KiB page end
and **2,031,620 bytes** before the next 2 MiB line. The smallest 2 MiB rounding
gap among all products read at page_dist ≤ 16 is 283,652 bytes.

Mapping beyond the logical end: **unknown**. The view ends at its storage end, so
the storage gives no trailing bytes; whether the allocator block and the driver
mapping continue past it is not visible in the record, and this run did not try
to observe it. If the mapping ends at the page, those 11 reads had 4 bytes of
mapped slack, exactly the stock condition. If the block extends to the next
2 MiB line, they had at least 283 KB. The two readings point in opposite
directions and the data cannot choose between them.

## 10. Why the arm cannot settle it

The stock fault geometry exists because a 4,194,300-byte request ends 4 bytes
before the next page and at the same time 4 bytes before the 2 MiB line where
its own block ends: the page remainder and the block remainder coincide.

Adding 65,536 bytes of front padding, a multiple of 4 KiB, leaves the page
remainder exactly as the base alignment gives it but moves the 2 MiB line where
the block ends 65,536 bytes away from the logical end. The two remainders no
longer coincide, so the operand is tight against a page that is probably not the
end of its mapping.

That is the trap the mission warned about, and it is now measured rather than
assumed: zero trailing storage bytes does not mean an unprotected tensor.

## 11. Recommended next experiment

Front-pad by exactly **2,097,152 bytes**, one 2 MiB page. Because 2 MiB is a
multiple of both the page size and the block granularity, the pad leaves both
remainders unchanged: the logical end stays 4 bytes before the page end and
4 bytes before the 2 MiB line where a rounded block ends, while the allocation
doubles and the address shifts by 2 MiB. Under either mapping model the operand
is then exactly as tight as stock, with zero trailing storage bytes.

Gates: whole-model CPU bitwise for the new pad size, the same isolation checks
(offset 2,097,152, trailing 0, end at storage end, gradient stock), descriptors
unchanged, and a census that must show `page_dist == 4` and
`grid_2mib_dist == 4` for at least one product actually read by both consumers.
A fault there would show that the trailing proximity is what matters and that
the earlier clean runs were protection, not layout. A clean run there would be
the strongest available evidence that layout, not over-read, drives the fault.
