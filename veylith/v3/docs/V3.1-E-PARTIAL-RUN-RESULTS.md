about 115 s. No checkpoint after step 0 exists. Per the authorization there
was no retry, no dense fallback, no further training, and no test evaluation.

## 11. Faults, warnings and deviations

- Fault: `Memory access fault by GPU node-1 ... Reason: Page not present or
  supervisor privilege`. Exit code 134, SIGABRT. The coredump handler failed
  with status 1 and wrote no core file.
- The kernel log for 07:05-07:08 UTC shows no amdgpu error and no GPU reset,
  only unrelated Bluetooth USB resets. The fault was reported by the ROCm
  runtime; the GPU stayed responsive and returned to idle.
- No KFD PIDs after the fault. Kernel 7.2.11-zen1, ROCm 7.2.4 and Mesa
  26.2.5 are unchanged.
- No NaN or Inf loss, no OOM, no router collapse and no update over 120 s
  before the fault. Loss and gradient norm fell normally.
- The fault is consistent with the historical ROCm sparse-MoE fault. This is
  one occurrence on real data at roughly 80 updates. The 8.3 s v3.1-C smoke
  did not reproduce it, so that smoke was not sufficient evidence of
  long-run stability.
- Deviation: preflight counted the test split's shard metadata (token and
  sequence counts) but read no test text or token arrays. It had no influence
  on training or selection.
- No retry, no dense fallback, no system change, no push.

## 12. Recommendation

1. Do not resume this run. The GPU fault is unresolved and a resume would be
   an unauthorized retry.
2. Treat the fault as the primary blocker, not the training code. The
   confirmed 60 updates were numerically healthy: main CE 8.85 to 7.42, grad
   norm 1.93 to 0.27, router recovered from the step-10 dip.
3. A separately authorized fault-isolation pass should use short real-data
   runs with 25 or 50-step checkpoints and isolate sparse MoE versus SDPA
   versus the optimizer path. Dense-combined remains a separate-approval
   fallback, not an automatic switch.
4. If the sparse fault reproduces quickly, the next decision is a controlled
   sparse-versus-dense comparison with the same data and step budget, not a
   full pass.
5. Keep the exact prefix-decode evaluation and the step-suffixed checkpoints.
   Both worked. Add the 50-step first checkpoint before the next attempt.
6. Do not start the 500M-1B-token scaling phase until the GPU fault has a
   proven mechanism or a proven safe configuration.
