## 2. Feasibility study

**Where the buffer comes from.** The 682 x 3075 bf16 buffer is the input gradient
of the expert `w3` linear (`hidden 682 -> embd 256`, no bias) in
`veylith/debug/sparse_moe_v2_train.py`. ATen allocates it inside the linear's
backward node (`MmBackward`/`AddmmBackward`); no Python hook can supply an output
buffer to that node.

**Why `out=` alone is not a substitute.** `torch.mm(..., out=)` does not
participate in autograd, so it cannot replace the node in place. Reaching the
allocation requires replacing the node with a custom autograd `Function` that
performs the same two GEMMs:

```
grad_input  = mm(grad_output, weight_cast, out=<padded view>)
grad_weight = mm(grad_output.t(), x).to(weight.dtype)
```

with `weight_cast = weight.to(grad_output.dtype)`, mirroring what autocast does
(ATen reaches this through its own cast node).

**A trap that the CPU gate caught.** The first version allocated the padded
buffer with the wrong shape, and `mm(out=)` silently *resized* it, which would
have discarded the padding while still producing correct values. The gate now
checks that the write lands in the padded view (`out_wrote_into_view`), that the
returned tensor keeps its pointer and storage (`pointer_preserved`,
`storage_preserved`), and that no resize occurred. This is exactly the
interchangeability assumption the brief warns about, and it is measureable.

**Mechanism chosen.** `veylith/v3/perf/v31p5g_pad.py` replaces each
`SwiGLU.w3` with a wrapper whose backward writes the input gradient into a
storage of `tensor_bytes + 64 KiB`, using a `(rows, cols)` view at offset 0 so
the logical tensor keeps its shape, contiguous strides and dtype while 64 KiB of
accessible slack follows it. No post-GEMM copy is introduced; the GEMM writes
directly into the padded view.

## 4. Executions

### A, reference (valid)

| item | value |
|---|---|
| command | experimental harness, `--pad 0` (no wrapper applied) |
| result | **faulted**, HIP illegal address, exit 1 |
| wide GEMM calls | 6, descriptors `(682, 3075, 682)` and `(256, 3075, 256)` |
| minimum gap from the 682-wide output end to the next 2 MiB page | **4 bytes** |
| GPU afterwards | idle, no reset |

So the reference geometry is confirmed again, in the same harness that would run
the padded arm.

### B, padded (invalid)

| item | value |
|---|---|
| command | same harness, `--pad 1` |
| result | exited 1 with `RuntimeError: expected mat1 and mat2 to have the same dtype, but got: c10::BFloat16 != float` |
| fault | none |
| wide GEMM calls | **0** |
| padded allocations | 1, shape `(2932, 682)` bf16, stride `(682, 1)`, contiguous, offset 0 |
| slack behind the tensor | **65,536 bytes**, 67,568 bytes from the tensor end to the page-rounded storage end |
| GPU afterwards | idle, no reset |

**The arm is invalid, not clean.** The wrapper allocated the intended buffer and
then raised in its backward: it passed the fp32 master weight to a bf16 `mm`
because the first version did not mirror autocast's weight cast. No GEMM ran with
a padded output, so no conclusion about the boundary is possible from this run.

The failure is fixed in the committed harness (explicit `weight_cast`, and the
weight gradient returned in the parameter dtype) and the fix is covered by the
CPU mixed-dtype gate above. It is **not** GPU-verified.

## 5. Interpretation

| class | verdict |
|---|---|
| 1, boundary dependence supported by a valid comparison | no |
| 2, boundary dependence contradicted by a valid comparison | no |
| 3, fault reproduced but output manipulation invalid | **yes** |
| 4, fault not reproduced | no |
| 5, inconclusive | yes for the causal question |

**Confounding factors.** Even a successful padded arm would not be a pure
control: the wrapper replaces an ATen backward node with a custom Function, so
the autograd graph differs in node type even when every gradient is bitwise
identical, and the allocation pattern of the whole backward changes. Kernel
identity must therefore be checked from the hipBLASLt descriptors in the padded
run, not assumed.

**What is established.** The reference fault and its geometry are reproducible in
this harness; the padded mechanism produces the intended 64 KiB slack geometry on
the device for the target tensor; and the `out=` interchangeability question is
now answered by measurement rather than assumption.

## 6. Recommended next step

One bounded run of the corrected padded arm (a fresh authorization is needed
because the two-run budget is spent), with the same containment, and these gates
before any fault interpretation:

1. **Descriptor equivalence:** the padded run's 682-wide `Cdesc` rows, cols, ld
   and transpose flags must match the reference's `(682, 3075, 682)` /
   `(256, 3075, 256)`; any change invalidates a same-kernel claim.
2. **Placement validity:** every padded allocation must show `slack_after_tensor
   >= 64 KiB` and the distance from the tensor end to the page-rounded storage
   end must exceed 44 bytes, otherwise the arm is invalid rather than clean.
3. **Numerical equivalence on device:** the first iteration's loss and the
   gradient norms must match the reference bitwise; a mismatch means the wrapper
   changed the computation and the comparison is void.
4. Only then: fault versus clean, which would support or contradict boundary
   dependence with one controlled comparison.

A clean padded run would still not identify the faulty dispatch; it would only
show that moving the boundary removes the fault.
