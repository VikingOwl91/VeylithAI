# v3.1-PERF-4D controlled prefill integration

Status 2026-10-27. Production integration of the verified PERF-4B/4C policy,
with CPU tests and a GPU gate. No architecture, numerical or unrelated
performance change.

**Result: integrated, all gates pass.** The prefill is disabled by default for
training runs, `VEYLITH_DETERMINISTIC_PREFILL=1` restores the previous behaviour
for debugging, deterministic algorithms and their operator checks stay enabled,
and the production entrypoint reproduces PERF-4C bitwise on the verified
resume fixture.

## 1. Implementation diff

Three production touch points, 15 changed lines plus one new module.

| file | change |
|---|---|
| `veylith/v3/training/determinism.py` (new, 97 lines) | policy parsing, application, restoration decorator and log wording |
| `veylith/v3/training/train.py` | `@restores_prefill_state` on `train`, apply the policy right after deterministic mode is configured, one startup log line |
| `veylith/v3/training/checkpoint.py` | `versions.environment.deterministic_prefill` in the provenance block |

```python
# train.py, immediately after use_deterministic_algorithms
prefill_policy = resolve_prefill_policy()
apply_prefill_policy(prefill_policy)
...
log(describe_prefill_policy(prefill_policy))
```

Nothing else moved: model forward and backward, routing, optimizer, precision,
dataset, schedule, checkpoint formats and the configuration fingerprint are
untouched. `torch.use_deterministic_algorithms(True, warn_only=False)` is still
the only call that configures deterministic mode; the policy runs after it, as
required.

Scope note on evaluation-only paths: `training/evaluate.py` is unchanged and
untouched, because the policy lives in `train()`. A standalone evaluation in a
fresh process therefore keeps PyTorch's own default. This needed no scope
expansion.

## 2. Runtime policy behaviour

| `VEYLITH_DETERMINISTIC_PREFILL` | prefill | note |
|---|---|---|
| unset | disabled | default for training runs |
| `0` | disabled | explicit |
| `""` | disabled | explicit empty |
| `1` | enabled | debug |
| anything else (`true`, `yes`, `2`, ` 1`, `1 `, ...) | error | `ValueError` before any training work |

Parsing is an exact match with no stripping or lowercasing, so a malformed
export fails loudly instead of being guessed. Through the CLI the error surfaces
as `error: ...` and exit code 1, which is the existing behaviour for
`ValueError`.

Restoration: `train` is wrapped so the process-global flag is snapshotted on
entry and restored in a `finally`, covering normal returns, `ValueError` from
the policy itself, and any exception raised during training. The wrapper uses
`functools.wraps`, so the signature and docstring are unchanged.

Ordering: the policy is applied after `use_deterministic_algorithms`, which would
otherwise re-enable the prefill. Deterministic algorithms stay enabled in both
modes, and the fill flag is independent of them.

## 3. CPU test results

Full suite: **122 passed, 2 skipped** (previously 96 passed, 2 skipped; 26 new
tests). No test was skipped or relaxed.

New `veylith/v3/tests/test_prefill_policy.py` covers:

- default mode disables the prefill, and reports source `default`;
- `VEYLITH_DETERMINISTIC_PREFILL=1` enables it, and reports source `environment`;
- explicit `0` and `""` disable it, unset is disabled rather than enabled;
- ten invalid values are rejected (`true`, `TRUE`, `yes`, `on`, `2`, `-1`,
  `" 1"`, `"1 "`, `0.0`, `enabled`), and an invalid environment value fails
  resolution;
- deterministic algorithms remain enabled and `warn_only` remains false while
  the prefill is off;
- restoration after a normal return, after an exception, and when the policy
  application itself never runs;
- the startup log wording for both modes;
- the configuration fingerprint is identical with the prefill on and off, and
  the environment variable does not appear in `cfg.to_dict()`.

Additions to `veylith/v3/tests/test_training.py`, using the existing tiny CPU
corpus and real `train()`:

- default mode: the log line is emitted, the saved state's provenance records
  `{"effective": False, "env": None}`, the flag is restored and deterministic
  algorithms remain enabled;
- debug override: the log line, `{"effective": True, "env": "1"}` and
  restoration;
- an invalid environment value raises before any state file is written;
- `evaluate()` leaves the flag untouched and returns identical metrics with the
  prefill on and off.

## 5. Provenance and logging evidence

Startup log, captured from the real runs:

```
deterministic prefill enabled (VEYLITH_DETERMINISTIC_PREFILL='1')
deterministic prefill disabled (VEYLITH_DETERMINISTIC_PREFILL unset)
```

Provenance, stored in `versions.environment` of every state and artifact:

```json
"deterministic_prefill": {"effective": false, "env": null}
```

The `effective` value is read from PyTorch at save time and the raw environment
value is kept beside it, so a run can be classified after the fact even if the
environment is gone. This is additive: `versions` is free-form, `load_state`
does not validate it, and the artifact/state formats stay at 1.

## 6. Checkpoint compatibility

- Fingerprint unchanged: `1212c3d1...` both before and after, proven by the
  resume succeeding through the production `load_state` validation and by the
  CPU fingerprint test.
- The policy is not a config field and does not appear in `TrainConfig`, so it
  cannot drift between writing and reading a state.
- `STATE_FORMAT` and `ARTIFACT_FORMAT` stay 1; `load_state` checks kind, format
  and fingerprint only.
- Existing v3.1 states resume unchanged: the step-250 fixture was loaded by the
  new code and produced identical digests to PERF-4C.
- New states carry one extra provenance key, so their file sha256 differs from
  states written before this change; that is expected and does not affect
  loading. Historical checkpoints were not modified and still hash to
  `6efff008...`, `ab259ebf...`, `865946d6...`.

## 7. Remaining safety limitations

- The prefill is a diagnostic, not a numerical guard. With the default policy a
  future read of unwritten device memory would yield plausible garbage instead
  of a loud NaN; nothing in the loop would flag it. `VEYLITH_DETERMINISTIC_PREFILL=1`
  restores the signal for that kind of investigation.
- Bitwise identity over the gated and 150-update windows is evidence, not a
  proof of memory safety. Allocator priming covered at most 3.0 GiB of a 5.18 GiB
  footprint and no driver or library memory (PERF-4C).
- The policy is process-global. Sequential calls to `train()` restore the flag,
  so they are safe; two training loops in concurrent threads of one process
  would fight over it. This trainer is single-process and single-run.
- Two runs with different policies share a fingerprint by design. Provenance is
  what distinguishes them, so anything comparing runs must read
  `versions.environment.deterministic_prefill` rather than assume it.
- The measured benefit is PERF-4C's: 6.26 percent on the update and 3.28 percent
  on energy per million CE targets. This stage did not re-measure it.
