## 2. Where the product gradient is allocated

`SwiGLU.forward` computes `silu(w1(x)) * w2(x)` and feeds that product to `w3`.
The product gradient is therefore the gradient with respect to the input of the
`w3` linear, and ATen allocates it inside the linear's backward node as the
output of `mm(grad_output, weight)`.

The existing mode 1 harness (`PaddedW3`) replaces exactly that node and writes
the input gradient into padded storage. So mode 1 *is* the gradient-only
intervention: it pads `dL/d(product)` at its source, leaves the forward product
untouched, and needs no inversion of `PaddedMul` and no gradient hook. The
product itself stays a stock `mul` output because `SwiGLU.forward` is not
patched in this mode.

Consumers of the product gradient: the elementwise `MulBackward`, which produces
the gradients flowing to `silu(w1(x))` and `w2(x)`. The GEMMs that read those
downstream derivative tensors are `w1`/`w2` backward, not consumers of the
product gradient itself.

## 9. Interpretation

| class | verdict |
|---|---|
| 1, valid gradient-only run, fault at stock product boundary | **yes** |
| 2, valid gradient-only run, fault elsewhere | no |
| 3, valid gradient-only run, clean with critical exposure | no |
| 4, valid gradient-only run, clean without critical exposure | no |
| 5, invalid or inconclusive | no |

The campaign now has a 2 x 2 on the same configuration and stack:

| arm | forward product | product gradient | runs | faults |
|---|---|---|---|---|
| PERF-5I, **PERF-5L** | stock | padded | 2 | **2** |
| PERF-5J, PERF-5K | padded | stock | 2 | **0** |

Both faults in the left column are page-exact with the stock product's tail,
including this one, where the nearest padded gradient storage ends 167,592 bytes below the fault page. The
gradient padding does not prevent the fault, and within this campaign it never
did.

What this does not establish: causal identification of the kernel. A fault at
another allocation would not have identified the original kernel, and this fault
is at the product, not at the padded gradient. The most defensible statement is
that the fault follows the stock product's page-ending operand read, and that
protecting that operand's storage removes it in two of two attempts.

## 10. Limitations

1. Two arms, four runs, one device, one driver, one harness. This is a strong
   association, not proof.
2. PERF-5L is a replication of the PERF-5I arm, not a new mechanism; its value is
   the exposure census and fault-page attribution that 5I lacked.
3. Kernel identity and the over-reading instruction remain unobserved.
4. The gradient-padded arm changes allocation layout as well as protection, so
   the 2 x 2 cannot separate "slack behind the operand" from "different
   allocator state".
5. The tail-52 control is a single observation.

## 11. Recommended next experiment

Separate protection from layout: pad the product's *front* instead of its tail.
Allocate `tensor_bytes + 64 KiB` and place the product at offset 64 KiB so the
storage ends exactly at the tensor end. The allocation size and address change
while the tail geometry and the absence of trailing slack are preserved.

- If the fault returns, tail protection is what matters and front padding is not
  a workaround.
- If it stays clean, the earlier clean runs were produced by allocator
  perturbation rather than by protecting the operand, which would weaken the
  whole operand hypothesis.

The usual gates apply: whole-model CPU bitwise, descriptors, per-allocation
slack and tail census, full-precision first loss. The arm is only informative if
the census shows a product actually landing at tail 1 to 64; otherwise it is
class 4, clean without exposure.
