# v3.1-PERF-2 actual-shape BF16 GEMM benchmark

Status 2026-10-27. Stage 2 benchmark only; no optimization implemented.

**Decision: Investigate elementwise kernel fusion and dtype conversions.**

The current PyTorch default on this ROCm build is already hipBLASLt, not
rocBLAS. Against the only other selectable BF16 backend (rocBLAS), hipBLASLt is
equal or faster on the weighted shape inventory: switching to rocBLAS would add
an estimated **3.96 ms per update** (1.6 percent of the 245 ms GEMM budget,
0.5 percent of a 0.78 s update). CK is installed but unsupported on gfx1201.
Outputs are bitwise identical across both backends on all 24 cases. With GEMM
backend headroom exhausted at this level, the next measured target is the
elementwise plus copy aggregate identified in Stage 1.

## 2. Backend discovery (the premise needed correction)

Stage 1 assumed the baseline was Tensile/rocBLAS. Measured instead:

- `torch.backends.cuda.preferred_blas_library()` exists and its default and
  current value are **Cublaslt**, i.e. hipBLASLt on this build.
- Setting `cublas` switches to rocBLAS. Direct library logs confirm the
  dispatch: `rocblas_gemm_ex` for rocBLAS, `rocblaslt_matmul` for hipBLASLt.
  Both are called per case in their respective configurations (24 log lines
  each, one per shape).
- `Ck` is compiled in but rejected on this architecture:
  `RuntimeError: ... architecture supported for CK GEMM: 0`. No other
  installed BF16 BLAS backend exists. Triton is present, but a Triton matmul
  would be a new kernel, not an installed path, so it was not used.
- `TORCH_BLAS_PREFER_HIPBLASLT=1/0` selects the same two settings at import
  time.

So the comparison is **current hipBLASLt versus rocBLAS**, not the reverse.
PERF-1's `Cijk_...` kernels appear under both libraries because hipBLASLt uses
Tensile-generated kernels too; kernel names alone do not identify the library.

## 4. Method

- One backend per process; `preferred_blas_library` set before tensor creation.
  Two independent timing runs per backend, plus one dispatch run.
- Deep-queue timing: 50 warmup calls, then 10 synchronized repetitions per
  case, each sized to about 100 ms (100 to 6,059 iterations). The first pass
  used only 200 iterations and was CPU-launch-bound; it was discarded. With
  the final queue depth, the dominant case measures 59 microseconds per call,
  consistent with Stage 1's 54.8 microseconds of GPU time per call.
- Preallocated output (`torch.mm(A, B, out=C)`) for the primary timing, so the
  comparison reflects the GEMM rather than allocator overhead. The allocating
  path was measured separately for the six largest cases and agreed within
  0.002 ms.
- Numerical check: same deterministic inputs in every process; outputs saved
  per case and compared elementwise across backends, with an FP32 GPU
  reference for scale.
- Dispatch: one call per case with `HIPBLASLT_LOG_LEVEL=3` and
  `ROCBLAS_LAYER=1`, plus a one-call profiler capture for kernel names.
- Workspace: hipBLASLt reports it in the log; rocBLAS does not expose it.
- Energy: 10 Hz PPT sampling during the runs; GPU package power only.
- No autotuning, no persistent tuning caches, no global environment changes.

Totals:

| metric | value |
|---|---:|
| weighted hipBLASLt minus rocBLAS | **-3.96 ms/update** |
| share of the measured 248.9 ms GEMM inventory | **-1.59 %** |
| share of the Stage-1 245 ms GEMM budget | -1.61 % |

Sign: negative means hipBLASLt is faster. The current default already is
hipBLASLt; **switching to rocBLAS would cost about 4 ms per update**, not save
it. hipBLASLt wins the three dominant shapes (0.972 to 0.992); rocBLAS wins
three small shapes by 7 to 8 percent, worth 0.63 ms/update in total and not
addressable without a per-op backend switch that PyTorch does not expose.

Variability: run-to-run median difference 0.78 percent (rocBLAS) and 0.94
percent (hipBLASLt), maximum per case 7.1 and 5.4 percent. Within-run
p95/median is 1.007 and 1.010 on average, worst case 1.57 and 1.53. The
weighted 1.6 percent difference is larger than the median run noise but close
to the worst-case per-case noise; the direction on the three dominant shapes is
consistent across both runs.

## 6. Numerics

All 24 cases produce **bitwise identical BF16 outputs** between rocBLAS and
hipBLASLt (maximum absolute difference 0.0). The FP32 GPU reference shows the
expected BF16 rounding scale, for example case 0: max abs 0.25, mean abs
0.0255, relative L2 0.00166. No numerical failure, no silent precision change,
no dispatch rejection.

## 7. Dispatch evidence

| | rocBLAS | hipBLASLt |
|---|---|---|
| library call | `rocblas_gemm_ex` | `rocblaslt_matmul` |
| log lines | 24 | 24 |
| case 0 trans flags | transA=T, transB=N | transA=OP_T, transB=OP_N |
| case 0 kernel | `Cijk_Alik_Bljk_BBS_BH_..._MT64x64x32_...` | same Tensile kernel |
| extra kernel | `__amd_rocclr_fillBufferAligned.kd` (workspace fill) | none observed for this shape |

Both libraries dispatch Tensile BF16 kernels; the difference is library
heuristics and workspace handling, not a different kernel family for the
dominant shape. GEMM inputs were confirmed as `bf16_r`, compute as `f32_r`,
and the transposed views were passed as `OP_T` rather than materialized.

## 8. Workspace and memory

- hipBLASLt reports **79,691,776 bytes (76 MB)** of workspace for every case,
  a fixed allocation in this build.
- rocBLAS does not expose workspace in its log.
- Peak VRAM over the whole inventory: hipBLASLt 0.589 GB reserved / 0.562 GB
  allocated; rocBLAS 0.543 GB reserved / 0.516 GB allocated. The roughly 46 MB
  difference is consistent with the hipBLASLt workspace.
- No unexpected memory growth across runs; no OOM.

## 9. Power telemetry

PPT (`power1_average`, GPU package) at 10 Hz during the runs: hipBLASLt mean
282.5 W, max 399 W, sclk 2.70 GHz, 94.3 percent busy; rocBLAS mean 283.8 W,
max 405 W, sclk 2.70 GHz, 94.5 percent busy. Whole-system wall power was not
measured. The benchmark windows are short, so these are activity indicators,
not a per-GEMM energy measurement.

## 10. Effect estimate and its limits

Applying the isolated per-case deltas to the Stage-1 call frequencies gives
-3.96 ms/update, i.e. rocBLAS would be 1.6 percent slower on the GEMM portion
and about 0.5 percent slower per training update. This is an **estimate under
perfect transfer**: in training the GEMMs are interleaved with elementwise and
copy kernels, clocks and queue behaviour differ, and no end-to-end run was
performed. The estimate is an upper bound on the benefit of switching, and the
benefit is negative.

## 11. Measured, derived, unknown

**Measured:** per-case latencies for both backends across two processes;
outputs bitwise identical; library dispatch from logs; trans flags and kernel
names; hipBLASLt workspace; peak VRAM; PPT power; CK rejection.

**Derived:** weighted per-update delta; percent of GEMM budget and update;
`p95/median`; run-to-run variability.

**Unknown:** whether a per-shape backend mix could capture the small rocBLAS
wins (no supported mechanism); whether non-Tensile kernels from a future ROCm
release would change the picture; the exact rocBLAS workspace.

## 12. Decision

**Investigate elementwise kernel fusion and dtype conversions.**

Why not "proceed with a bounded GEMM backend integration experiment": the
current default is already the faster backend. A bounded integration of
rocBLAS would make training slower by about 4 ms/update, and no per-op
switching API exists to harvest the small rocBLAS wins. CK is unsupported on
gfx1201, and no other installed BF16 path exists.

Why not "insufficient evidence": the measurement is now deep-queue and
stable, matches Stage 1's absolute per-call GPU time, and the outputs are
bitwise identical. The remaining uncertainty is smaller than the sign of the
result.

Why elementwise next: Stage 1 measured elementwise at 309 ms/update (42.5
percent of GPU time, 26,230 kernels) plus copies/dtype conversions at 82
ms/update (11.2 percent), together 53.7 percent, against GEMM's 33.7 percent.
With the GEMM backend question settled, that aggregate is the largest measured
remaining cost.
