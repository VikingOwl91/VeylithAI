## 2. Instrumentation

Two layers, both experimental, in `perf/v31p5p_provenance.py`:

- **Allocator history.** `torch.cuda.memory._record_memory_history(enabled="all",
  context="all", stacks="all", max_entries=50000)`. Allocations, frees and
  timestamps come from the allocator itself, at C++ level, with no operator
  interception. Snapshots are dumped to a single rotating file every 25 batches,
  plus one on fault and one at exit, so a SIGABRT cannot destroy everything.
- **Size-filtered tags.** A `TorchFunctionMode` that only inspects a small
  operator allowlist and only records BF16 tensors of exactly 4,194,300 bytes,
  plus a tensor hook on each tagged tensor so its gradient is tagged too. The
  mode calls the original function and only reads the result, so storage,
  autograd and dispatch are untouched.

Joins key on `(pointer, byte count, lifetime)`. A pointer alone never decides: the
PERF-5N fault address falls inside an earlier, unrelated allocation's storage.

## 5. Required observations

Operand census for BF16 `(3075, 682)` GEMM operands in this run: five distinct
pointers. Two of them sit at page distance 4 **and** grid distance 4.

| pointer | producer (observed) | phase | reads | OP_N | OP_T | fault |
|---|---|---|---|---|---|---|
| `0x7fbef0e00000` | `?.mul` | forward | 2 | 1 | 1 | none |
| `0x7fbecc600000` | `grad_of:torch._C._nn.linear` | backward | 1 | 0 | 1 | none |

Attribution quality:

- **Producer: observed.** Both came from the tag registry, keyed on pointer plus
  byte count, recorded while the tensor existed.
- **Phase: observed.** The product is a forward tensor; the other is the gradient
  of a linear output, produced in the backward pass.
- **Lifetime: partial.** Allocation precedes consumption by construction, the tag
  exists before the read, and no reuse is recorded for either address. Freed
  state is unknown: both addresses were evicted from the bounded history before
  the snapshot was taken, so the join cannot exclude a later reuse.
- **Consumer roles: observed** from the dispatch record.

The other three candidates were not at the critical geometry; two of them are
also tagged, one is untagged (a `linear` output whose tag fell outside the
recorded window).

## 6. The 4-byte gap, directly observed

Eight blocks in the final snapshot have `requested_size == 4194300` and a block
size of **4,194,304**. The allocator's own record therefore confirms the
mechanism proposed in PERF-5M: a 4,194,300-byte request gets 4,194,304 bytes, so
a 2 MiB aligned block ends exactly 4 bytes after the tensor and the next page is
outside the block.

Allocator frames are captured as `torch::unwind::unwind()`,
`torch::CapturedTraceback::gather`, `gather_with_cpp()`, which is the capture
machinery rather than the allocating operator. Layer 1 alone would therefore not
name a producer on this build; layer 2 is what made the attribution observed.

## 7. What this settles, and what it does not

Settled: the product itself reached the exact fault geometry of PERF-5I, 5L and
5N, `page_dist 4` and `grid 2 MiB distance 4`, and was read by both the `OP_N`
and `OP_T` formulations, in a stock unpadded run, and nothing faulted. The claim
that reading a tightly bounded product at that geometry causes the fault is
therefore false as stated, and the earlier 2 x 2 was a coincidence of which run
faulted rather than a property of the padding arms.

Not settled: why three earlier runs faulted at the same geometry. The candidates
that remain are a specific kernel instance or launch configuration, an
asynchronous access from another kernel, or a state-dependent mapping difference.
This run cannot separate them, and the clean result may also reflect the
intermittency already measured in PERF-5F (1 to 3 of 12,919 wide calls) or, less
likely, suppression by the instrumentation.

## 8. Interpretation

| class | verdict |
|---|---|
| 1, fault with producer and lifetime identified | no fault |
| 2, fault with ambiguous provenance | no fault |
| 3, no fault, instrumentation may have suppressed | **yes**, and note that the geometry was present |
| 4, fault at an unrelated allocation | no fault |
| 5, invalid | no, display numerics identical and every CPU gate passed |

This is the strongest form of class 3 available: the run was not clean because the
exposure was missing. It was clean with the same geometry and the same roles that
preceded three faults. A fault page matching a tensor's page is still not proof of
the faulting instruction, and a clean instrumented run is not a fix.

## 9. Remaining uncertainty

1. Whether this run's cleanliness is intermittency or instrumentation. One run
   cannot tell.
2. Which kernel instance over-reads when the fault does occur. The provenance now
   in place would name the tensor but not the instruction; no solution IDs are
   logged in this hipBLASLt build.
3. Whether the fault requires a particular allocation neighbourhood, since the
   geometry and roles were identical here.

## 10. Recommended next experiment

**Repeat the same instrumented stock run twice more, with the full-precision first
loss printed at capture time.** Rationale: the fault's base rate under this exact
configuration has been high (four of six stock-shaped runs before this one), so
two further runs with the tag registry armed discriminate cleanly between
"intermittent, instrumentation-transparent" and "instrumentation suppresses it".
If a fault occurs, the registry and snapshot now name the producer, the phase and
the consumer roles at the fault page.

Gates: display losses identical and the full-precision first loss equal to
`10.481635093688965`; at least one tail-4 operand read in each run; the fault
handler must leave parseable events and a snapshot. Stop after the first fault and
analyse it rather than running the second.
