# v3.1-PERF-4B deterministic prefill elimination

Status 2026-10-27. Bounded experiment. Production files untouched.

**Decision: proceed (option 1). Removing the deterministic NaN prefill is
numerically inert and makes the update 6.6 percent faster.**

Measured on the production training path, four interleaved arms of 60 updates:

| arm | prefill | median update | trimmed mean | CE targets/s |
|---|---|---:|---:|---:|
| b1 | on | 779.7 ms | 779.6 ms | 41,952 |
| n1 | off | 724.6 ms | 727.8 ms | 44,787 |
| n2 | off | 724.9 ms | 725.3 ms | 45,084 |
| b2 | on | 771.8 ms | 772.0 ms | 42,362 |
| **paired** | | **-51.0 ms (-6.57%)** | **-49.2 ms (-6.34%)** | **+6.59%** |

Device time falls 46.2 ms and kernel launches fall 25.8 percent. All 60 updates
of all four arms produce bitwise identical training CE, auxiliary loss and
gradient norms, and the two-update gate is bitwise identical across the real
graph including two distinct allocator priming patterns.

## 2. What was changed, and what was not

One setting, through an experimental shim:

- `veylith/v3/perf/v31p4b_nofill.py` provides `prefill_disabled()` (scoped
  context manager) and `DeterminismShim` (wraps
  `torch.use_deterministic_algorithms` so the production loop runs with kernel
  determinism on and the prefill off, then restores both the wrapper and the
  flag).
- `veylith/v3/perf/v31p4b_harness.py` drives the gate, the profile and the
  production path.

Unchanged: model, parameters, forward and backward math, BF16/FP32 boundaries,
optimizer, learning rate, schedule, dataset, batch size, microbatch count, RNG
seeds, routing, dropout, checkpoint format. `torch.use_deterministic_algorithms`
stays enabled; only `fill_uninitialized_memory` is cleared.

State evidence: in every arm `fill_uninitialized_memory` is `False` while the
gated or timed steps run and `True` immediately after the shim exits, and
kernel determinism stays `True`. The shim intercepted exactly one
`use_deterministic_algorithms` call per prefill-off run and zero per
prefill-on run.

## 3. A harness defect found before Gate 1 could be trusted

The first Gate 1 run returned zero mismatches in all five comparisons, but its
values (`main_ce` 9.120014944655088, grad norm 0.09972061216831) did not match
the PERF-3B/PERF-3D reference on the same step-0 state
(`9.121862960188356`, `1.484588623046875`).

Root cause, proven: the head capture hook was written as

```python
lambda module, inputs, output: captured.setdefault("logits", output.detach())
```

`dict.setdefault` returns the stored value, so the hook returned a detached
tensor. PyTorch replaces a module's output with a non-None hook return, so the
graph was severed at the head and the update was not the real training step.
A two-line CPU check reproduces it: with that hook the output has
`requires_grad=False` and no `grad_fn`; with a hook that returns `None` it keeps
`AddmmBackward0`. PERF-3D was not affected because its hook was a `def` with no
return.

The gate was therefore comparing two equally damaged runs, which is exactly the
failure mode a bitwise gate cannot detect on its own. Comparing against a known
reference digest is what caught it.

After the fix the gate reproduces the reference exactly, and the digests match
PERF-3B and PERF-3D: logits `5b39534159178a7a`, model `525afc2a393952a1`,
gradient `ffe4e4b449542029`, optimizer `ff7bcedf47c7830a`.

## 4. Gate 1: correctness

Five arms, each a separate process with a fresh model built from the verified
step-0 state, two optimizer updates each:

| comparison | mismatched fields |
|---|---:|
| baseline A vs baseline B (determinism) | 0 |
| prefill on vs off | 0 |
| prefill off, primed 0xAA vs unprimed | 0 |
| prefill off, primed 0x55 vs unprimed | 0 |
| prefill off, primed 0xAA vs primed 0x55 | 0 |

Fields compared per update: logits digest, main CE, auxiliary loss, composite
loss, gradient norm, learning rate, router digest, gradient digest, weight
digest, optimizer-state digest. Values: CE `9.121862960188356` then
`9.091102196978962`, grad norm `1.484588623046875` then `1.5635069608688354`.

### Allocator invariance and its coverage limit

Each primed arm filled a 3.0 GiB byte buffer with 0xAA or 0x55, freed it back to
the caching allocator, then ran the same two gated updates. Results are bitwise
identical to the unprimed arm and to each other, so no computed value in those
steps depends on the contents of reusable device memory.

Coverage is partial and this is not a proof of memory safety:

- 3.0 GiB was primed against a 5.19 GiB peak allocation footprint including
  parameters and optimizer state, so roughly the first 3 GiB of new allocations
  could come from primed blocks. Later allocations may come from fresh driver
  segments, which are zeroed by the driver rather than by us.
- Allocations that the model makes before the gated updates (parameters,
  optimizer state, the data plan) are not covered.
- Driver-side and library-side memory (hipBLASLt workspaces, the attention path,
  allocator metadata) is not covered.
- The two priming patterns differ in every byte, but a read that only touches a
  region overwritten identically in both runs would not be detected.

Within that envelope, the test is a strong negative result for uninitialized
reads during the gated steps.

## 5. Gate 2: kernel counts and device time

Five profiled updates per condition, kernel events only, 5-update means:

| family | prefill on | prefill off | delta |
|---|---:|---:|---:|
| NaN prefill kernels | 11,545 | 993 | **-10,552 (-91.4%)** |
| NaN prefill device time | 46.35 ms | 4.09 ms | **-42.26 ms** |
| elementwise | 20,342 / 315.1 ms | 20,342 / 310.5 ms | 0 kernels |
| GEMM | 5,064 / 245.7 ms | 5,064 / 247.4 ms | 0 kernels |
| other | 4,024 / 121.0 ms | 4,024 / 120.0 ms | 0 kernels |
| **total** | **40,975 / 728.17 ms** | **30,423 / 681.99 ms** | **-10,552 / -46.18 ms** |

The residual 993 fills are explicit zero-initialisation in the model and harness
(`new_zeros` per MoE layer, the auxiliary accumulator), not the prefill. GEMM and
elementwise kernel counts are identical, which is the expected shape of a change
that removes allocations' prefills and nothing else.

Profiled wall is not used for any end-to-end claim; the numbers above are device
time only.

## 6. Gate 2: production-path timing

`training.train.train` with the PERF-1 configuration (`stop_after=60`,
`log_every=1`, `eval_interval=1000`, `max_vram_gb=12`), four interleaved arms,
first 10 updates discarded as warmup, 50 measured per arm:

| metric | baseline (n=50 x2) | no prefill (n=50 x2) | delta |
|---|---:|---:|---:|
| median update | 775.7 ms | 724.8 ms | -51.0 ms (-6.57%) |
| trimmed mean | 775.8 ms | 726.6 ms | -49.2 ms (-6.34%) |
| update stdev | 4.1 / 3.2 ms | 17.7 / 3.9 ms | |
| CE targets/s | 42,157 | 44,935 | +2,778 (+6.59%) |
| peak allocated | 5.186 GiB | 5.186 GiB | 0 |
| peak reserved | 5.688 GiB | 5.688 GiB | 0 |
| package power mean | 204.0 / 207.0 W | 210.7 / 210.6 W | +5 W |
| package power max | 313 / 318 W | 327 / 325 W | +12 W |
| process CPU (whole run) | 214.2 s | 129.0 s | -85.2 s (-39.8%) |

Power and occupancy are whole-arm averages including validation and checkpoint
phases, so they are context, not a per-update measurement. Power is slightly
higher without the prefill, which is consistent with the same work done in less
time rather than with more work.

The process CPU drop is much larger than 10,552 launches per update can explain
(at the instrumented 5.8 us per launch that would be about 3.6 s per arm, not
85 s). It also includes two full validation passes and two 1.57 GB checkpoint
writes per arm. I record it as observed and do not claim a mechanism for its
magnitude; the decision rests on wall time and CE targets per second, which are
measured directly.

### Long-horizon equality, beyond the gate

Because both conditions are deterministic and differ only in the prefill, the
two-update gate can be extended to the whole timed run. All four arms produced
**identical training curves for all 60 updates**: step 1 CE
`9.121862960188356`, step 60 CE `7.407413370689`, and every per-step auxiliary
loss and gradient norm identical. That is 60 updates x 8 microbatches of full
forward and backward with zero divergence, which is much stronger evidence than
the two-update gate alone.

experiment proceeds.

## 8. Decision

**Option 1: proceed to a short paired A/B training experiment.**

The change is worth carrying forward because it is numerically inert on the real
graph, it removes a quarter of all kernel launches, and it buys 6.6 percent
throughput with no VRAM cost. Before it goes anywhere near production, one more
bounded experiment should extend the evidence:

- Paired arms of 150 updates, interleaved, resumed from a mid-run state so
  non-zero AdamW moments and a non-zero step counter are exercised (the gated
  runs start from step 0 with empty optimizer state).
- Same two-update gate plus allocator priming at the resume point.
- Confirm the 60-update curve identity holds over the longer horizon, including
  one validation and one checkpoint per arm.
- Re-measure wall, CE targets per second, VRAM and power.

That experiment also has to answer the policy question, which no bitwise gate
can: the prefill is a debugging aid that turns an uninitialized read into a
loud NaN. Turning it off trades that signal for silence. The invariance evidence
above says no such read influences any gated step in this model today; it cannot
say anything about code added later. That trade is a maintainer decision, and
the production change needs separate authorization in any case.

## 9. Unknowns and risks

- Only 60 updates were exercised end to end, from step 0 with empty optimizer
  state. Resume paths, long-run drift and eval-heavy phases are untested beyond
  the two per arm.
- Allocator priming covers at most 3.0 GiB of a 5.19 GiB footprint and does not
  cover driver-side or library-side memory; the invariance result is strong
  within that envelope, not universal.
- The 39.8 percent process CPU reduction is unexplained in magnitude.
- Losing the NaN signal is a real, if quiet, reduction in debuggability.
- Validation and checkpoint phases also allocate; their prefill cost was not
  measured separately.

## 10. Deviations

1. Fixed the harness hook defect described in Section 3 and re-ran all five gate
   arms. The first run's numbers are not used anywhere.
2. Added the allocator-invariance arm set (0xAA, 0x55, unprimed) as specified,
   with its coverage limit documented rather than treated as proof.
3. Ran 60-update production arms rather than a reimplementation, per the PERF-4A
   design, so the metric matches PERF-1 directly.
4. The process CPU metric is reported with a stated caveat instead of being
   presented as a mechanism.
