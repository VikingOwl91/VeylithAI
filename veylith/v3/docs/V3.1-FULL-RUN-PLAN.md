# v3.1-E single-pass full-corpus plan

Status 2026-10-27. One bounded pass over the frozen 95.95M-token training
split with Architecture A. No second epoch, no downloads, no architecture or
corpus change.

## 1. Deterministic plan

Computed with `data_pipeline.loader.plan_sequences(split="train",
seq_len=512, mode="concat")` against
`~/veylith-v3-data/multi-100m-20261026`:

| item | value |
|---|---:|
| training token positions | 95,951,233 |
| concat sequences | 187,405 |
| batches at microbatch 8 | 23,426 |
| accumulation 8 | 2,928 full windows + 1 partial window (2 batches) |
| optimizer updates | **2,929** |
| supervised CE targets | **95,763,828** |
| warmup (3.0 %) | **88 updates** |
| peak LR | 3e-4 |
| final LR | 3e-5 (10 % cosine floor) |
| checkpoint selection | validation macro main CE |

`verify_plan` reports no token reuse, no coverage gap, and the manifest token
total. The last window is partial and is included as one update with the
same token-weighted loss; no sequence is repeated or dropped to round the
count.

## 2. Model and training

Architecture A: 98,340,864 total, 36,409,344 sparse-active, 8 layers, width
512, GQA 8Q/2KV, 8 experts top-2, expert FFN 960, no shared expert, vocab
8192, context 512, NTP only, no MTP. BF16 autocast with fp32 master weights,
SDPA, sparse MoE, AdamW (0.9/0.999, eps 1e-8, weight decay 0.01), gradient
clip 1.0, seed 0, microbatch 8 x accumulation 8 = 64 sequences. Router aux
coefficient 0.01 on the 7-layer sum.

## 3. Checkpoints and resume

State paths are step-suffixed: `ckpt_state_step{step}.pt`. Initial state at
step 0, then 100, 500, 1000, 1500, 2000, 2500, 2929. The selected artifact is
`ckpt_best.pt`. Each state is atomic and hashed into `checkpoints.jsonl`.

Planned resume boundary: stop after the step-500 update, verify the saved
state (fingerprint, loader `(0, 4000)`, schedule step 500, token counter),
then resume from it in a second process. The resumed first update records a
`resume_trace`; the final counter must equal the plan total. This verifies
operational continuation, not bitwise GPU determinism.

## 4. Evaluation

Validation at step 0 and every 250 updates, plus the final step. Per source:
main CE and bits/char, then macro and token-weighted aggregates, train/val
gap, router entropy and expert shares. Selection is validation macro main CE
only; the test split is not read until after selection.

Bits/char uses the exact prefix-decode span:
`len(decode(ids)) - len(decode(ids[:1]))` per sequence, which is the
telescoped span of targets 1..L-1. The implementation is
`training/chars.py`; it is validated on CPU and is the default in
`evaluate`. The older proportional document-share estimate is not used for
this run.

The final test evaluation loads `ckpt_best.pt` and runs the same exact
protocol on the frozen test split. It is evaluation only, with
`torch.no_grad()`.

## 5. Budgets and stop conditions

- At most 2,929 optimizer updates (cap 3,000).
- At most 95,951,233 training token positions (the plan consumes exactly one
  pass; 95,763,828 targets).
- At most 90 minutes total GPU execution. Part 1 is capped at 30 minutes and
  part 2 at 60 minutes; each part also uses a process timeout.
- No retry after a GPU fault, HIP error, OOM, non-finite loss/gradient, or
  unresponsive GPU.
- No dense-combined fallback without separate approval.
- A single update over 120 s stops the run.
- A router mean entropy below 0.5 for 10 consecutive updates stops the run.
- No remote push, no system/ROCm/kernel/driver change, no additional data.

Expected throughput from v3.1-D is about 36.5k tokens/s, so training is about
44 minutes; validation and checkpoint hashing add roughly 8-10 minutes. The
90-minute cap leaves margin for slower allocator or loader behavior.
