# v3.1-PERF-5E BF16 consumer attribution

Status 2026-10-27. One bounded GPU execution, plus source and trace analysis on
the existing artifacts. No production change, no serialization, no backend
switch, no reset, no retry.

**Outcome: the BF16-to-FP32 consumer is excluded as an over-reader; the GEMM
epilogue remains the only candidate, and this run did not fault.**
Classification: **C, candidate operation only**, with the run itself falling
under **D** because no fault occurred to attribute.

Two independent lines of evidence disfavour the consumer:

1. The shipped template masks the elementwise tail. In this build's ROCm branch
   of `vectorized_elementwise_kernel`, the block that handles the remainder uses
   `memory::policies::unroll`, whose `load` and `store` guard every element with
   `if (thread_idx < remaining)` and use scalar loads. A masked tail reads
   exactly `remaining` elements and cannot cross the allocation end.
2. In the new run, 10,729 copies read an input whose storage ends exactly at a
   2 MiB page, and none faulted.

## 2. CPU-only evidence analysis

### 2.1 The 57 PERF-5D traces, re-inspected

- 57 cycles: 56 full training iterations (1,606 to 3,330 kernels, 453 GEMMs
  each) and 1 batch-only cycle.
- Tail pattern: 46 of 56 iterations end `aten::silu_backward` -> `aten::mm` ->
  `aten::copy_`; the remaining 10 end on elementwise ops and look cut mid
  iteration.
- In the last full trace the only kernel after the last GEMM is
  `at::native::bfloat16tofloat32_copy_kernel`, launched by `aten::copy_`, with a
  distinct correlation id from the GEMM it follows.

### 2.2 The GEMM-to-copy correlation is ordering, not identity

The traces carry kernel names and `External id` links, but no pointers and no
shapes (they were recorded with `record_shapes=False`), so PERF-5D could not show
that the copy consumed the boundary buffer. That gap is what this stage closes.

### 2.3 The boundary buffer, from the hipBLASLt log

`Cdesc=[type=R_16BF rows=682 cols=3075 ld=682]` at a 2 MiB-aligned base, extent
682 x 3075 x 2 = **4,194,300 bytes**, allocator block 4 MiB = 4,194,304, so the
tensor ends **4 bytes** before the page that begins at the block end. The layout
is column-major with `ld = 682`, i.e. the transposed `w3` backward input-gradient
output for the 3,075 routed tokens.

### 2.4 The kernel name implies a contiguous input

The observed kernel is `vectorized_elementwise_kernel<4, bfloat16tofloat32_...>`,
which PyTorch selects only when the iterator can be vectorized, i.e. the copy
input is contiguous and suitably aligned. A strided copy would take the
`elementwise_kernel` path instead.

### 2.5 Tail masking in the shipped template (decisive)

From `torch/include/ATen/native/cuda/CUDALoops.cuh`, ROCm branch:

```cpp
int remaining = N - bws * blockIdx.x;
if (remaining < bws) {          // the remainder block
  ... memory::policies::unroll<...>(data, remaining, ...);
} else {                        // full blocks
  ... memory::policies::vectorized<...>(...);
}
```

and `torch/include/ATen/native/cuda/MemoryAccess.cuh`, `unroll_base`:

```cpp
for (int i = 0; i < elems_per_thread; i++) {
  if (thread_idx < remaining) { ... loader.template load<arg_t>(...) ...; thread_idx += num_threads; }
}
```

with the same guard in `store` and a `check_inbounds(i)` guard around the
computation in `elementwise_kernel_helper`. The remainder block therefore reads
exactly `remaining` elements, one scalar each, and the vectorized path only runs
on full blocks inside `N`.

**Consequence:** a vectorized elementwise tail in this build is masked. The
4-byte boundary arithmetic alone is not evidence of an over-read, and the
"copies the GEMM output" association does not by itself explain a fault 4 bytes
past the tensor.

### 2.6 Is `record_shapes=True` sufficient?

No. Shapes identify the operand class, but not which allocation the copy read.
Pointers, storage base and storage size are needed to compare against the fault
page, so this stage added a metadata-only dispatch recorder alongside
`record_shapes=True`.

## 3. Hardened trace persistence

The rolling exporter now appends `cycles.jsonl` and flushes it at every cycle
before any other work, with the cycle number, the covered iteration, the file
path and the byte size. In this run **121 of 121 cycles** landed in
`cycles.jsonl` with iteration identifiers `0..119`, so coverage is recorded rather
than reconstructed. Trace files remain atomically published via `os.replace`, and
no synchronization or serialization was added.

**This run did not reproduce the fault.** PERF-5C and PERF-5D faulted within 26

the allocator layout, and the fault is layout-sensitive, so the absence is
plausibly caused by the instrumentation itself. It is reported as a deviation,
not as evidence that the fault is gone.

## 5. Precondition frequency (from the non-faulting run)

| measure | count |
|---|---:|
| GEMM outputs whose storage ends exactly at a 2 MiB page | 3,401 (all with 0 bytes slack) |
| of those, with a partial last dimension (`N mod 64 != 0`) | 7, all shape `(16384, 8)` |
| copies whose input storage ends exactly at a 2 MiB page | 10,729 |
| of those, copies whose tensor range reaches the page | 10,729 |
| of those, with a partial last dimension | 2,212 |
| 682-column GEMM outputs (`(256,682)`, `(16384,682)`, `(3922,682)`) | 5,861 |
| 682-column outputs that ended at a page | **0** |

Two things follow. First, copies routinely read right up to a 2 MiB page
(10,729 times) with no fault, which is what the masked tail predicts. Second, the
specific combination the fault needs, a 682-column GEMM output whose 4 MiB block
ends within the modelled 44-byte over-read of a page, **did not occur in this
run at all**. The clean outcome is explained by that absence, not by the consumer
being wrong or right.

The one thing this stage does establish negatively is that the consumer is not a
plausible over-reader: the template masks the tail, the copy input is contiguous
(hence on that path), and 10,729 page-ending copies ran without a fault.

## 7. Remaining alternative explanations

- **The GEMM epilogue itself** (store past the output end, or a Tensile over-read
  of an operand whose block ends at a page). Now the leading candidate. The
  kernel log's `RW: 0x0` suggested a read, which would favour an operand read,
  but that flag reading is not authoritative.
- **Another kernel reading the reused block** later, once the 4 MiB block is
  handed out again by the caching allocator; the block boundary, not the original
  tensor, is what the fault page pins.
- **A different dispatch on the faulting iteration** that this non-faulting run
  never issued.
- Instrumentation-induced avoidance is itself a live explanation for the missing
  fault, so no conclusion about the mechanism can rest on this run alone.

## 8. Proposed bounded PERF-5F discriminator (not executed)

Four arms, one bounded GPU execution each, fresh processes, the same reproducer
and geometry, no serialization:

1. **Reference reproduction** with the 5D rolling profiler only (no
   `record_shapes`, no dispatch mode), which has faulted in two of two previous
   stages. This re-establishes the fault under minimal instrumentation.
2. **Storage padding**: keep the computation identical but pad the 682 x 3075
   output's block so the tensor end is at least 64 KiB away from any page.
   *Changes allocator placement*; a clean result tests the boundary condition,
   not the kernel, and must never be read as proof of the faulty kernel.
3. **Standalone cast on the boundary-sensitive shape**: allocate a 682 x 3075
   bf16 buffer whose block ends 4 bytes after the tensor, fill it, then run only
   `aten::copy_` to fp32. *Changes tensor lifetime and the surrounding op
   sequence*; it isolates the consumer. The masked-tail source predicts this is
   clean, so a clean result is expected and confirms the exclusion, while a fault
   would contradict the source reading.
4. **GEMM without the cast**, if a numerically and operationally meaningful form
   exists: keep the `w3` backward GEMM and consume its output with an operation
   that does not cast (for example accumulate in bf16). *Changes kernel
   selection and possibly the numerical result*, so it is an ablation, not a
   control.

Order: 1, then 3 (cheap, decisive for the consumer), then 2, then 4 only if the
first three leave the GEMM as the sole candidate. Abort on any second unexpected
fault or any reset. The same containment as PERF-5C/5D applies: idle gate,
`ulimit -c 0`, 120 s timeout, fresh process, kernel-log capture, no retry.
