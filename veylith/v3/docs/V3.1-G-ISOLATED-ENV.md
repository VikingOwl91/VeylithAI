# v3.1-G isolated ROCm training environment

Status 2026-10-27. Planning and read-only investigation; implemented by
v3.1-H in `veylith/v3/env/`. v3.1-G itself installed nothing and ran no GPU
workload. The implementation note below describes the final flow.

Implementation note: v3.1-H uses `veylith/v3/env/pyproject.toml` plus
`uv.lock` as the source of truth, exports `requirements.lock` for review, and
installs with `uv sync --frozen` against the explicit PyTorch source. The
`requirements.in` sketch below is superseded by that flow. See
`veylith/v3/env/README.md`.

## Answer

The simplest reliable way to decouple training from Arch Linux's system Python
and PyTorch packages is a managed CPython 3.14.8 virtual environment with
`include-system-site-packages = false`, a hash-locked
`torch==2.14.1+rocm7.2` cp314 wheel, and a launcher that sanitizes the Python
and ROCm environment variables.

That setup removes Arch's Python packages from the training stack. It does not
make Arch Linux a ROCm-supported operating system, and it does not isolate the
kernel, amdgpu/KFD, firmware, glibc, libstdc++ or libgcc. A digest-pinned
container is the fallback when stronger user-space isolation is required. A
source build is not justified.

The known bf16 sparse-MoE fault is a separate blocker. The isolated environment
does not fix it. The training path remains Dense-Combined until a newer
PyTorch/ROCm combination is separately proven.

`librocsolver`, `librocsparse`, `librocfft`, `librocrand` and related libraries
from `/opt/rocm/lib`. Its RUNPATH includes `/opt/rocm/lib`. The owning Arch
packages include `hip-runtime-amd 7.2.4-1.1`, `rocblas 7.2.4-3`,
`hipblaslt 7.2.4-1` and `miopen-hip 7.2.4-1`.

The host libraries that remain relevant are glibc 2.44, gcc-libs 16.2.1
(libstdc++ and libgcc), zstd 1.5.7, xz 5.8.4, linux-zen 7.2.11 and
linux-firmware-amdgpu 20260916. `/dev/kfd` is `crw-rw-rw-`, `/dev/dri/renderD128`
is `crw-rw-rw-`, and the user is in the `render` and `video` groups.

A venv with `include-system-site-packages = false` would not isolate ROCm while
it still used the system torch, because the system extension resolves ROCm from
`/opt/rocm/lib`. The isolation in the recommended candidate comes from the
wheel's bundled ROCm user-space and its `$ORIGIN` RPATH, not from `venv` alone.

## 2. Isolation boundaries

Fully isolated with candidate A, the managed venv plus bundled wheel:

- Python interpreter and standard library, provided by a uv-managed CPython,
  not `/usr/bin/python3.14`.
- Python packages, in the venv only, with no system or user site.
- PyTorch wheel and its compiled extensions.
- ROCm user-space libraries bundled in the wheel: HIP, rocBLAS, hipBLASLt,
  MIOpen, RCCL, rocSOLVER, rocSPARSE, rocFFT, rocRAND, rocPRIM and the gfx1201
  Tensile kernels.
- Dynamic linker resolution for torch and ROCm, via the wheel's
  `RPATH=$ORIGIN`, provided no `LD_LIBRARY_PATH` override is present.
- Python and ROCm environment variables, through the launcher.

Host-dependent and not isolated by A:

- Linux kernel, amdgpu/KFD, firmware, `/dev/kfd`, `/dev/dri` and user groups.
- glibc, libstdc++, libgcc, libzstd and liblzma. The testB inventory shows
  libc, libstdc++, libgcc, libzstd and liblzma from `/usr/lib`, while ROCm
  libraries resolve from the venv.
- The `uv` binary used for installation, unless a pinned standalone `uv` is
  kept.
- Filesystem, local data root and checkpoint directory.

Distribution-dependent:

- Container B isolates more user-space, including glibc and libstdc++, but
  still shares the host kernel, amdgpu/KFD, firmware and device nodes.
- Source build C can pin source and compiler versions, but it still links to
  host ROCm and host C/C++ libraries unless fully bundled.
- Official ROCm support is distribution-dependent. ROCm 7.2.1 lists the RX
  9070 XT (gfx1201) but only for Ubuntu 24.04.4, Ubuntu 22.04.5, RHEL 10.1 and
  RHEL 9.7. Arch Linux is not on the supported list.

## 4. PyTorch and ROCm compatibility

The latest stable PyTorch is 2.14.1, released 2026-09-30. There is no stable
2.15.0 or 2.16.0 release as of 2026-10-27. The 2.15 and 2.16 builds in the
nightly index are development builds and are not a reproducible long-term
base.

The primary wheel is:

- URL: `https://download.pytorch.org/whl/rocm7.2/torch/`
- file: `torch-2.14.1+rocm7.2-cp314-cp314-manylinux_2_28_x86_64.whl`
- sha256: `e378baf90ba06c988e234449787a6fd9dac60dcd869eef35cfcc9546cd3f1f14`
- size: 6,224,879,579 bytes
- index last modified: 2026-09-30

The local testB venv is the strongest compatibility evidence. It used
`uv` with `include-system-site-packages = false`, no user site, and exactly
this wheel. It reported `torch 2.14.1+rocm7.2`, HIP 7.2.53211, gfx1201,
finite bf16 matmul, finite bf16 forward and backward, correct fp32 gradients
and a successful sync. It loaded 33 ROCm/HIP/AMD libraries from the venv and
0 from system `/opt/rocm`. Its `libtorch_hip.so` has `RPATH=$ORIGIN`; host
libc, libstdc++, libgcc, libzstd and liblzma remain.

The `rocm7.14` wheel is not as clean for isolation. TestA, testC and testD
loaded one system library from `/opt/rocm/lib/libhsa-amd-aqlprofile64.so` and
the smoke script printed a warning. The `rocm7.2` wheel loaded none. The
`rocm7.14` builds are useful for a later sparse re-verification, not for the
primary isolated training environment.

Nightly evidence, for context only:

| build | local result | sparse 8E/top-2 | notes |
|---|---|---|---|
| 2.14.1+rocm7.2 | smoke pass, 0 system ROCm libs | known fault | primary stable, use dense-combined |
| 2.14.1+rocm7.14 | smoke pass, 1 system ROCm lib | known fault | not cleaner for isolation |
| 2.15.0.dev20261005+rocm7.14 | smoke pass | passes the reproducer | nightly, not stable |
| 2.16.0.dev20261006+rocm7.14 | smoke pass | passes 8E/top-2, 16E/top-4 faults | nightly, no general fix |

Do not treat the 8E/top-2 reproducer passing as proof of general sparse
stability. The v2 investigation left the exact kernel and fix attribution
unresolved, and a 16-expert/top-4 case still faulted on a newer nightly.

Official AMD support statements:

- ROCm 7.2.1 system requirements list the RX 9070 XT as RDNA4, gfx1201, but
  the supported operating systems for that class are Ubuntu 24.04.4,
  Ubuntu 22.04.5, RHEL 10.1 and RHEL 9.7. Arch is not listed.
- ROCm 10.1.0 compatibility matrix lists gfx1201, Ubuntu 26.04.1, 24.04.5 and
  22.04.5, RHEL 10.2 and 9.8, and PyTorch 2.14.0, 2.13.0 and 2.12.0 with
  Python 3.14, 3.13, 3.12, 3.11 and 3.10.

The primary A stack is therefore an official PyTorch wheel on an officially
supported GPU, running on an unofficial Arch host. That distinction must stay
in the training manifest and the risk register.

## 5. Dependency locking and reproducibility

Primary A uses a managed CPython 3.14.8, a requirements input, a hash-locked
requirements file and a launcher.

Exact package set for the lock, matching the locally validated testB venv plus
the application dependencies:

```
torch==2.14.1+rocm7.2
triton-rocm==3.8.0
filelock==3.32.3
fsspec==2026.7.0
jinja2==3.1.6
markupsafe==3.0.3
mpmath==1.3.0
networkx==3.6.1
setuptools==78.1.0
sympy==1.14.0
typing-extensions==4.16.0
numpy==2.5.4
sentencepiece==0.2.2
pytest==9.1.1
```

The lock must include hashes and both index URLs. The torch wheel hash is the
one recorded above. Keep a local copy of the 6.22 GB wheel in a cache outside
Git, for example `~/veylith-wheel-cache/`, and verify its
sha256 before installation. The lockfile itself is small and can be committed
under `veylith/v3/env/` in the authorized migration.

Environment fingerprint fields:

- Python: version, executable, `prefix`, `base_prefix`,
  `site.ENABLE_USER_SITE`, full `sys.path`, and the uv-managed build path.
- uv: exact version, for example `0.13.5`.
- Packages: exact `uv pip freeze` output, lockfile sha256, and
  `uv pip check` result.
- Torch: `torch.__version__`, `torch.version.hip`, `torch.version.cuda`,
  `torch.__file__`, `torch.__config__.show()` sha256, and the wheel URL and
  sha256.
- Native libraries: `ldd` and `readelf -d` of `libtorch_hip.so`; RPATH; count
  of ROCm libraries from `/opt/rocm` (must be 0); allowlisted host libc,
  libstdc++, libgcc, libzstd and liblzma paths and versions.
- Host: `uname -r`, system `/opt/rocm/.info/version`, `pacman -Q` for glibc,
  gcc-libs, zstd, xz, linux-zen and linux-firmware-amdgpu, and the
  `/dev/kfd` and `/dev/dri` permissions.
- Training manifest: add the fingerprint sha256, lockfile sha256, torch/HIP
  versions, `sys.prefix` and `site.ENABLE_USER_SITE` to `run_info.json` and to
  the checkpoint `versions()` record. Do not rely on the current
  `versions()` fields alone; they omit HIP, ROCm library provenance and the
  lockfile.

Drift detection before training:

- Run `uv pip sync --require-hashes` and `uv pip check`; a mismatch is a hard
  stop.
- Compare the current fingerprint with the accepted baseline. Package,
  torch, HIP, user-site and unexpected `/opt/rocm` library drift is a hard
  stop. Kernel, firmware or allowlisted host-library drift is recorded and
  requires a re-smoke before a GPU run.
- Run the check for every training process, including dataloader workers and
  subprocesses. A parent-only check is not enough.
- The launcher must unset `PYTHONPATH`, `PYTHONHOME`, `ROCM_PATH`, `HIP_PATH`
  and `LD_LIBRARY_PATH`, and set `PYTHONNOUSERSITE=1`.
- The smoke script's current `PASS` is not an isolation gate. It treats
  system ROCm library leakage as a warning. The migration gate must fail on
  any unexpected `/opt/rocm` library, including profiling libraries.

## 6. Migration plan

Keep `~/veylith-v31-gpu-env`, `~/veylith-v3-env`, all checkpoints and all logs
untouched. Do not alter system Python or pacman packages. Create the new
environment only in a later authorized phase, for example at
`~/veylith-v31-isolated`.

Exact installation commands for that later phase, not to be executed now:

```bash
# Managed Python, independent of Arch's /usr/bin/python3.14
uv python install 3.14.8
uv venv --managed-python --python 3.14.8 ~/veylith-v31-isolated

# requirements.in contains the pinned package set from section 5
uv pip compile ~/veylith-v31-isolated/requirements.in \
  --python ~/veylith-v31-isolated/bin/python \
  --index-url https://pypi.org/simple \
  --extra-index-url https://download.pytorch.org/whl/rocm7.2 \
  --generate-hashes --emit-index-url \
  -o ~/veylith-v31-isolated/requirements.lock

uv pip sync ~/veylith-v31-isolated/requirements.lock \
  --python ~/veylith-v31-isolated/bin/python \
  --require-hashes
uv pip check --python ~/veylith-v31-isolated/bin/python
```

If the managed 3.14.8 build is unavailable, the already-installed uv-managed
CPython 3.12.12 plus the cp312 wheel is the fallback. It matches the CPU test
environment, which already passes the v3 suite, but it needs its own GPU smoke.
Do not mix cp312 and cp314 wheels in one environment.

The launcher, not a bare `source`, should sanitize the environment:

```bash
env -u PYTHONPATH -u PYTHONHOME -u ROCM_PATH -u HIP_PATH -u LD_LIBRARY_PATH \
  PYTHONNOUSERSITE=1 \
  ~/veylith-v31-isolated/bin/python "$@"
```

The existing data root remains
`~/veylith-v3-data/multi-100m-20261026`. New runs write to a
new run directory. No dataset or architecture change is part of the migration.

Validation ladder, in order:

1. Python and package import checks: `sys.prefix` is the new venv,
   `sys.base_prefix` is the managed Python, `site.ENABLE_USER_SITE` is false,
   `sys.path` has no `~/.local` or `/usr/lib/python3.14/site-packages`, torch
   and NumPy import, `torch.from_numpy` works, and `uv pip check` is clean.
2. Fingerprint verification: lockfile hashes, torch wheel hash, no unexpected
   `/opt/rocm` libraries in `ldd` or `/proc/self/maps`, and the host fields
   recorded.
3. CPU-only model and dependency tests: the v3 test suite with
   `HIP_VISIBLE_DEVICES=""` and `CUDA_VISIBLE_DEVICES=""`; the v3.1-A
   architecture and training tests; checkpoint load tests.
4. Minimal HIP/BF16/SDPA GPU smoke, separate authorization: gfx1201, finite
   bf16 matmul and backward, SDPA causal and sliding-window masks, sync,
   VRAM, and the same library-provenance check. The testB smoke did not cover
   SDPA, and it had no NumPy.
5. Sparse-MoE reproducer, separate authorization: only meaningful for a
   newer-torch experimental environment. On 2.14.1 it is expected to
   reproduce the known fault. It is not a gate for the Dense-Combined path.
6. Bounded real-data training stability, separate authorization: Dense-
   Combined, a fixed update and time cap, validation and checkpoint/resume
   checks. The v3.1-F decision and `V3.1-FULL-RUN-PLAN.md` define the shape.

GPU stages 4 to 6 require separate explicit authorization. No GPU run was
performed in this phase.

## 7. Fallback container commands

Use only if A is rejected or if stronger user-space isolation is required.
The official image changes torch and ROCm axes, so it must pass the same
ladder independently. Pin the image digest, not the tag.

```bash
podman pull docker.io/rocm/pytorch@sha256:099f59a3bee9c436f5cc57db6bc6076fdeda579c57e9e22ae40f856d5905b3e4

podman run --rm -it \
  --device=/dev/kfd --device=/dev/dri/renderD128 \
  --group-add keep-groups \
  --security-opt seccomp=unconfined \
  --ipc=host --shm-size=16g \
  --userns=keep-id \
  -v ~/veylith-v3-data/multi-100m-20261026:/data:ro \
  -v ~/veylith-v31-runs:/runs:rw \
  -v ~/git/AI-Research-v2dev:/workspace:ro \
  -w /workspace \
  docker.io/rocm/pytorch@sha256:099f59a3bee9c436f5cc57db6bc6076fdeda579c57e9e22ae40f856d5905b3e4 \
  python -c "import torch; print(torch.__version__, torch.version.hip)"
```

The digest above is `rocm10.1.0_ubuntu24.04_py3.12_pytorch_release_2.14.0`
(`latest`, 2026-10-05, 11.7 GB compressed). The Python 3.14 variant is
`rocm10.1.0_ubuntu26.04_py3.14_pytorch_release_2.14.0` with digest
`sha256:68295d40dcdcb53d9b50828f30017faad8cf5ad9a8c7923c5a815b414b45e3e6`.
For Docker instead of Podman, replace `--group-add keep-groups` with
`--group-add render --group-add video`.

Do not mount `/opt/rocm`, system Python, credentials or the host's package
directories into the container. Mount data read-only and outputs separately.
Record `podman image inspect --format '{{.Digest}}'` in the run manifest. If a
custom image is used to preserve `torch 2.14.1+rocm7.2`, build it from a pinned
ROCm base plus the hash-locked wheel, and treat the image build as a separate
authorized migration step.

## 8. Decision

**Primary:** candidate A, a managed CPython 3.14.8 venv with
`include-system-site-packages = false`, the hash-locked
`torch 2.14.1+rocm7.2` cp314 wheel, NumPy, SentencePiece and pytest, a
sanitizing launcher, and a fingerprint/drift gate. This is the smallest change
that removes Arch Python and PyTorch packages from the training stack while
preserving the current RDNA4/gfx1201 behavior.

**Fallback:** candidate B, a digest-pinned ROCm PyTorch container. It isolates
more user-space but changes torch and ROCm versions, is much larger, and still
shares the Arch kernel, amdgpu/KFD and firmware. It is not a turnkey official
Arch solution.

**Not recommended:** candidate C, a local PyTorch source build. The official
wheel already provides gfx1201 kernels, and the build and maintenance cost is
not justified.

If official end-to-end ROCm support is a hard requirement, neither A nor B
suffices on this Arch host. The supported path is a supported Ubuntu or RHEL
host, or a VM with GPU passthrough, with the ROCm support matrix matching the
kernel and driver. That is a larger infrastructure decision, not a Python
environment change.

Residual risks and open evidence:

- Arch Linux is not in the ROCm 7.2.1 supported OS list. The local testB smoke
  is experimental evidence, not an official support statement.
- The managed Python 3.14.8 plus the wheel plus NumPy and SentencePiece has
  not been installed and smoke-tested together. testB used system Python and
  had no NumPy.
- SDPA in the pip-wheel environment has not been verified. The v3.1-C smoke
  used the system torch.
- The 6.22 GB wheel's installed size is not measured. The venv will be much
  larger than the current 13 MB environment.
- The container's ROCm 10.1.0 on the Arch 7.2.11 kernel and firmware is
  unverified. Its PyTorch is 2.14.0, not 2.14.1.
- The sparse bf16 fault remains. Isolation does not repair it. Use
  Dense-Combined until a newer stable PyTorch/ROCm combination is proven on
  the target workload.
- Host glibc, libstdc++, kernel, firmware and KFD can change under
  `pacman -Syu`. The fingerprint can detect drift; it cannot prevent it or
  reproduce the old host.
