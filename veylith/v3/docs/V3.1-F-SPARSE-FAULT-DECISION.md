# v3.1-F sparse-MoE fault decision

Status 2026-10-27. CPU-only static review and existing-evidence audit. No GPU
execution, no training, no system or checkpoint changes.

## Answer

The v3 sparse-MoE implementation is not the root cause. The v3.1-E fault is
the same known PyTorch/ROCm bf16 sparse-MoE backward kernel problem that the
v2 investigation already isolated on torch 2.14.1. The v3.1-E error message
and the 2 MiB-aligned fault address match that signature.

Do not spend a source-level fix on the sparse implementation. The justified
next action is a separately authorized **Dense-Combined** training experiment.
A stable PyTorch >= 2.15 upgrade is the only real fix candidate, but it is a
system/tooling change and not a general fix: a 16-expert/top-4 configuration
still faulted on 2.16.0.dev20261006.

## 1. Most plausible fault location and evidence

Location: the bf16 backward path of the variable-size sparse-MoE dispatch,
inside PyTorch/ROCm kernels. The v3 Python code is mathematically correct and
its indices are in bounds; the write is inside a kernel called by the sparse
path.

Verified evidence:

- The v3.1-E fault is
  `Memory access fault by GPU node-1 ... Page not present or supervisor
  privilege` at `0x7fb466000000`, exit 134. The address is 2 MiB aligned.
- The v2 root-cause document records the same signature across ~12 faults,
  always a 2 MiB-aligned segment boundary, and maps it to an OOB write past
  the last allocation in a mapped segment:
  `veylith/debug/root-cause.md`, observations 10-12.
- The v2 deterministic reproducer faults on torch 2.14.1, forward-only is
  clean, fp32 is clean across five seeds, dense-combined is clean, and CPU is
  clean. The current v3 environment is torch 2.14.1 / HIP 7.2.53211, the
  affected line.
- The v2 version matrix shows torch 2.15.0.dev20261005+ passes the tested
  8-expert/top-2 reproducer, but a 16-expert/top-4 configuration still faults
  on 2.16.0.dev20261006. This is a configuration-dependent behavior change,
  not a general fix. See `veylith/debug/README.md` and
  `veylith/debug/version-comparison.md`.
- The v3.1-E run has no NaN/Inf, no OOM, no GPU reset, no router collapse and
  no update over 120 s. A numerical or application failure is not supported
  by the evidence.

The last durable record is step 60 (1,962,240 tokens). The next 10-step log
would have been step 70, so the fault occurred during one of updates 61 to 69.
The exact kernel is not identifiable from the v3 log: the v3 stderr has the
runtime fault only, with no stack trace or kernel name. The v2 op-level traces
show the forward completing and the fault surfacing at the next sync or H2D
copy, which is why "last completed Python operation" is not the faulting op.

## 2. Does the issue appear in code shared between v2 and v3?

Yes, as an equivalent dispatch and backward pattern, not as identical source.

| | v2 failing sparse code | v3 sparse code |
|---|---|---|
| routing | `topk` on fp32 router logits | `topk` on fp32 router logits |
| token selection | `sel = (w_e > 0).nonzero(...)` int64 | `mask = (top_idx == e).any(-1)` bool |
| expert input | `x_flat.index_select(0, sel)` | `flat[mask]` boolean gather |
| accumulation | out-of-place `out.index_add(0, sel, delta)` | out-of-place `out.index_add(0, mask.nonzero(...), ...)` |
| dtype path | bf16 autocast, fp32 router | bf16 autocast, fp32 router |
| backward | `index_select`/`index_add` backward | boolean-gather/`index_add` backward |

The v2 recovered code is `veylith/debug/sparse_moe_v2_train.py`, lines 267-286.
The v3 code is `veylith/v3/architecture/model.py`, lines 133-160. The earlier
v2 bool-mask variant (`sparse_moe_v2_train_boolmask.py`) also faulted, so
switching v3 to int64 `index_select` is not a fix; that is the v2 code that
faulted. Both variants are in the affected class.

The application-level checks are green:

- The existing `test_attention_and_moe_paths_match_in_forward_and_gradients`
  compares sparse and dense output and gradients in fp32.
- `test_moe_bf16_paths_are_finite_on_cpu` covers bf16 sparse and dense.
- A new `test_sparse_dense_moe_parity_with_empty_experts` covers fp32 and
  bf16, forces experts 2 and 3 to be empty, and checks sparse/dense output
  and gradient parity plus the router gradient. It passes.

These tests cannot reproduce a GPU kernel bug. They establish that the v3
indices, shapes, dtype casts and autograd graph are correct.

## 3. Is a small, justified source-level correction available?

No correction to the sparse implementation is justified by the evidence.

- The indices are in bounds: `nonzero` on a boolean mask is unique and sorted,
  `top_idx` is in `[0, E)`, and the `index_add` base is `(N, C)`.
- The dtype boundary is already correct: the contribution is cast to
  `out.dtype` before `index_add`, and the bf16 regression test passes.
- The in-place/aliasing path is already avoided: `index_add` is out of place,
  so the autograd graph reaches the experts.
- Switching to int64 `index_select`/`index_add` would reproduce the v2 code
  that faulted. Switching to bool-mask `index_put` is worse; the earlier v2
  variant faulted too.
- Running the sparse path in fp32 is a precision workaround, not a code fix.
  The v2 evidence says fp32 is clean, but it changes the training path and
  cost, has not been measured at the v3.1-A scale, and a mixed bf16/fp32 MoE
  boundary is not proven to avoid the kernel path entirely.

A **guard** is a reasonable safety measure, but it is not a fix: refuse bf16
sparse training on the known-affected torch 2.14.x line unless an explicit
override is set. That would prevent another accidental 60-update run. It is
not required for the immediate decision, and it does not make sparse safe.
If the user wants that guard, it should be a separate, reviewed change.

## 4. Can the existing implementation be isolated in one short GPU experiment?

Not usefully. The v2 reproducer already isolates the failure deterministically
on this stack, and the v3.1-E run is a real-configuration confirmation. A
short sparse A/B run would only reconfirm the known fault and risk another GPU
fault; it would not tell us whether the v3 Python code is correct, because the
v2 audit and the CPU parity tests already do.

If a GPU experiment is authorized, its highest-value form is not another
sparse isolation. It is a bounded **Dense-Combined** training run at the v3.1-A
configuration to measure step time, VRAM, loss and router behavior. A sparse
versus dense microbenchmark could be added later, but it is not needed to
choose the workaround.

## 5. Is Dense-Combined a reasonable temporary training workaround?

Yes.

- It is already implemented as `moe_impl="dense"` and is the v2 production
  path on this stack.
- It uses no variable-size `nonzero`/`index_select`/`index_add`; all experts
  run on every token and are combined with dense routing weights.
- It is mathematically equivalent up to reduction order. The v2 Phase C
  comparison found sparse and dense equidistant from an fp64 reference
  (relative ~1e-6, fp32 reduction noise).
- It fits 16 GB. The v3 analytical estimate for Architecture A, MB8, seq 512,
  activation checkpointing, is 4.26 GB total including state, 1.9 GB reserve
  and 12 % margin. The sparse estimate is 4.05 GB.
- It costs compute. The v3 estimate is 5.81e16 FLOPs for the 95.95M-token
  pass versus 2.25e16 sparse, about 2.6x. A full pass may exceed a 90-minute
  budget; a bounded run is the right first experiment.
- The v2 benchmark on a smaller model and newer torch measured dense at
  140.6 ms/step versus sparse at 124.1 ms/step, with dense using 8.02 GB
  versus 4.70 GB. Expect a larger gap at the v3 scale, but still within the
  card for MB8.

Dense-Combined is a workaround, not a fix. It does not prove sparse safe, and
it does not close the upstream PyTorch/ROCm issue.

## 6. Proposed next action

Run a separately authorized **Dense-Combined** bounded training experiment,
not another sparse run.

Suggested configuration:

- Architecture A, `--moe dense`, SDPA, bf16 autocast with fp32 masters.
- Same verified corpus, tokenizer and seed 0; MB8 x accumulation 8; seq 512.
- AdamW, clipping 1.0, LR 3e-4, warmup 3 % of the chosen horizon, cosine to
  10 %, aux 0.01.
- 500 optimizer updates, 16,352,000 token positions (or a 30-minute GPU cap,
  whichever is reached first). Checkpoint at 50, 100, 250 and 500; validate
  at 0, 100, 250 and 500. No test split until selection.
- Stop immediately on a GPU fault or reset, HIP error, OOM, non-finite loss
  or gradient, persistent router collapse, an update over 120 s, or the time
  or token cap. No automatic retry and no automatic switch back to sparse.
- Success criteria: 500 updates without a fault, decreasing main CE, healthy
  router, checkpoints that load, and a deterministic resume check. If that
  passes, decide between a longer dense run and a stable PyTorch >= 2.15
  environment for sparse re-verification.

The alternative, upgrading PyTorch to a stable >= 2.15 release, is the only
real sparse fix candidate. It is a system/tooling change, requires
re-verification on the v3 target configuration, and is not authorized in this
phase. The 16-expert/top-4 failure on a newer nightly means the upgrade alone
is not a blanket guarantee.

Do not run another sparse experiment on torch 2.14.1 without a new decision.
