# v3.1-A memory and compute budgets (analytical)

Status 2026-10-26. Analytical estimates only. No GPU profiling, no training.
The numbers are upper bounds with explicit assumptions; measured values will
differ.

## 1. Assumptions

| item | assumption |
|---|---|
| precision | bf16 weights/grads, fp32 master weights and Adam moments |
| optimizer state | 16 bytes per parameter (2 + 2 + 4 + 4 + 4) |
| activation checkpointing | layer inputs stored, the rest recomputed (about 30 % extra step time) |
| attention | flash/SDPA, so no T x T matrix is materialized; a manual-attention number is listed separately |
| sequence | 512 tokens |
| reserved VRAM | 1.9 GB for the desktop/ROCm context (rocm-smi showed 1.89 GB in use) |
| safety margin | 12 % for fragmentation/allocator headroom |
| batch | microbatch 1/2/4/8, gradient accumulation to effective 64 |
| GPU | 16 GB RX 9070 XT, bf16 |

The model-state term is about 1.53-1.64 GB for the four candidates. With the
reserved memory and margin, every candidate fits a 16 GB card at microbatch
8 with substantial headroom. This is the analytical budget; the training
implementation must still measure the real allocator peak.

## 3. Activation memory (seq 512, checkpointing on)

Total GB including state, data, 1.9 GB reserved and 12 % margin:

| candidate | MB 1 | MB 2 | MB 4 | MB 8 | MB 8, no ckpt | MB 8, dense-combined | MB 8, no flash |
|---|---:|---:|---:|---:|---:|---:|---:|
| A | 3.91 | 3.93 | 3.97 | 4.04 | 4.37 | 4.26 | 4.23 |
| B | 3.90 | 3.92 | 3.96 | 4.03 | 4.46 | 4.21 | 4.26 |
| C | 3.87 | 3.89 | 3.92 | 4.00 | 4.39 | 4.17 | 4.29 |
| D | 3.98 | 4.00 | 4.04 | 4.12 | 4.44 | 4.34 | 4.30 |

All are well under 16 GB. The activation term is small at this model size;
the state and the reserved context dominate. Microbatch 8 with 8 gradient
accumulation steps gives the effective batch 64. If the future GPU
implementation sees a higher peak (for example because it keeps a full
attention matrix, does not checkpoint, or uses a different optimizer state
layout), the fallback is microbatch 4 or 2 with more accumulation; the table
shows the sensitivity.

Dense-combined mode uses E/k times the expert activations but remains far
below 16 GB at these sizes. It is a compute fallback, not a memory problem.

The wall-clock column extrapolates the P1-1 profile (162 ms/step at batch
64 x 256, 25.6M dense-combined, 101k tokens/s) by the active-parameter ratio
and a 1.3 block-size factor. It is **not** a reliable prediction: the GPU
kernel, attention path, optimizer and allocator will decide the real step
time. The first GPU run must measure it.

## 5. Compute budget at the data limits

- 95.95M tokens: A about 0.5 h by the anchor; a single 0.1B run is cheap on
  this GPU. The bottleneck is data, not compute.
- 500M tokens: about 2.5 h by the anchor; needs about 5x the current corpus.
- 1B tokens: about 5 h by the anchor; needs about 10x the current corpus.

These estimates assume sparse expert execution. If the ROCm sparse path
faults and dense-combined is used, multiply the expert part by E/k; the
dense-combined total at 95.95M is about 5.8e16 FLOPs (roughly 1.3 h by the
same anchor).

## 6. Known gaps

- No measured allocator peak; the 12 % margin and 1.9 GB reserve are
  assumptions.
- Activation checkpointing recompute time is not modelled in the FLOPs
  (about 30 % extra step time is expected).
- The anchor was measured at block 256; block 512 attention changes the
  ratio. The 1.3 factor is a placeholder, not a measurement.
- The 8192-vocabulary head (4.19M parameters, 512 x 8192) is included in the
  state and compute; its logits tensor at batch 8 x 512 x 8192 is about
  67 MB in bf16 and is not separately itemized in the activation term.
