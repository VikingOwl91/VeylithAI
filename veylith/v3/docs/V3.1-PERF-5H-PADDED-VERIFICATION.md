# v3.1-PERF-5H corrected padded arm

Status 2026-10-27. One GPU execution, used. No production change, no checkpoint
change, no package change, no reset, no retry, no serialization, no push.

**Outcome: classification 3, invalid comparison due to numerical differences.**

The execution itself succeeded: the padded arm ran all 100 iterations to
`COMPLETED`, every one of its 4,400 padded allocations had the intended geometry,
and the `w3` input-gradient GEMM dispatched with the same descriptors as the
reference. It also produced no fault. But the harness changed the **model state
at initialization**, so the run is not a comparison to the reference and is not
admissible as boundary evidence.

The cause is proven on CPU, not inferred from the loss: the PERF-5G wrapper
replaced each `SwiGLU.w3` (`nn.Linear`) with a plain `nn.Module`, and
`GPT._init_weights` only initializes `nn.Linear` and `nn.Embedding`. The `w3`
weights therefore kept PyTorch's default uniform initialization instead of
`N(0, 0.02)`, and the RNG stream shifted for every parameter initialized after
them. The mechanism is corrected and CPU-gated in this commit; it is not
GPU-verified, and the one-execution budget is spent.

3-D `grad_output`. ATen's linear backward flattens leading dimensions first. This
arm never reached that path, because `--grad_filter experts` leaves the dense
block without any gradient, so its `w3` backward is not built. It would fire in
any arm where the dense block trains. Fixed and gated here.

## 4. Gate A, GEMM descriptors

The `w3` input-gradient GEMM is the `(682, 256, 682)` `OP_N` operand variant: the
weight is `(256, 682)`, so hipBLASLt sees those bytes as a 682 x 256
column-major operand. The second producer of a `(3075, 682)` output is `w1`'s
forward, the `(256, 682, 256)` `OP_T` variant.

| field | reference | padded |
|---|---|---|
| `Adesc` | `R_16BF 682 256 682` | identical |
| `Bdesc` | `R_16BF 256 3075 256` | identical |
| `Cdesc` | `R_16BF 682 3075 682` | identical |
| `transA` / `transB` | `OP_N` / `OP_N` | identical |
| compute type | `COMPUTE_32F` | identical |
| scale type | `R_32F` | identical |
| epilogue | `EPILOGUE_DEFAULT`, alpha 1, beta 0 | identical |
| workspace | 79,691,776 bytes | identical |
| `w1` forward signature | `R_16BF 256 682 256`, `OP_T` | identical |

Both signatures of the `(682, 3075, 682)` output group match field for field.
The reference's wider signature set differs only in the expert token counts that
appeared (`M` values) and in run length, since the reference faulted after
iteration 25. Matching descriptors do not prove identical kernel selection, and
this hipBLASLt build logs no solution id.

That one target allocation: `data_ptr 0x7f0c52f80600`, storage 4,259,836 bytes,
tensor 4,194,300 bytes, offset 0, stride `(682, 1)`, 65,536 bytes of slack,
68,100 bytes to the page-rounded storage end. Its GEMM dispatched with
`C=0x7f0c52f80600` and the reference `Cdesc`, so the padded buffer is the real
C of the target GEMM, not a bystander.

Allocated storage is not the same as confirmed mapping accessibility. The
page-rounded end is inferred from the storage allocation; the GPU mapping itself
was not observed. The useful part is that the padded tensor end sits 68,100 bytes
inside its own storage, so an over-read of up to that much lands in the same
allocation instead of past it.

Note the alignment: the padded buffer's tensor end is 522,756 bytes before the
next 2 MiB boundary, not 4. The protection comes from the slack, not from
reproducing the 4-byte alignment.

## 6. Gate C, numerical correctness: failed

| iteration | reference | padded |
|---|---|---|
| 0 | 10.4816 | **10.4890** |
| 25 | 10.4898 | **10.4931** |
| eval after 25 | 10.4923 | **10.4872** |
| eval after 99 | not reached | 10.4892 |

No tolerance is applied; these are the recorded strings and they differ. The
divergence is present at iteration 0, which is a pure forward quantity computed
before any backward, so it cannot be produced by the padded backward at all. It
is produced by the initialization defect in section 2.

Residual limitation, stated rather than worked around: the reference arms
recorded only 4-decimal losses, and no arm has ever recorded gradient norms, so
device-level bitwise gradient comparison against a reference does not exist.
Gate C could only be applied at the recorded precision. That is why the
full-model CPU gate now exists: it compares the whole state and every gradient
bitwise, and it is the gate that caught this.

The clean result carries no weight for boundary dependence: the model state
differed at initialization, so the run is a different model, not the same model
with a different output buffer.

**A stock buffer of the same size did sit at the fault geometry.** In this run,
one `w1` forward output of `(3075, 682)` had its end 4 bytes before a 2 MiB
boundary, the geometry of every prior fault, and the run still completed 100
iterations clean. With a correct model state that observation would matter. Here
it is confounded by the different weights, and it is recorded as an observation,
not as evidence.

## 9. Confounders

1. Model state differed at initialization (section 2). This is what invalidates
   the arm.
2. Two different GEMMs produce a 4,194,300-byte `(3075, 682)` bf16 output in this
   model, `w1`'s forward and `w3`'s input gradient. Only the second is padded
   here. A clean padded run could therefore never separate "the `w3` buffer's
   boundary matters" from "the fault needs a different producer".
3. The custom `Function` replaces an ATen backward node even when every gradient
   is bitwise identical, so the autograd graph and the allocation order of the
   whole backward differ.
4. Addresses are reused by the caching allocator, so pointer matching between a
   log line and an allocation record is only reliable when the recorded shape
   also matches the descriptor. Bare pointer matches produced two false
   positives in this log.

## 10. What changed in the harness

- `apply_padding` now patches the bound `forward` of each `SwiGLU.w3` instead of
  replacing the module. The class, the parameter object, the parameter names and
  the initialization path stay identical.
- The patch is installed from `GPT.__init__` after construction, so
  `_init_weights` runs first and still sees `nn.Linear`.
- The backward flattens leading dimensions before the GEMMs and views the result
  back, matching ATen's linear backward for 3-D input.
- Every padded allocation is recorded, with the pointer, storage, stride, offset,
  resize flag and page distance, instead of a sample of twenty.
- `full_model_gate()` compares whole-model state, logits, loss and every
  gradient bitwise between stock and patched models.
- `v31p5h_plan.py` reuses the 5G containment path; `v31p5h_analyze.py` applies
  gates A to D on CPU from the captured artifacts.

## 11. Recommended next experiment

One run of the corrected arm, on fresh authorization, with these conditions
before any interpretation:

1. **State gate:** the full-model CPU gate must pass, and the run's first printed
   loss must equal the reference's `10.4816` exactly. If it does not, the arm is
   invalid and no fault conclusion follows.
2. **Descriptor gate:** the `w3` backward signature must remain
   `R_16BF 682 256 682`, `OP_N`/`OP_N`, with `Cdesc` `R_16BF 682 3075 682`.
3. **Geometry gate:** the padded target must show at least 65,536 bytes of slack
   and more than 44 bytes to the page-rounded storage end, and the analysis must
   identify it by descriptor signature plus matching shape, not by bare pointer.
4. **Producer gate:** record, per iteration, which of the two `(3075, 682)`
   producers sits within 64 bytes of a page. If the stock `w1` forward output
   keeps landing at the boundary, a clean padded run cannot separate the two, and
   a second arm that pads or displaces that producer as well becomes necessary.

Because one clean run is preliminary, and because the fault appeared in roughly 1
to 3 of 12,919 wide calls, a single clean arm cannot establish stability. Any
claim of "padding removes the fault" needs repeated clean arms at matched
geometry, and even then it would not name the faulty dispatch.
