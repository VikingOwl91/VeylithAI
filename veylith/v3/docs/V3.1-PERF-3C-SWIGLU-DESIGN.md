# v3.1-PERF-3C SwiGLU fusion design audit

Status 2026-10-27. Design and static analysis only. No GPU workload, no
benchmark, no production change.

**Selected strategy for a PERF-3D prototype: A, fused forward only with the
native ATen backward.**

Reason: it is the only strategy whose backward can be bitwise exact by
construction. The backward reuses the same ATen `mul` and `silu_backward`
kernels on the same BF16 operands, so no gradient formula, rounding or
accumulation dtype changes. Only the forward kernel is new and must pass a
bitwise gate before any performance work.

**Expected benefit is about 5 ms per update, not 14 ms.** The 14 ms estimate
requires a fused backward (strategy B/C), whose bitwise equivalence cannot be
guaranteed from first principles. This design does not silently downgrade the
gate to a tolerance.

## 2. The current computation (verified)

Source: `veylith/v3/architecture/model.py`, `SwiGLU.forward` (line 109-110):

```python
return self.drop(self.w3(F.silu(self.w1(x)) * self.w2(x)))
```

Under `torch.autocast(cuda, bfloat16)`, with FP32 parameters:

| step | op | dtype in | dtype out | evidence |
|---|---|---|---|---|
| a | `w1(x)` Linear | BF16 input (autocast), FP32 weight cast to BF16 | **BF16** | trace: `aten::mm` BF16; PERF-1 |
| b | `w2(x)` Linear | same | **BF16** | same |
| t | `F.silu(a)` | BF16 | **BF16** | trace: `aten::silu` (4088,960) BF16, 448 calls/up, 7.80 ms |
| y | `t * b` | BF16, BF16 | **BF16** | trace: `aten::mul` (4088,960) BF16, 448 forward + 896 backward calls, 36.66 ms |
| z | `w3(y)` Linear | BF16 | BF16 | trace |
| dropout | after w3, on (4088,512) | BF16 | BF16 | trace: `native_dropout` 448/up, 7.44 ms |

Saved tensors for backward, verified on CPU with
`saved_tensors_hooks`: **a (silu input), t (silu output, saved by mul), b (mul
operand)**, all BF16. Three saved tensors per expert call.

Backward, verified on CPU against an explicit chain (bitwise equal) and from
the PERF-1 trace (2 `mul` + 1 `silu_backward` kernels per call):

```
g_t = grad * b          # mul backward
g_b = grad * t          # mul backward
g_a = silu_backward(g_t, a)
```

`g_a` and `g_b` are BF16 and flow into the w1/w2 Linear backwards. Projection
parameter gradients are then accumulated into FP32 master gradients by
`AccumulateGrad`, exactly as in the baseline.

Shapes per expert call: a, b, t, y are (4088, 960) BF16, contiguous (rows are
8 sequences x 511 positions). The input x is (4088, 512); w3 produces
(4088, 512). No strided or non-contiguous operand occurs in this subgraph.

### What is inferred rather than directly verified

- The trace records op names, shapes, dtypes and kernel time; it has no Python
  stacks. The mapping of the (4088,960) BF16 `mul`/`silu`/`silu_backward` ops to
  `SwiGLU.forward` is inferred from shape and frequency and is unambiguous: the
  only (4088,960) elementwise product in the model is the SwiGLU gate multiply.
- The exact CUDA/HIP silu kernel formula is source-derived from PyTorch's
  `ActivationSiluKernel.cu` and was validated on CPU, not on this GPU.

## 3. Backward derivation

For `y = SiLU(a) * b` with `s = sigmoid(a)` and `SiLU(a) = a * s`:

```
dy/da = b * (s * (1 + a * (1 - s)))
dy/db = SiLU(a)
```

The ATen `silu_backward` computes exactly
`grad * (s * (1 + x * (1 - s)))` with `s = 1 / (1 + exp(-x))` in FP32 and one
BF16 rounding at the end. CPU validation:

| check | result |
|---|---|
| `F.silu(bf16)` vs FP32 `x / (1 + exp(-x))` then BF16 | **bitwise equal** |
| `bf16 * bf16` vs FP32 product then BF16 | **bitwise equal** |
| `aten::silu_backward` vs `g * s * (1 + x*(1-s))` | **bitwise equal** |
| alternate algebra `g * s * (1 + x - x*s)` | **not equal**, max diff 1.22e-4 |

The algebraic reordering is therefore not a neutral rewrite. Any fused
implementation must use the left-associated form above.

## 4. Precision and rounding boundaries

Current forward, kernel by kernel:

1. `a = bf16(GEMM)` from w1.
2. `t = bf16(t_f)` where `t_f = float(a) / (1 + exp(-float(a)))`; the division
   and exp are FP32, one BF16 rounding at the store.
3. `y = bf16(float(t) * float(b))`; the multiply is FP32, one BF16 rounding at
   the store.

Current backward:

1. `g_t = bf16(float(grad) * float(b))`.
2. `g_b = bf16(float(grad) * float(t))`.
3. `g_a = bf16(float(g_t) * (s * (1 + float(a) * (1 - s))))` with FP32 `s`.
4. Linear backwards produce BF16 input gradients and BF16 weight-gradient
   GEMMs; `AccumulateGrad` adds into FP32 parameters 8 times per update.

The proposed fused forward must reproduce steps 2 and 3 in that order,
including the intermediate BF16 rounding of `t` before the multiply. A kernel
that keeps `t` in FP32 and multiplies would produce different results; the bit
pattern of `t` must be materialized because it is also saved for the backward.

## 5. Numerical equivalence contract

The fused op must satisfy:

| property | requirement | can it be guaranteed? |
|---|---|---|
| forward `t` | same BF16 bits as ATen silu | only if the kernel uses the same exp/div and rounding; must be tested on gfx1201 |
| forward `y` | same BF16 bits as `t*b` | yes if `t` matches and the multiply is FP32 then BF16 |
| saved tensors | a and t saved in BF16 | yes |
| `g_t`, `g_b` | same BF16 bits as the two mul kernels | yes, by calling the same ATen mul kernels in the backward |
| `g_a` | same BF16 bits as ATen silu_backward | yes, by calling `aten::silu_backward` |
| input-gradient accumulation | unchanged | yes: a and b each have one consumer in the fused op; g_a/g_b go to the same Linears |
| dropout RNG | unchanged | yes: dropout is outside the fused region |
| router / aux | unchanged | yes: the gate and aux are outside |
| optimizer / param grads | unchanged | yes: AccumulateGrad and AdamW untouched |
| bitwise | full training step | backward guaranteed; forward conditional on the Triton silu match |

Unlike PERF-3B, no shared tensor changes accumulation dtype here. The fused
op's output `y` has a single consumer (w3); its inputs a and b each have a
single consumer (the fused op); the gradients g_a and g_b are consumed by the
w1/w2 Linears exactly as before. The PERF-3B failure mode does not transfer.

The forward bitwise condition is not guaranteed a priori: Triton on ROCm may
lower `exp` or division differently from ATen's `expf`. That is the single
unknown the prototype must test, and the gate is bitwise, not a tolerance.

## 6. Strategy comparison

Measured cluster: 58.91 ms per update (mul 36.66, silu 7.80, silu_backward
14.45). Per expert call: 2 forward kernels (silu, mul) and 3 backward kernels
(2 mul, 1 silu_backward); 448 expert calls per update.

| strategy | launches/update | traffic effect | numerical risk | autograd | ROCm | complexity | bitwise preservation |
|---|---|---|---|---|---|---|---|
| **A. Fused forward, native backward** | forward 896→448 (448 fewer); backward 1,344 unchanged | removes one (4088,960) BF16 read of t per call: 3.5 GB/update, ~4.4 ms at 800 GB/s, plus ~0.5-1 ms launches | forward silu exp/div/rounding; backward exact by construction | custom Function, backward calls ATen mul + silu_backward | Triton 3.8, bf16 on gfx1201 (to verify) | low-medium | backward guaranteed; forward conditional on a bitwise test |
| B. Custom Function, fused forward and backward | forward 448 fewer; backward 1,344→448 (896 fewer) | removes the g_t intermediate write+read and t read: about 10.5 GB/update, ~13 ms | backward formula, exp, and rounding must all match; algebraic reordering is not neutral | custom backward for three paths | Triton 3.8 | medium-high | not guaranteed |
| C. Triton forward and backward kernels | same as B | same as B, potentially best control of traffic | same as B, plus kernel-level exp/rounding | manual Function | Triton 3.8; needs gfx1201 testing | high | not guaranteed |
| D. Scoped torch.compile / Inductor | potentially both | Inductor fuses the elementwise chain | Inductor may reorder/round differently; deterministic modes and graph breaks unknown | automatic | Inductor on gfx1201 unproven | medium | not guaranteed |

The 14 ms figure in PERF-3A corresponds to strategies B/C, which fuse the
backward. Strategy A's realistic saving is about **5 ms per update** (0.6
percent of a 0.78 s update), because the backward remains three ATen kernels.

## 7. Selected prototype design (PERF-3D, not authorized here)

**Strategy A: fused forward only, native ATen backward.**

### Scope

- New experimental module `veylith/v3/perf/v31p3d_swiglu.py`:
  - a Triton kernel computing `t` (BF16) and `y = t * b` (BF16) in one pass,
    with the explicit FP32 formula and the intermediate BF16 rounding of t;
  - `FusedSiluMul(torch.autograd.Function)` saving a and t;
  - backward: `g_t = torch.mul(grad, b)`, `g_b = torch.mul(grad, t)`,
    `g_a = torch.ops.aten.silu_backward(g_t, a)`, all under no_grad;
  - instance-level patching of the experimental SwiGLU forward only.
- Production `model.py` unchanged. No architecture, optimizer, checkpoint or
  dtype changes.

### Unit-test matrix (GPU, tiny plus exact shapes)

| case | purpose |
|---|---|
| (4088, 960) random BF16 | exact production shape; compare t and y bitwise |
| (1, 960), (17, 960) | tail/odd sizes and kernel masks |
| values 0, ±large, ±1e-30, exact BF16 boundaries | exp overflow/underflow and rounding |
| t bitwise comparison | `uint16` view equality against `F.silu(a)` |
| y bitwise comparison | equality against `t * b` |
| backward bitwise | g_a, g_b equal to the ATen chain |
| non-contiguous inputs | must be rejected explicitly, not silently copied |
| dtype guard | non-BF16 inputs rejected |

### Gates

1. **Bitwise forward/backward gate.** Any mismatch stops PERF-3D; no tolerance.
2. **Two-update deterministic correctness gate.** Baseline twice plus variant
   once, from the verified step-0 state, comparing logits, CE, aux, router
   assignments, gradients, weights and optimizer state by digest, as in
   PERF-3B. Baseline determinism is checked first.
3. **Five-update profile, only if both gates pass.** Count silu/mul kernels,
   elementwise time, full-update wall, VRAM and PPT power against the PERF-1
   method.

### Expected changes and hypotheses

- Forward kernels: 2 → 1 per expert call, i.e. **448 fewer launches per update**
  (about 1.1 percent of the 41,016 total).
- Backward kernels unchanged.
- Kernel time hypothesis: **-4 to -6 ms/update** (t read and launch), not 14.
- Wall-time hypothesis: about -0.6 percent; this is a hypothesis, not a claim.
- VRAM: one saved t, unchanged; no new persistent buffers.

### Abort conditions

Any bitwise mismatch in forward or backward; non-finite values; fewer than 448
fewer forward kernels; no measurable kernel-time reduction; GPU/HIP fault;
environment drift.

## 8. Unknowns and risks

- Whether Triton's `exp`/division on gfx1201 reproduces ATen's silu bit for bit
  is **unknown** without a GPU test. If it does not, strategy A is rejected and
  the 14 ms requires a tolerance change that this programme does not allow.
- Whether the Triton compiler preserves the explicit BF16 rounding of t before
  the multiply; the unit test must check the stored `t` bits.
- The measured 5 ms traffic estimate assumes 800 GB/s effective and that the
  elementwise stream is on the critical path; the profiled saving may differ.
- Strategy B/C could be revisited only if a standalone kernel demonstrates a
  bitwise-identical fused backward on the exact shapes; that is a separate
  numerical experiment, not part of PERF-3D.
- Inductor (D) remains unproven for this model on ROCm and is not selected.

## 9. Decision

**Recommend Strategy A for a bounded PERF-3D prototype**, with the bitwise
forward/backward gate first and the two-update gate second. If the forward is
not bitwise identical, stop and reject the fusion; do not relax the gate.

The expected benefit is small (about 5 ms, 0.6 percent of the update), and it
is not guaranteed. The design is recommended because the backward risk is
eliminated by construction and the remaining unknown is isolated to one
kernel and one test.
