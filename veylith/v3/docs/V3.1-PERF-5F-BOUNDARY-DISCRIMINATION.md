# v3.1-PERF-5F boundary-sensitive fault discrimination

Status 2026-10-27. Three bounded GPU executions of a four-execution budget. No
production change, no checkpoint change, no package change, no reset, no retry.

**Outcome: fault reproduced without causal discrimination, with the consumer
hypothesis now excluded experimentally.** The 682 x 3075 boundary geometry is
present in every faulting run (four independent reproductions to date, each
ending exactly 4 bytes before a 2 MiB page), a standalone BF16-to-FP32 cast on
the same geometry at the same 4-byte distance is clean, and the one manipulation
this environment can apply to the allocator provably cannot move that boundary.
No arm changed the boundary, so the causal question stays open.

## 2. CPU preparation

### 2.1 Geometry, verified across all previous faults

Re-derived in this stage from each run's own hipBLASLt log and kernel log:

| run | fault page | C buffer | extent | tensor end | gap | page aligned |
|---|---|---|---:|---|---:|---|
| 5C baseline | `0x7f3b44c00000` | `0x7f3b44800000` | 4,194,300 | `0x7f3b44bffffc` | 4 | yes |
| 5C attribution | `0x7fdb92000000` | `0x7fdb91c00000` | 4,194,300 | `0x7fdb91fffffc` | 4 | yes |
| 5D rolling | `0x7fd7b5400000` | `0x7fd7b5000000` | 4,194,300 | `0x7fd7b53ffffc` | 4 | yes |
| 5F case A | `0x7f4aae400000` | `0x7f4aae000000` | 4,194,300 | `0x7f4aae3ffffc` | 4 | yes |

Four runs, four different absolute addresses, one identical geometry: a
682 x 3075 bf16 GEMM output whose extent ends 4 bytes before a 2 MiB page, where
that page is the end of the 4 MiB mapping.

### 2.2 Copy-tail masking, re-verified

`ATen/native/cuda/CUDALoops.cuh` (ROCm branch) sends the remainder block to
`memory::policies::unroll`, and `MemoryAccess.cuh`'s `unroll_base` guards `load`
and `store` with `if (thread_idx < remaining)` using scalar `LoadWithoutCast`.
The vectorized path runs only on full blocks inside `N`. The observed copy
kernel, `vectorized_elementwise_kernel<4, bfloat16tofloat32_...>`, is the
contiguous variant. A masked tail cannot cross the allocation end.

### 2.3 Can padding be introduced without changing the GEMM?

At the allocator level, yes in principle: `PYTORCH_HIP_ALLOC_CONF` with
`roundup_power2_divisions` is supported by this build (string present in
`libtorch_hip.so`), and it changes block sizes only. Shapes, strides, dtypes and
therefore GEMM descriptors and kernel selection are untouched, so the comparison
is not confounded in that sense.

But it cannot move *this* boundary, and the arithmetic shows why. The tensor is
4,194,300 bytes. Any rounding granularity derived from the next power of two
(8,388,608) divided by a power of two lands on 524,288 or larger, and the
smallest rounding up from 4,194,300 is 4,194,304, i.e. exactly the page-aligned
end the driver already produces. Coarser settings produce 4,194,304 as well;
only a jump to 8,388,608 would add slack, and that is not what the knob does at
four divisions. The 4-byte gap is therefore invariant under this control, which
the measurement in case C confirms.

### 2.4 Placement checks

Every case records the actual pointer, extent and the distance to the next 2 MiB
boundary, taken from the hipBLASLt log for the model runs and from the
allocation itself for the standalone cast. Observed allocation boundaries are
kept separate from the inferred mapping end: the mapping ends at the page
boundary implied by the driver rounding of the block, which is why the fault page
equals `tensor_end + 4` in every run.

## 3. Executions

Each ran in a fresh process, idle-gated, `ulimit -c 0`, 120 s timeout, with the
original sparse reproducer and the original backend. No serialization.

| case | what ran | result | geometry |
|---|---|---|---|
| A | reference: 5D rolling profiler, no shapes, no recorder | **faulted**, SIGABRT, exit -6, page `0x7f4aae400000`, wall 24 s | 12,919 wide calls, 1 within 64 B of a page, min gap 4 |
| B | standalone bf16->fp32 cast on 682 x 3075 | **clean**, exit 0, two casts, wall 6 s | tensor end `0x7f5e82bffffc`, next page `0x7f5e82c00000`, gap **4** |
| C | reference plus `PYTORCH_HIP_ALLOC_CONF=roundup_power2_divisions:4` | **faulted**, SIGABRT, exit -6, page `0x7f4ccea00000`, wall 23 s | 12,919 wide calls, 3 within 64 B, min gap still 4 |

Case A reproduced the fault, which is the precondition for the others; case B
exercised the consumer in isolation at the exact boundary distance; case C
attempted the only padding this environment allows.

**Case B is the important negative.** The tensor ended 4 bytes before a 2 MiB
page (the precise geometry of the faulting model buffers), the buffer was fully
written, and two BF16-to-FP32 casts read it without a fault. The masking
analysis predicted exactly this. The kernel name was not captured because the
profiler was queried before its context closed; the operation is unambiguous from
the code path (`aten::_to_copy` to float32), but the record is weaker than it
should be, and that is reported rather than glossed.

**Case C is void, not confounded.** The padding never changed the geometry: the
wide buffers still ended 4 bytes before a page, and the run faulted. Per section
2.3 that outcome is arithmetically forced for a 4,194,300-byte request, so this
arm tests nothing about the boundary.

## 4. Interpretation

| class | verdict |
|---|---|
| 1, boundary dependence demonstrated | **no** |
| 2, boundary dependence supported but confounded | **no**: the manipulation did not take, so it is not even a confounded test |
| 3, fault reproduced without causal discrimination | **yes**: A and C faulted, the geometry is exact and repeated, but no arm varied it |
| 4, fault not reproduced | **no** |
| 5, experiment inconclusive | **yes for the causal question** |

What the stage does establish:

- The **consumer is excluded as the faulting access**. It reads a buffer whose
  end is 4 bytes from a page and does not fault (B), and its tail is masked by
  the shipped template (2.2).
- The **boundary correlation is exact and reproducible** (four runs), and it is
  **rare**: 1 to 3 of 12,919 wide GEMM calls sit within 64 bytes of a page in a
  faulting run, which is consistent with an intermittent, layout-dependent
  defect rather than a per-call one.
- The allocator knob that the v2 investigation once used as a workaround
  **cannot move this particular boundary**, so its earlier success does not
  transfer to this shape.

Updated candidate ranking: (1) the `w3` backward GEMM epilogue writing past its
output end, (2) a Tensile operand read past the end of the same mapping, (3) any
kernel that later reads the reused 4 MiB block once the allocator hands it out
again. The consumer is out.

## 5. Why case D was not run

The remaining arm was reserved for a second discriminator, and none is available
under this stage's constraints. Changing the boundary for a 4,194,300-byte
tensor requires either a different shape (forbidden: original geometry), a
model-level padded allocation (forbidden: no production or model changes), or an
allocator granularity that this build cannot express (section 2.3). Spending the
fourth execution on another attempt at the same knob would produce another void
arm, so the budget is left at three.

## 6. Recommended next step

A discriminator that can actually change the boundary must control the
allocation of the `w3` backward output. Two options, both needing explicit
authorization because they touch code:

1. **Padded-output ablation in the experimental harness only**: wrap the expert
   `w3` linear so its output is a view into a storage that is at least 64 KiB
   larger than the tensor, keeping shapes, strides, dtype and therefore the GEMM
   descriptors identical. Verified by logging the pointer, extent and gap. A
   clean run then supports boundary dependence; a faulting run refutes it.
2. **Epilogue-versus-operand discrimination**: with the padded output in place,
   also place the *operand* (the 682-column input of the next GEMM) at a page,
   one condition per run, to separate a store overrun from an operand read.

Both must keep the PERF-4D production baseline untouched, run one condition per
fresh process, and keep the same containment and stop rules.
