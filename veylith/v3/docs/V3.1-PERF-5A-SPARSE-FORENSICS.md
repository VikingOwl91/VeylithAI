### 3.1 What the fault actually was

- Device side: an HSA/GPUVM **memory access fault**, "Page not present or
  supervisor privilege", reported by the ROCm runtime. `observed` (E1, E15).
- Host side: the process died with **exit code 134, SIGABRT**, not SIGSEGV. No
  Python traceback, no core file (the coredump handler failed). `observed` (E1,
  E20, E21). Any description of this as a "segmentation fault" would be wrong.
- GPU state: **no GPU reset** and no amdgpu error in the kernel log for either v3
  fault; `rocm-smi` stayed responsive and no KFD process remained. `observed`
  (E20, E21). The GPU was not wedged.
- Phase: **backward**. Forward-only completes 3/3; the fault needs expert-weight
  gradients. `observed` for v2 (E2, E10); `inferred` for v3 from signature and
  the sparse-backward context.

## 5. Hypothesis matrix, ranked

### 1. E: hipBLASLt solution-specific K-tail over-read, layout-dependent

- **Supporting:** E15-E19 give a named kernel, a concrete address arithmetic
  with no N term, a measured 16-byte slack at a page boundary, a passing run
  with more slack, and 44,930 direct hipBLASLt dispatches. It also explains
  several otherwise odd clean results: uniform routing (K = 16384, K mod 64 = 0),
  dense-combined (K = all tokens), fp32 (different kernel family), and the
  forward (fixed K = 256 for the first expert GEMM).
- **Contradicting:** never observed for the 8E/top-2 or v3 faults (U1, U8); the
  model is not hardware-verified (U2, U3); E9's GEMM sweep was clean, though it
  covered forward-path shapes, not the variable-K expert weight gradients.
- **Minimal discriminating test:** one bf16 GEMM at M=256, N=682, K=4108 with B
  ending at a page boundary versus at least 64 KiB of slack, hipBLASLt forced.
- **Expected:** fault in the tight-slack arm only; clean at N=640 and K=4160.
- **Risk:** process abort (SIGABRT), no reset expected; one GPU fault per
  offending run. Containment required.

### 2. F: PyTorch ROCm workspace or kernel implementation

- **Supporting:** the behavior change is PyTorch-side (E14, I3); the failing call
  is reached through PyTorch's workspace and heuristic path; disabling hipBLASLt
  workspaces on a failing build did not prevent the fault, while re-enabling them
  on a passing build reintroduced it (asymmetric, so PR #196920 is a candidate,
  not a proven cause).
- **Contradicting:** the named faulting kernel is a library kernel, not an ATen
  kernel, so the defect may live one layer down (U7); the asymmetry means the
  workspace PR alone cannot explain everything.
- **Minimal discriminating test:** run the deterministic reproducer with
  `torch.backends.cuda.preferred_blas_library("rocblas")`, which bypasses
  hipBLASLt entirely and is already known to be bitwise identical on this stack
  (PERF-2, 24 cases).
- **Expected:** clean with rocBLAS, fault with hipBLASLt, if the locus is the
  hipBLASLt call path at all.
- **Risk:** low; the same abort risk as any reproducer run.

### 3. C: layout, strides and alignment as the enabling condition

- **Supporting:** boundary addresses (E12, E15), grad-filter sensitivity at
  identical kernels (E10), the alignment workaround (E18), and the 16E kernel
  being an `Ailk_Bjlk` (layout-specific) solution.
- **Contradicting:** it is a condition, not a cause; a correct kernel would not
  care where its operand ends. E9 varied strides without faulting.
- **Minimal discriminating test:** spacer sweep that shifts B's offset within
  its segment across a 2 MiB range in 64 KiB steps, same shape and backend.
- **Expected:** fault frequency tracks the offset; a fixed alignment removes it.
- **Risk:** low; at most one abort per offending arm.

### 4. A: sparse indexing, gather and scatter backward

- **Supporting:** sparse-only (E4), expert-grad-only (E10), variable routing
  necessary (uniform routing clean), forward clean while the gathering backward
  faults, and E13 associates the boundary block with index ops.
- **Contradicting:** indices are in bounds and audited; per-op isolation clean
  (E8); a corrected micro-test clean; a deliberate OOB index produces the *same*
  signature, so the signature cannot identify this hypothesis; and the named
  kernel in the 16E case is a GEMM (E15).
- **Minimal discriminating test:** keep the exact expert GEMM shapes but replace
  the variable-size gather with a fixed full-size slice (padded), so the index
  ops run on constant shapes.
- **Expected:** if A, the fault disappears with fixed-size dispatch even though
  the GEMMs are unchanged.
- **Risk:** low.

### 5. B: BF16 atomics or gradient accumulation

- **Supporting:** bf16-only (E3), backward-only (E2), and the knowledge that
  `index_add` backward uses atomics in bf16.
- **Contradicting:** the fault occurs with `--no_optimizer` (no AdamW state), a
  bf16 `index_add` backward alone was clean over 5000 trials, and the reported
  fault is an unmapped-page access, not a lost update or NaN. E4's CPU control
  also used the same arithmetic.
- **Minimal discriminating test:** replace the scatter-accumulate with an fp32
  accumulation buffer while keeping bf16 GEMMs.
- **Expected:** no change if B is false.
- **Risk:** low.

### 6. H: asynchronous error reported at a later synchronization point

- **Supporting:** the fault always surfaces after the last completed sync (E21:
  after the iteration-25 print; v2 op traces: the traced iteration's backward
  completes and the fault fires at the next H2D copy), and there is never a
  Python traceback.
- **Contradicting:** as a *cause* it is refuted by E5, which serializes every
  launch and still faults.
- **Minimal discriminating test:** none needed; treat H as a reporting property.
  Any reproducer must attribute the fault to a phase, never to the last printed
  operation.
- **Risk:** not a fault source.

### 7. D: autograd graph lifetime or aliasing

- **Supporting:** grad-filter sensitivity (E10) shows the graph shape matters;
  long-lived references change allocation order.
- **Contradicting:** the sparse path already accumulates out of place; forward
  and isolated backward are clean; a use-after-free would fault at a freed
  address, not at the end of a mapped segment.
- **Minimal discriminating test:** `retain_graph=True` plus an explicit
  `gc.collect()` between iterations; if the outcome is unchanged, D is out.
- **Risk:** low.

### 8. G: GPU compiler or driver fault

- **Supporting:** the failure is a hardware-level page fault.
- **Contradicting:** E14 is a clean control: same GPU, kernel, driver and ROCm
  7.14 runtime, torch 2.14.1 faults while 2.15.dev20261005 passes. A driver or
  compiler bug would not flip with the user-space library.
- **Minimal discriminating test:** none; already discriminated.
- **Risk:** not a candidate.

Ranking by evidence, not intuition: E, F, C, A, B, H, D, G.
E and F are complementary rather than exclusive: E names the failing kernel,
F explains why the behaviour changed and where a fix landed.

## 7. Numerical and safety contract for any future sparse path

The dense baseline is frozen above and must not be perturbed by sparse work.

Any future sparse implementation must separately satisfy:

1. **Process and GPU stability:** no GPUVM fault, no SIGABRT, no reset, KFD clean
   after each run, kernel log clean.
2. **Shapes and routing:** indices in bounds, unique where the algorithm needs
   uniqueness, per-expert token counts matching the router, no dropped tokens.
3. **Numerical correctness:** outputs and gradients within the same distance
   from an fp64 reference as the dense-combined path.
4. **Reproducibility:** bitwise reproducible within the sparse path for a fixed
   seed, and resumable.
5. **Performance:** a measured end-to-end gain over the frozen dense baseline at
   equal or lower VRAM, with the host-side caveat from PERF-4A respected.

**Bitwise identity between dense and sparse is not expected to be automatic.**
The expert GEMMs have a different K (routed subset versus all tokens) and the
combination accumulates in a different order (`index_add` into a scatter buffer
versus a dense sum over experts). v2 measured both equidistant from an fp64
reference at about 1e-6 relative, which is fp32 reduction noise. A future sparse
acceptance gate therefore has to compare against a reference, not against dense
bits, and **no tolerance relaxation is authorized now**; any tolerance requires
its own explicit authorization.

## 8. Proposed PERF-5B

One bounded diagnostic experiment, staged so that a negative result is still
informative. Not implemented and not authorized here.

- **Files:** `veylith/v3/perf/v31p5b_gemm_tail.py` (single-GEMM reproducer with
  spacer sweep and backend switch) and `veylith/v3/perf/v31p5b_plan.py` (case
  runner that spawns one process per case and records exit code, stderr, dmesg
  window and GPU health). No production file touched.
- **Dtypes and shapes:** as in section 6; bf16 primary, fp32 control; M=256,
  N in {682, 640}, K in {4108, 4160}, leading dimensions varied to produce
  contiguous and non-contiguous operands.
- **Order:** CPU model, then the two negative shape controls, then the slack
  control, then the spacer sweep, then the model-reproducer positive control,
  then the rocBLAS arm. Stop the matrix at the first deviation from the expected
  column.
- **Limits:** at most 8 GPU executions, 120 s each, fresh process each, one GPU
  fault permitted in total (the positive control is expected to fault); abort
  immediately on a second unexpected fault, on a GPU reset, on an amdgpu error in
  dmesg, or on a lingering KFD process.
- **Logs:** per-case `stdout`, `stderr`, `exit_code`, `signal`, wall time,
  `rocm-smi --showpids` before and after, and the dmesg window for the run.
- **Recovery:** no retry, no GPU reset; if the device is unresponsive, stop and
  report rather than attempt recovery.
- **Success criteria:** a discriminating outcome.
  (a) rocBLAS clean and hipBLASLt faulting, or the target shape faulting while
  N=640 and K=4160 stay clean: E/F confirmed, and the mitigation space becomes
  backend choice or shape padding.
  (b) everything clean including the positive control: the environment drifted,
  stop and re-derive before any further work.
  (c) the synthetic arms all clean while the positive control faults: the
  single-GEMM hypothesis is unproven (U6 stands), and the next step is
  kernel-level attribution on the model reproducer, not more shape sweeps.
- **Failure criteria:** an unexpected fault in a negative control, a GPU reset,
  or an amdgpu error in dmesg; then the experiment stops and the matrix is
  reported as inconclusive rather than rerun.

## 9. Unknowns and limitations

- The v3 fault was never attributed to a kernel; every statement tying it to the
  hipBLASLt mechanism is an inference from signature and configuration, not a
  capture.
- The K-tail model is a CPU reconstruction from disassembly; the three hardware
  assumptions (U2, U3, U4) are unverified, and the single-GEMM reproducer has
  never been run.
- The 8E/top-2 fault and the 16E/top-4 fault may not share a mechanism; only the
  configuration trend is shared.
- The fix attribution (PR #196920) is asymmetric and unproven.
- Archived v2 evidence was read as-is; some of it (memory-history stacks) is
  self-described as partially garbled.
- No GPU, sparse path, benchmark or training ran in this stage, so nothing here
  is a new measurement of the fault.
