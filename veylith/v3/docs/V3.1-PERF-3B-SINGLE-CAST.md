# v3.1-PERF-3B single-cast RMSNorm prototype

Status 2026-10-27. Bounded experimental prototype. Production code and the
v3.1-L artifacts are unchanged.

**Decision: Reject P1 due to numerical or semantic mismatch.**

The forward is bitwise identical to the baseline, but the single shared BF16
norm output changes backward gradient accumulation from FP32 to BF16. Gradients
differ at 5.6e-5 relative on update 1, and after one optimizer step the
weights, gradients, optimizer state and update-2 router assignments diverge.
The mission requires bitwise identity and forbids relaxing tolerances, so the
profiling gate was not run and no performance claim is made.

## 2. Implementation

The variant is runtime-only (`v31p3b_variant.py`), applied to an experimental
model instance by the harness. It patches 17 RMSNorm modules and 7 MoE modules.

- `RMSNorm.forward`: the original FP32 computation
  `x * rsqrt(x.pow(2).mean(-1) + eps) * weight` is kept exactly, then the final
  result is cast once with `.to(torch.bfloat16)`.
- `MoE.forward`: an exact copy of the production forward with the dense
  accumulator changed from `flat.new_zeros(flat.shape)` to
  `flat.new_zeros(flat.shape, dtype=torch.float32)`, because the norm output is
  now BF16 and the combine must stay FP32.
- No architecture, parameter, checkpoint-format or optimizer change.

Non-Linear consumers were checked explicitly:

| norm output | consumers | type |
|---|---|---|
| `ln1` | q, k, v projections | Linear only |
| `ln2` | router gate and 8 experts' w1/w2 | Linears, **plus `flat.new_zeros`** in the MoE combine |
| `ln_f` | LM head | Linear only |

`flat.new_zeros` was the only non-Linear use; it is forced to FP32, so the
combine path is unchanged. Routing math, dropout, the auxiliary loss, the
optimizer, gradient clipping and all guards are untouched.

## 3. Correctness gate

Method: three independent runs in one process, each built from the verified
step-0 weights and the step-0 RNG state, with the data iterator restarted at
batch 0. Two updates per run. Digests are SHA-256 over tensors in sorted name
order (BF16 values widened exactly to FP32 for hashing).

- Baseline run A versus baseline run B: **bitwise identical** on every field,
  including the head logits digest, router digests, gradients, weights and
  optimizer state. The deterministic baseline permits a bitwise gate.
- Baseline versus variant:

| measurement | baseline | variant | result |
|---|---:|---:|---|
| update 1 main CE | 9.121862960188356 | 9.121862960188356 | identical |
| update 1 aux sum | 7.554577529430389 | 7.554577529430389 | identical |
| update 1 loss | 9.197408735482659 | 9.197408735482659 | identical |
| update 1 head logits digest | `5b395341...` | `5b395341...` | identical |
| update 1 router assignments | `30f05349...` | `30f05349...` | identical |
| update 1 grad norm | 1.484588623046875 | 1.484505295753479 | differs, abs 8.33e-5, rel 5.6e-5 |
| after step 1: weights / grads / optimizer | digests | digests | all differ |
| update 2 main CE | 9.091102196978962 | 9.091184373471135 | differs, abs 8.22e-5, rel 9.0e-6 |
| update 2 aux sum | 7.563181102275848 | 7.563266575336456 | differs |
| update 2 grad norm | 1.5635069608688354 | 1.5644505023956299 | differs, rel 6.0e-4 |
| update 2 router assignments | `de28e574...` | `566d2fb4...` | differ |

The forward, loss, aux and router assignments of update 1 are bitwise
identical. The first divergence is the backward gradient norm. After the
optimizer step the weights diverge, and update 2 differs in forward, router and
gradients.

## 4. Mechanism

A retained-gradient diagnostic on the block-1 `ln2` output, one microbatch:

| item | baseline | variant |
|---|---|---|
| norm output dtype | float32 | **bfloat16** |
| gradient at the norm output | float32 | **bfloat16** |
| gradient norm | 1.9537017215043306e-4 | 1.9537282059900463e-4 |
| max absolute difference | | 2.25e-8 |
| relative L2 | | 0.665 percent |

In the baseline, each of the 17 consumers casts the FP32 norm output to BF16
inside its Linear; the cast's backward converts each BF16 input gradient back
to FP32, so autograd accumulates 17 FP32 gradients. In the variant, all 17
consumers share one BF16 tensor. Autograd accumulates their gradients in the
tensor dtype, so the sum is performed in BF16, and the cast backward only widens
the already-rounded sum. That is a real change in gradient accumulation
semantics, not a measurement artifact.

The forward identity also confirms the cast placement itself is correct: the
GEMM operands are exactly the values autocast produced. The failure is entirely
on the backward accumulation path.

## 5. Profiling gate

**Not executed.** The correctness gate failed, so the cast-count and kernel-time
comparison was skipped. No evidence exists for or against the -18 ms hypothesis
in this prototype, and none is claimed.

## 6. Decision and salvage path

**Reject P1 due to numerical or semantic mismatch.**

Rationale: the optimization as specified (one shared BF16 cast) cannot preserve
FP32 gradient accumulation. Any exact variant would need either per-consumer
FP32 accumulation, which reintroduces the casts and therefore the cost, or a
fused kernel that accumulates the consumer gradients in FP32 inside a custom
backward. The latter is a different design (closer to the P2 fusion candidate),
not the single-cast P1, and would require its own correctness gate.

If a tolerance-based experiment were ever authorized, the measured divergence
is small (update-1 grad norm 5.6e-5 relative; update-2 CE 9.0e-6 relative), but
this stage does not relax the gate and does not proceed to paired A/B training.

## 7. Deviations

- The first harness invocation failed before any GPU work because the project
  path was missing from `sys.path`; fixed, no updates consumed.
- An initial CPU-only copy check showed different MoE outputs because dropout
  consumed RNG between the two calls. In eval mode, and against the class method
  directly, the copied MoE is bitwise identical on FP32 input.
- No profiling was run after the gate failure.
