# v3.1 design note: 0.1B MoE baseline

Status 2026-10-26. Design and CPU validation only. No training, no GPU, no
model quality claim. The architecture is in `V3.1-ARCHITECTURE.md`; memory
and compute are in `V3.1-MEMORY-COMPUTE.md`; evaluation is in
`V3.1-EVALUATION.md`.

## 1. Decision in one paragraph

Use **candidate A** (8 layers, width 512, GQA 8/2, 8 experts top-2, expert
FFN 960, no shared expert, vocab 8192, context 512, no MTP): **98.34M total
parameters, 36.41M active per token**. Keep **candidate C** (12 layers,
width 384, top-2 plus one shared expert: 95.88M / 39.92M) as the fallback
for routing stability or a depth/width change. B is a depth ablation, D is
the top-1/shared variant. The choice is based on parameter accounting,
attention/MoE tradeoffs and the unresolved ROCm sparse-fault risk, not on
benchmark claims.

## 2. Data context

| item | value |
|---|---|
| train tokens | 95,951,233 |
| validation / test tokens | 2,122,377 / 2,094,292 |
| tokenizer | BPE 8192, multi-source |
| mix | FineWeb-Edu 62.9 %, Wikipedia 21.2 %, Cosmopedia v2 15.9 % |
| Python-Edu | blocked (The Stack v2 terms); 5 % gap |

The corpus is a single-pass budget of about **1 token per parameter** for a
0.1B model. That is far below compute-optimal scaling (roughly 20 tokens per
parameter for a Chinchilla-style estimate, about 2B tokens for 100M
parameters). v3.1-A is therefore a **data-limited baseline**, not a
compute-optimal model. The design does not hide this mismatch.

## 3. Candidate comparison

| id | config | total | active sparse | active ratio | role |
|---|---|---:|---:|---:|---|
| A | 8L, 512w, top-2, ffn 960, no shared | 98.34M | 36.41M | 0.370 | primary |
| B | 10L, 512w, top-2, ffn 800, 2 dense | 97.82M | 38.84M | 0.397 | depth ablation |
| C | 12L, 384w, top-2, ffn 736, shared | 95.88M | 39.92M | 0.416 | fallback |
| D | 8L, 512w, top-1, ffn 896, shared | 102.47M | 35.03M | 0.342 | routing ablation |

All are within 95-105M total and 35-40M active. A is the simplest; C adds a
shared expert and more depth at a narrower width; D tests top-1; B tests
depth with two dense layers.

## 4. Why A, and why not the alternatives

- A has the lowest active count of the top-2 candidates (36.4M), the fewest
  layers (cheapest activation memory and shortest path), and no shared-expert
  complexity. It keeps the v2 attention/MoE recipe, which the project has
  already validated on CPU and on the GPU with the dense-combined path.
- B is 0.5M smaller but 2.4M more active and adds two dense layers; it is a
  useful ablation, not a better default.
- C is a genuine fallback: the shared expert gives always-on capacity and
  may stabilize routing; the 12-layer/384-wide shape changes the depth/width
  tradeoff. Its active count is at the top of the target range (39.9M).
- D is cheaper (35.0M) but top-1 routing is more collapse-prone; it is an
  experiment, not the baseline.
- A tied head would save 4.19M total/active but changes the capacity and
  comparability; it stays a config ablation (`tie_embeddings`).

## 5. Data scaling recommendation

1. Run A on the current 95.95M tokens as a single-pass baseline; it is the
   only data available without new downloads and it is enough to validate the
   training stack, routing and evaluation.
2. Treat the result as **data-limited**; do not compare it to compute-optimal
   models or claim general quality.
3. For a serious 0.1B attempt, grow the corpus to 500M-1B tokens:
   - more FineWeb-Edu (the source has 9.67M documents);
   - more Wikipedia (6.4M articles);
   - Python-Edu only after The Stack v2 terms review/acceptance.
   No download happens in this task.
4. At 500M tokens (about 5 tokens/param) and 1B (about 10 tokens/param), the
   model is still below compute-optimal but far more informative. Memory and
   compute estimates are in `V3.1-MEMORY-COMPUTE.md`.
5. Keep the 8192 tokenizer; per-source fertility is 1.55 (FineWeb), 1.75
   (Wikipedia), 1.57 (Cosmopedia). Re-check fertility if the mix changes.

## 6. Evaluation strategy

Use the frozen multi-source validation and test splits; never train on them.
Report per source and overall:

- main next-token CE, perplexity, bits/char per source;
- token-weighted overall CE and a macro average over sources;
- train/validation divergence (fixed train sections);
- router entropy, expert share, unused experts;
- throughput, peak VRAM, step time on the eventual GPU run;
- fixed seeds, checkpoint metadata, reproducible selection.

Dense and smaller-MoE baselines: the existing 25.6M v2 MoE (29.28M with the
8192 vocabulary), the 17.3M smaller MoE and the 8.3M dense baseline from the
data task. They are comparison points, not assumptions of superiority.
Generation is secondary; Shakespeare-only evaluation is not a primary
measure. Full protocol: `V3.1-EVALUATION.md`.

## 7. MTP

Excluded from v3.1-A: no config fields, no shifted t+2 loss, no `mtp_ce`
metric, no checkpoint keys, next-token inference only. v2 MTP code and
checkpoints stay historical. Later ablation: same data/seed/config, w=0.0
baseline against w=0.2/0.5, compare main CE/bits per source, MTP CE,
train/val gap, router and generation; no benefit without a controlled run.

## 8. Open decisions before training

1. Sparse vs dense-combined execution on ROCm: sparse is the algorithmic
   design; a bounded fault smoke test must pass before the run. Dense is the
   safe fallback at E/k expert compute.
2. Learning rate, warmup, batch, dropout: inherit v2 (3e-4, 100, 64, 0.1)
   unless a CPU-side argument changes it.
3. Context 1024: not in the baseline; doubles attention cost/memory.
4. Tied head and shared expert: ablations, not defaults.
5. Checkpoint format: define in the training implementation; no MTP fields.
6. Training data: 95.95M now, 500M-1B for a serious run.

## 9. Risks

- Data-limited baseline: 1 token/param; results will understate the
  architecture's potential and must be labelled as such.
- ROCm sparse MoE fault is unresolved; dense fallback increases compute.
- Cosmopedia is 15.9 % synthetic; per-source evaluation is required.
- Routing stability at 8 experts/top-2 is not proven at this scale; monitor.
- No training code, checkpoint format or GPU measurement exists yet.
