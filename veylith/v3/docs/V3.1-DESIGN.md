# v3.1 pretraining design note (2026-10-26)

Status: proposal only. No model code, no training run, no GPU work. This note
compares candidate architectures on the actual 95.95M-token corpus from
`MULTI-SOURCE-100M-2026-10-26.md`.

## 1. Data and budget

| item | value |
|---|---|
| train tokens | 95,951,233 |
| validation / test tokens | 2,122,377 / 2,094,292 |
| tokenizer | BPE 8192, model sha256 `411227a8...` |
| context | 256 (v2 block size) |
| train mix | FineWeb-Edu 62.9 %, Wikipedia 21.2 %, Cosmopedia v2 15.9 % |
| blocked | Python-Edu 5 % (The Stack v2 terms) |
| single pass | 5,856 steps at batch 64 x 256 |
| eval | held-out multi-source split, bits/char and main CE per source |

One pass is 5,856 steps. The corpus is 217x the Tiny Shakespeare training
split of v2 (0.44M tokens), so the data-scarcity regime that produced the
early v2 overfitting is gone. No token is repeated in the planned pass.

## 2. Candidates

All candidates use the v2 components where possible: RoPE, RMSNorm, GQA,
SwiGLU, tied? (v2 uses an untied output head), context 256, bf16. Vocab
8192 adds two 8192 x n_embd matrices (embedding and untied head).

| candidate | total params | active / token | vocab-dependent params | compute (6 x tokens x active) | estimated 1-pass runtime |
|---|---:|---:|---:|---:|---:|
| v2 MoE 25.6M, 8192 | 29,284,608 | 13,571,328 | 4,194,304 | 7.81e15 FLOPs | about 16 min |
| smaller MoE, n_embd 192, 8192 | 17,271,728 | 8,431,728 | 3,145,728 | 4.85e15 FLOPs | about 11 min |
| dense 6 x 256, 8192 | 8,323,328 | 8,323,328 | 4,194,304 | 4.79e15 FLOPs | about 5 min |

Notes:

- Active means the audit convention: full dense matrices and full embeddings
  count as active; top-2 routed experts count as active for the MoE. The
  dense-combined training path computes all experts, so its per-token compute
  is the total parameter count (29.28M for the first row), not the active
  count. The runtime estimates use the measured 162 ms/step (b64 x 256,
  25.6M dense-combined) as a scaling anchor and are rough, not benchmarks.
- The smaller MoE numbers extrapolate the E2 configuration from the P1-3
  audit (n_embd 192, head_dim 24, expert width 512: 14.51M total / 5.67M
  active at vocab 1000), plus the 8192 vocabulary.
- The dense baseline is 6 layers, width 256, full causal attention, SwiGLU
  8/3, no MoE, no MTP, untied head: 8.32M parameters, all active.
- The v2 MoE at 8192 is 3.7 tokens per total parameter in one pass; not
  Chinchilla-optimal, but a legitimate single-pass research run.

## 3. Comparison

| dimension | v2 MoE 25.6M | smaller MoE 17.3M | dense 8.3M |
|---|---|---|---|
| capacity | highest | middle | lowest |
| active compute per token | 13.57M (29.28M dense-combined) | 8.43M (17.27M dense-combined) | 8.32M |
| GPU memory | highest | middle | lowest |
| throughput | 1.0x anchor | about 1.5x | about 3x |
| routing risk | top-2 + shared + aux | same | none |
| data/compute balance at 96M tokens | 3.7 tok/param | 5.6 tok/param | 11.5 tok/param |
| comparability to v2 results | direct | architecture ablation | clean dense baseline |
| failure modes | router collapse, aux tuning, MTP interference | same | none of those; plain under/overfitting |

The dense baseline is the cheapest clean reference and the easiest to debug.
The smaller MoE keeps the research line and roughly matches the dense
baseline's active compute while adding routing. The 25.6M MoE is the direct
continuation of v2 and tests whether more data removes the earlier deficit,
but it is 3.5x the compute of the dense baseline.

## 4. Recommendation

Primary v3.1 candidate: **smaller MoE, n_embd 192, vocab 8192**
(17.27M total / 8.43M active). It keeps the v3 research question (does MoE
help at matched data?) and fits a single pass in roughly 11 minutes at the
measured anchor.

Compute-matched control: **dense 6 x 256, vocab 8192** (8.32M, all active).
One run on the same data and schedule separates "MoE effect" from "more
parameters / more compute".

Upper-capacity reference: **v2 MoE 25.6M, vocab 8192** (29.28M total /
13.57M active) only if a third run is approved; it answers whether the v2
deficit was data scarcity.

This is a recommendation, not an approval. No run starts without a separate
GPU approval and a fixed command.

## 5. Evaluation strategy

- Use the frozen multi-source validation and test splits; report main CE and
  bits/char per source, not only the pooled number.
- Keep the v2 bits/char protocol; never compare raw token losses across
  tokenizers.
- Report the synthetic share (Cosmopedia) separately; a pooled score can be
  dominated by FineWeb.
- Check router entropy and expert usage on held-out text; no collapse.
- Check repetition on fixed prompts; generation quality is secondary.
- Contamination caveat: Cosmopedia was generated from FineWeb seeds;
  near-duplicate dedup removes near-identical text, not semantic overlap.
  Per-source results are the honest view.

## 6. Open decisions before the run

1. Width/depth: keep 6 x 256 for comparability or widen the dense baseline
   to match 17M total?
2. MTP: keep it (v2 comparability) or drop it for a clean next-token
   baseline? MTP is 43 % of the v2 composite value.
3. Context: 256 (v2) or 512 (more compute, longer documents)?
4. LR schedule, warmup, batch size and dropout: inherit v2 (3e-4, 100, 64,
   0.1) unless a CPU-side argument changes it.
5. One run or two (MoE and dense control)? The task allows only after
   explicit approval.
6. Disk and checkpoint policy: one 100-150 MB artifact per run, state about
   400 MB, outside git.

## 7. Risks

- Data mix: 15.9 % synthetic Cosmopedia, 21.2 % Wikipedia with share-alike
  terms, 62.9 % web text. A single pooled score hides source-specific
  behavior.
- The 5 % Python-Edu gap is a documented deviation, not replaced.
- The corpus is 1.9 GB and the loader is deterministic, but no model has
  been trained on it; the first run is exploratory.
- The runtime estimates are extrapolations from one profiling run, not
  measured on this corpus.
- No model quality claim is made before a run.
