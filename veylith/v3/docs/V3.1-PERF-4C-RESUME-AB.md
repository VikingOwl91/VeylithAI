# v3.1-PERF-4C resumed-state paired A/B

Status 2026-10-27. Isolated experiment. Production files untouched.

**Decision: option 1, recommend production integration with an explicit safety
policy.** The prefill removal is bitwise inert across 150 resumed updates, it
reproduces the original v3.1-L trajectory exactly, and it buys 6.3 percent on
the update with no VRAM cost.

| metric | baseline (2 arms) | prefill off (2 arms) | delta |
|---|---:|---:|---:|
| median update | 784.8 ms | 735.7 ms | -49.1 ms (-6.26%) |
| trimmed mean | 785.8 ms | 733.0 ms | -52.8 ms (-6.72%) |
| CE targets/s | 41,490 | 44,388 | +6.99% |
| whole-arm wall | 155.1 s | 148.1 s | -7.0 s (-4.51%) |
| kernels/update | 40,978 | 30,426 | -10,552 (-25.7%) |
| device ms/update | 728.33 | 680.75 | -47.58 (-6.5%) |
| J per million CE targets | 7,834 | 7,577 | -3.28% |
| peak reserved | 5.598 GiB | 5.598 GiB | 0 |

The PERF-4B gain reproduced at 6.26 percent against 6.57 percent; it was not
assumed.

**0 mismatches**, including step 260, 300 and 400. The resumed run reproduces
the original 500-update run exactly, with step-400 CE

## 6. Safety assessment

Resumed training adds allocations the PERF-4B gate did not have: the 1.57 GB
state is loaded onto the device before priming, and the loader and scheduler
rebuild their state. Priming was therefore applied after the resume, covering
the update phase only.

Priming coverage, stated as before: 3.0 GiB of patterned bytes freed into the
caching allocator, against a 5.18 GiB peak allocation footprint. Not covered:
allocations made before priming (parameters, optimizer state, resume load), the
tail of the footprint beyond 3 GiB, fresh driver segments, hipBLASLt workspaces
and allocator metadata. A read of a region that both runs overwrite identically
would not be detected.

Remaining uninitialized-read risk: the invariance results are a strong negative
for these steps, not a proof. The failure mode the prefill guards against is
silent: instead of a loud NaN, a future code change that reads unwritten memory
would produce plausible garbage, and nothing in the training loop would flag it.
`torch.use_deterministic_algorithms(True)` remains on, so kernel-level
determinism and its operator checks are unaffected.

Diagnostic capability lost: the NaN prefill. Nothing else in the deterministic
mode changes.

Whether a debug/production split is justified: yes, and it is the condition of
the recommendation. The setting is a runtime flag, not a training config field,
so it does not enter the fingerprint and does not break resume compatibility
with existing states. A policy that keeps the capability without paying for it
in production:

1. Default prefill off for training runs, set in `train()` immediately after
   deterministic mode is enabled.
2. `VEYLITH_DETERMINISTIC_PREFILL=1` restores the current behaviour for
   debugging, new-operator bring-up and any investigation of a suspicious loss.
3. Record the effective value in the run's provenance (log line and artifact
   metadata) so a run can be classified after the fact.
4. Never disable it in tests that deliberately probe uninitialized memory, and
   re-enable it when adding an operator that allocates output it does not fully
   write.

This does not claim that bitwise identity proves memory safety. It claims that
for this model, these 150 resumed updates and the gated steps, no computed value
depends on uninitialized memory, and that the safety net stays available on
demand.

## 7. Decision

**Option 1: recommend production integration with the explicit safety policy
above.** Integration itself needs separate authorization; nothing here changes
production behaviour.

Rationale: the optimisation is bitwise inert over 150 resumed updates against a
non-zero optimizer state, it reproduces the original run's trajectory, it
removes a quarter of all kernel launches, and it returns 6.3 percent on the
update and 3.3 percent on energy per million CE targets with no VRAM cost.

## 8. Unknowns and limitations

- 150 updates from step 250 were exercised. Steps 1 to 250 and 401 to 500 were
  not re-run under this change, though the 251-400 window reproduces the
  original run.
- Only one resume point was tested. A resume from a different step, or one
  crossing an epoch boundary, could exercise different allocator and loader
  states.
- Priming covers at most 3.0 GiB of the 5.18 GiB footprint and none of the
  driver or library memory.
- The whole-run process CPU drop is unexplained in magnitude; the wall and
  energy results do not depend on it.
- `ckpt_best.pt` is never written with `stop_after < max_steps`, so artifact
  comparison beyond `best_state` was not possible.

## 9. Deviations

1. `log_every` was set to 1 for all arms (the fixture's config used 10) to get
   per-update records. It is a run-control field outside the fingerprint and is
   applied identically to all four arms; the validation and checkpoint schedules
   were left exactly as stored.
2. A per-arm `stop_after` of 400 was used so each arm runs 150 updates from the
   fixture.
3. No production file, checkpoint, architecture, precision, package or ROCm
   setting was changed.
