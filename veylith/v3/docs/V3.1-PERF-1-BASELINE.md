# v3.1-PERF-1 synchronized baseline and GPU profile

Status 2026-10-27. Stage 1 only: measurement, no optimization.

**Decision: Proceed to actual-shape BF16 GEMM comparison.**

The GPU is the critical resource: 95 to 96 percent busy during the measured
updates, 0.727 s of GPU kernel time per update against a 0.780 s update wall.
GEMM accounts for 33.7 percent of GPU time, with one library dispatch (Tensile
BF16) and eight concrete shapes. Attention is 4.8 percent with the efficient
backend already selected, and CPU/router overhead is bounded to the small
residual. The elementwise plus copy aggregate is larger (53.7 percent) but
memory-bound and outside the four Stage 2 options; it is recorded as the next
candidate after the GEMM comparison.

## 3. Timing methodology

- **Baseline** uses the unmodified production loop. The timer synchronizes
  once at the start and once at the end of each update, as in the v3.1-L
  post-fix code. No synchronizations inside forward, backward or the optimizer.
  `step_seconds` covers H2D copies, forward, backward, clipping and optimizer
  step; the outer data-loader window fetch happens before the start sync and is
  therefore excluded.
- **Instrumented traces** run in a separate harness that replicates the update,
  adds `record_function` annotations (`data_fetch`, `forward`, `backward`,
  `grad_clip`, `optimizer`, `update`), and profiles CPU plus GPU activity. Five
  unprofiled warmup updates precede five profiled updates per trace. Trace
  timings are reported separately and never blended into the baseline.
- **Data loader** was timed separately with the frozen loader and no model:
  ten warmup windows plus fifty measured windows of eight microbatches.
- **Energy** is integrated from 10 Hz PPT samples over windows whose start and
  end are recorded with the same monotonic clock as the training harness.

- Spread of the three medians: 0.0117 s, 1.5 percent. Repetition 1 is slowest;
  the telemetry is consistent with a first-run clock ramp, but that is a
  hypothesis, not a measurement.
- Pooled standard deviation 0.0184 s, inflated by one 0.992 s outlier in rep 1.
- Including the 13.7 ms loader window per update: 40,596 / 41,243 / 41,337
  CE targets/s per rep, 41,056 pooled.
- Full loop wall per update, measured from the curve clock: 0.8275 / 0.7993 /
  0.7961 s, i.e. roughly 0.02 to 0.05 s above `step_seconds` for data and
  Python overhead.
- Peak allocated 5.568 GiB, peak reserved 6.107 GiB, identical across
  repetitions and to v3.1-L.
- Process CPU time 224.4 / 217.1 / 216.0 s over 114.8 / 111.0 / 110.1 s wall,
  about 1.95 cores on average (the loop pins torch to one thread; the rest is
  loader, HIP runtime and evaluation).
- Loss falls from 9.1219 to 7.4074 over 60 updates; all losses and gradient
  norms finite; final mean top-2 assignment entropy 0.9824, no collapse.
- Checkpoint overhead: the production loop wrote one 1,573,847,593-byte state
  per repetition at step 60, after the last timing record. The wall after the
  step-60 record is 30.5 / 29.7 / 30.0 s and contains the final validation plus

  two to three seconds; the split between validation and write is derived, not

- Step-0 validation and training startup account for about 32.3 / 30.9 / 30.1 s
  before the first update (derived from the step-1 elapsed time minus one

- The v3.1-L median over updates 11 to 500 was 0.7452 s. This 50-update
  baseline is 4.7 percent slower. The cause is not established; the most
  plausible explanation is short-run clock and thermal state, since the
  telemetry shows the first repetition at lower clocks. This is a hypothesis,
  not a measurement.

## 8. Kernel dispatch evidence

**GEMM.** `aten::mm` is the only matmul primitive observed (42,200 calls per
trace, 5,064 per update; `aten::linear` and `aten::matmul` are composites).
Every GEMM kernel name begins with `Cijk_..._BBS_BH_Bias_HA_S_SAV_UserArgs`,
i.e. Tensile/rocBLAS BF16 kernels, with tile configurations `MT64x64x32`,
`MT64x64x64`, `MT128x128x32`, `MT64x32x32` and `MT32x64x32`. No hipBLASLt
kernel names appear in either trace.

Actual shapes, from trace 2 (calls and milliseconds per update):

| shape (M x K @ K x N) | calls | ms/update |
|---|---:|---:|
| 4088 x 512 @ 512 x 960 (expert w1/w2) | 1,792 | 72.2 |
| 4088 x 960 @ 960 x 512 (expert w3 and backward) | 2,240 | 61.0 |
| 960 x 4088 @ 4088 x 512 (weight gradients) | 1,792 | 47.1 |
| 512 x 4088 @ 4088 x 960 | 896 | 23.4 |
| 4088 x 512 @ 512 x 512 (attention projections) | 384 | 9.7 |
| 8192 x 4088 @ 4088 x 512 (LM head) | 16 | 6.4 |
| 512 x 4088 @ 4088 x 512 | 256 | 4.8 |
| 128 x 4088 @ 4088 x 512 | 256 | 4.1 |

**SDPA.** The dispatcher path is visible: `aten::scaled_dot_product_attention`
calls `aten::_scaled_dot_product_efficient_attention`, which runs
`aten::_efficient_attention_forward` and, in backward,
`aten::_efficient_attention_backward` with kernels `bwd_kernel_dk_dv.kd` and
`bwd_kernel_dq.kd`. This is the **efficient attention** backend on ROCm. There
is no flash-attention kernel and no math fallback: the only softmax kernels are
`c10d`-style `SoftMaxForwardReg`/`SoftMaxBackwardSmem` from the cross-entropy
loss (`aten::_log_softmax`), not from attention. Measured attention cost is
34.8 ms per update, 4.8 percent of GPU time.

**Optimizer.** AdamW runs through `Optimizer.step#AdamW.step` and
`multi_tensor_apply_kernel` variants, 19.3 ms per update (2.6 percent).

- Whole experiment: 85,186 J of GPU package energy over 594.8 s, mean 143 W
  including idle, validation and CPU-only periods.
- Baseline measured windows, aligned to the run clock: mean 276.6 W, sclk
  3.21 GHz, busy 95 to 96 percent. Per repetition **6,668 / 6,790 / 6,789
  J per million CE targets**, pooled **6,749**.
- Unprofiled warmup windows in the traces (2.6 GHz, clock ramp): 5,907 J/M.
- Profiled windows (3.2 GHz plus profiler CPU overhead): 7,897 to 8,051 J/M.

The baseline alignment uses the run's own elapsed clock and the JSON write
time; it carries about one to two seconds of boundary uncertainty (2 to 5

whole-system wall power was not measured and no wall-power figure is claimed.

## 11. Top three measured bottlenecks

1. **Memory-bound elementwise work: 309 ms per update, 42.5 percent of GPU
   time, 26,230 kernels per update.** Dominated by fp32 gradient accumulation
   (71.3 ms), bf16 expert-weight multiplies (36.7 ms), fp32 binary elementwise
   (32.8 ms) and manual-unroll kernels (27.5 ms). This is measured GPU time,
   not inference.
2. **BF16 GEMM: 245 ms per update, 33.7 percent, 5,064 launches.** All through
   Tensile at shapes M=4088, N/K of 512 and 960. This is the largest single
   library-dispatched category and the one Stage 2 can compare directly.
3. **Copies and dtype conversions: 82 ms per update, 11.2 percent, 7,181
   kernels.** The two largest are bf16 copy (35.4 ms) and bf16 to fp32
   conversion (27.4 ms), i.e. the autocast/master-weight boundary.

Attention (34.8 ms, 4.8 percent) and the optimizer (19.3 ms, 2.6 percent) are
not bottlenecks at this configuration.

## 12. Measured, derived, hypothesis, unknown

**Measured:** baseline update distributions and CE throughput; peak VRAM;
loader time; GPU kernel time and category sums from five profiled updates;
kernel launch counts; GEMM and SDPA dispatch names and shapes; PPT power,
clocks and busy percent; KFD process list; reproduction of v3.1-L step-1 loss
and gradients.

**Derived:** throughput including the loader; J per million CE targets for the
baseline windows (clock alignment); GPU-busy estimate from the sampler and the
wall/kernel ratio; per-phase GPU split (correlation-based attribution, zero
unmapped kernels).

**Hypothesis:** the 4.7 percent gap between this short baseline (0.7804 s) and
the historical long-run median (0.7452 s) is a short-run clock and thermal
effect. The uninstrumented CPU launch cost is a fraction of the profiled
0.237 s per update and is overlapped with GPU work.

**Unknown:** the exact uninstrumented CPU and launch overhead; the per-update
energy at fully stabilized clocks outside the profiled runs; whole-system wall
power; whether a different GEMM library or tile selection is faster at these
shapes (that is Stage 2).

## 13. Recommended Stage 2

**Actual-shape BF16 GEMM comparison.** Benchmark the eight measured shapes
(M=4088; N,K in {512, 960}; plus the 8192x4088 LM head) on this GPU with the
installed libraries only, comparing the current Tensile dispatch against any
available alternative backend without changing the model. Success criterion: a
reproducible per-shape speedup that, applied to the measured 245 ms per update,
would move end-to-end throughput by more than 2 percent.

If Stage 2 shows no GEMM headroom, the measured elementwise plus copy aggregate
(53.7 percent) is the next target: fuse the fp32 gradient accumulation and the
bf16 expert-weight multiply, and reduce the bf16 to fp32 conversions. That is
outside the four Stage 1 decision options and is recorded as a follow-up, not
as a Stage 2 authorization.
