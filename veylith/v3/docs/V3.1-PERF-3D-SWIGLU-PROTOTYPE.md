# v3.1-PERF-3D SwiGLU forward fusion prototype

Status 2026-10-27. Bounded experiment, isolated module, no production change.

**Decision: reject (option 3, insufficient performance benefit).**

The prototype is numerically faithful: the fused forward and the untouched
ATen backward are bitwise identical to the baseline, and a two-update matched
run reproduces logits, losses, router assignments, gradients, weights and
optimizer state exactly. It also does what PERF-3C predicted on the device:
the SwiGLU cluster falls from 57.6 to 52.3 ms and launch count falls by 456 per
update.

It still does not make the update faster. Measured on 40 non-profiled updates
per arm, the update is **5.7 ms slower at the median** (758.9 to 764.6 ms) and
**6.6 ms slower on trimmed means** (759.3 to 766.0 ms), because the new call
path costs **+12.1 ms of CPU per update** (+26.5 us per fused call) while the
device work only shrinks by 5.3 ms. One Triton launch, two explicit
allocations and a custom `autograd.Function` cost more on the critical path
than the two ATen dispatches they replace.

That is a net throughput loss of about 0.9 percent, not a gain.

## 2. Implementation

`veylith/v3/perf/v31p3d_swiglu.py`:

- `_silu_mul_kernel`: one Triton kernel, `BLOCK=1024`, computing
  `t = BF16(FP32(a) / (1 + exp(-FP32(a))))`, storing `t`, then
  `y = BF16(FP32(t) * FP32(b))`. The intermediate rounding is explicit, so the
  multiply reads the BF16 `t` exactly as the two-kernel baseline does.
- `FusedSiluMul`: saves `a`, `t`, `b`; backward calls `torch.mul(grad, b)`,
  `torch.mul(grad, t)` and `aten::silu_backward(g_t, a)`, unchanged in dtype and
  order.
- `apply_variant`: instance-level replacement of `SwiGLU.forward`, 57 modules.

57 is the true module count: one dense FFN at width 1365 plus 7 MoE layers with
8 experts at width 960. With 8 micro-batches that is **456 calls per update**,
not the 448 used in PERF-3A and PERF-3C; the dense-width module was missed
there. The measured launch delta is correspondingly -456, not -448.

### Two defects in my first implementation, both fixed before the reported numbers

1. **Deterministic NaN prefill.** `torch.use_deterministic_algorithms(True)`
   sets `fill_uninitialized_memory`, so each `empty_like` also enqueued a full
   device fill. That added 912 `[4088,960]` fills per update and 6.67 ms of GPU
   time, which is larger than the fusion saves. Proven on device
   (deterministic off: 0 fills; on: 2 per call; flag off: 0) and fixed with a
   scoped save/restore around the two allocations. Every element of both
   buffers is written by the kernel, so the prefill was unobservable. Gate 1
   now asserts the flag is restored.
2. **Sync storm in my harness.** Per micro-batch `float(...)` conversions and
   `router.detach().cpu()` forced 88 queue drains per update, inflating wall time
   from 0.78 s to 1.28 s. Checks and the router digest are now batched into one
   synchronization per update. After the fix the non-profiled update is 759 ms,
   consistent with PERF-1's 780 ms.

Both gates were re-run after these fixes. Nothing below predates them.

Nine cases plus backward, all compared on raw bit patterns (`int16` view):

| case | shape | t bitwise | y bitwise | max abs diff |
|---|---|---|---|---|
| production | (4088, 960) | yes | yes | 0.0 |
| single row | (1, 960) | yes | yes | 0.0 |
| irregular | (17, 960) | yes | yes | 0.0 |
| odd tail | (4097, 961) | yes | yes | 0.0 |
| zeros | (4088, 960) | yes | yes | 0.0 |
| +50 | (4088, 960) | yes | yes | 0.0 |
| -50 | (4088, 960) | yes | yes | 0.0 |
| 1e-30 | (4088, 960) | yes | yes | 0.0 |
| BF16 boundary | (4088, 960) | yes | yes | 0.0 |

Backward on (4088, 960) with deterministic upstream gradients: `y`, `g_a` and
`g_b` bitwise identical, max abs diff 0.0 for both gradients. Rejections are
explicit rather than silent copies: non-contiguous raises
`requires contiguous inputs`, float32 raises `requires bfloat16 inputs`, CPU
tensors raise `requires CUDA/HIP tensors`.

Triton's `tl.exp` and `tl.div_rn` on gfx1201 reproduce ATen's silu exactly on
all nine cases, including both saturation directions. The numerical unknown
that PERF-3C isolated is closed for this shape set and dtype.

## 5. Gate 3: performance

### 5.1 Kernel attribution (profiled, 4 interleaved runs, 8 updates each)

Order `a0 (base), a1 (fused), b1 (fused), b0 (base)` cancels linear drift.
Milliseconds per update, kernel events only:

| run | variant | kernels/up | total | GEMM | fwd silu | fwd mul | fused | bwd mul | silu bwd | cluster |
|---|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| a0 | base | 40,984 | 716.01 | 246.27 | 7.00 | 9.78 | - | 26.72 | 14.28 | 57.78 |
| a1 | fused | 40,528 | 711.31 | 245.87 | - | - | 11.83 | 26.72 | 13.66 | 52.22 |
| b1 | fused | 40,528 | 715.26 | 246.65 | - | - | 11.97 | 26.74 | 13.70 | 52.41 |
| b0 | base | 40,984 | 713.44 | 244.35 | 6.89 | 9.49 | - | 26.74 | 14.25 | 57.37 |

- Launches: 40,984 to 40,528, exactly -456 (-1.11 percent), one per call.
- SwiGLU cluster: 57.78 to 52.22 and 57.37 to 52.41, so **-5.56 and -4.96 ms**
  (about -9 percent of the cluster). The spread across the two baseline runs is
  0.41 ms, so this delta is solid.
- Forward cost per call: 36.8 to 25.9 us, about -29 percent. The fused kernel
  (11.8 ms) is cheaper than silu plus the forward mul (16.8 ms), as designed.
- Backward mul is unchanged to the hundredth of a millisecond (26.72 vs 26.72).
- `silu_backward` measures 0.55 to 0.62 ms faster although the op, shapes and
  dtypes are identical. That is a buffer-address effect from the changed
  allocation history, not fusion merit, and I do not claim it.
- Total device time: -4.70 ms in pair a and +1.82 ms in pair b. Non-cluster
  families drift by +0.9 and +6.8 ms between pairs (GEMM, FP32 adds, BF16
  copies, fills), so the total is not separable from run-to-run drift at this
  resolution. Only the cluster delta is.

Peak memory: 5.590 GiB reserved in all eight runs; peak allocated 5.193 GiB
(baseline) versus 5.201 GiB (variant), the two 7.85 MB buffers.

### 5.2 End-to-end update (non-profiled, 20 updates per run, 4 interleaved runs)

Profiled wall time is not usable here: recording 41k kernels per update with
shapes costs about 13 us of CPU per kernel, so wall time sits at 1.27 to 1.36 s
over 712 ms of device work regardless of variant. The paired numbers come from a
profiler-free mode.

| run | variant | median update | mean | p10 | p90 |
|---|---|---:|---:|---:|---:|
| t0 | base | 757.4 ms | 776.3 | 756.2 | 824.3 |
| t1 | fused | 764.5 ms | 764.5 | 756.6 | 771.1 |
| t2 | fused | 765.1 ms | 771.9 | 762.2 | 815.7 |
| t3 | base | 760.6 ms | 760.4 | 757.2 | 763.6 |
| combined | base (n=40) | 758.9 ms | 768.4 | | |
| combined | fused (n=40) | 764.6 ms | 768.2 | | |

Trimmed means (two outliers removed per arm): **759.3 versus 766.0 ms, +6.63 ms,
+0.87 percent**. Median-based throughput: **43,073 versus 42,697 CE targets/s**.

Both baseline runs are faster than both variant runs, and the CPU accounting
below explains it, so this is not ordering noise.

### 5.3 CPU accounting

Per-update `process_time`, same runs:

| arm | CPU per update | CPU per fused call | queue-drain count |
|---|---:|---:|---:|
| baseline | 1,506.3 ms | 11.7 us (silu + mul) | 1 per update |
| fused | 1,518.4 ms | 43.4 us per call in isolation | 1 per update |

**+12.1 ms per update, +26.5 us per call.** Isolated launch-cost microbenchmark
(7 interleaved rounds, medians, no synchronization inside the timed loop):

| path | us per call |
|---|---:|
| `F.silu(a); t * b` (two ATen calls, two allocations) | 10.60 |
| Triton launch only (no allocation, no Function) | 17.56 |
| flag toggle only | 0.60 |
| allocations plus Triton launch | 29.48 |
| plus `autograd.Function` wrapper | 43.43 |
| fills still enabled (deterministic prefill, untoggled) | 38.85 |

A single Triton Python launch already costs more than the two ATen dispatches
it replaces, and each explicit allocation is a separate Python-level dispatch.
The `autograd.Function` wrapper adds about 14 us. This is where the 5.3 ms of
device savings goes.

### 5.4 Power

The sampler covered whole run windows, including CPU-bound trace export, so it
cannot resolve update-level energy: mean 97.8 to 103.8 W, peak 266 to 272 W,
clocks 1.94 to 1.97 GHz mean. Reported as context only, not as a comparison.

## 6. Why the update did not get faster

The chain is fully accounted for:

1. Device: fused forward replaces silu plus the forward mul, -4.7 ms per update.
2. Device: backward mul unchanged, `silu_backward` -0.6 ms from allocation
   layout, total cluster -5.3 ms.
3. Host: the same change adds 12.1 ms of CPU on the critical path, because the
   fused call is three Python-level dispatches plus an autograd wrapper where
   the baseline is two dispatches.
4. Net: about +6 ms per update, -0.9 percent throughput.

A faster launch path could in principle surface the 5.3 ms, but that is a
different change (CUDA graph capture, a C++ extension, or a compiled kernel),
it adds infrastructure this training loop does not have, and the ceiling is
0.7 percent of device time. The larger clusters stay untouched: FP32 residual
adds 72.5 ms, BF16 copies 34.5 ms, dtype casts 26.8 ms, BF16 fills 18 ms.

## 7. Decision

**Reject. Insufficient performance benefit.** Numerically the prototype is
exactly what PERF-3C specified, and the device saving is real and reproducible.
It is 0.7 percent of device time, it does not survive the host-side cost it
introduces, and productionizing it would mean carrying a hand-written Triton
kernel, a runtime model patch and a workaround for PyTorch's deterministic
allocation prefill, for a measured net loss.

I do not recommend a paired A/B training experiment. A long run would measure
the same +0.9 percent regression with more GPU hours.

## 8. Unknowns and risks

- Whether a lower-overhead launch (graph capture, C++ extension, Inductor)
  would convert the 5.3 ms device saving into wall time is untested. It would
  need its own bitwise gate and its own perf gate.
- The +12.1 ms host cost is measured as a total. The decomposition in 5.3 comes
  from a microbenchmark with order effects of a few us, so the split between
  allocations, launcher and autograd wrapper is indicative.
- `silu_backward`'s 0.6 ms improvement from allocation layout is unexplained in
  detail and may not reproduce with different allocation histories.
- Strategy B/C (fused backward) remain unmeasured and still have no bitwise
  argument. Nothing here supports revisiting them.
- The deterministic-fill suppression is safe only because the kernel writes
  every element. Any future kernel with masked or partial stores must not use
  this pattern.

## 9. Deviations

1. Added the deterministic-fill suppression after measuring its cost; gated
   again afterwards.
2. Reworked the harness to one synchronization per update, because the first
   version's wall time was unusable.
3. Added a non-profiled timing mode; the profiled wall time is not comparable to
   PERF-1 and was not used for the end-to-end claim.
4. Used four interleaved profile runs instead of one pair, because a single
   pair cannot separate a 5 ms effect from drift.
5. Corrected the call count from 448 to 456.
6. No gate was relaxed, no tolerance substituted, and no production file,
   checkpoint or environment setting was changed.
