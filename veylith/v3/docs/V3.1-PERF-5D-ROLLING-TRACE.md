# v3.1-PERF-5D rolling trace and boundary attribution

Status 2026-10-27. One bounded GPU execution. No production change, no
serialization, no backend switch, no reset, no retry.

**Outcome: strong operation-level correlation, consumer favoured over the GEMM.**
The rolling profiler preserved 57 one-iteration traces across the fault. Every
traced iteration ends with the same three kernels (`silu_backward` -> GEMM ->
bf16-to-fp32 cast), the fault page is again exactly the end of a 682 x 3075 bf16
GEMM output with 4 bytes of slack, and the kernel log reports a read. A consumer
of that GEMM output is therefore better supported than the GEMM itself. The
faulting kernel is still not named, and the faulting iteration's own trace is not
provably among the exports.

## 2. CPU-only preparation

### 2.1 Harness

`veylith/v3/perf/v31p5d_rolling.py` wraps the established reproducer without
touching it:

- `torch.profiler` with CPU+CUDA activity, `record_shapes=False`, no stacks.
- One profiler cycle per iteration: the step boundary is the reproducer's own
  `sparse_moe_v2_train.get_batch`, patched to call `prof.step()` **before** the
  fetch. That is the one call that runs at the top of every iteration, and the
  historical fault surfaces at the fetch itself, so the previous iteration is
  exported just before the failing copy.
- `on_trace_ready` publishes each cycle to `trace-cycle-NNNN.json` via a
  temporary file and `os.replace`, so no reader sees a partial trace and no
  cycle overwrites another.
- Metadata carries the cycle number, the covered iteration and the byte size.
- No synchronization is added for logging, no `AMD_SERIALIZE_KERNEL`, no backend
  change, no package change.

**Deviation from the suggested schedule:** this build rejects
`repeat=-1` (`AssertionError: ... repeat=-1 (need >= 0)`). `repeat=0` is the
infinite repeat here, so the schedule is `wait=0, warmup=0, active=1, repeat=0`,
which also removes the wait/warmup gaps that would have skipped the faulting
iteration.

### 2.2 Lifecycle verification (CPU only)

`--mode selftest` runs three CPU steps with the same schedule and exporter:

```
cycles 4, published 4, all_nonempty True, covered iterations [0, 1, 2, 2]
```

Four files appeared, each non-empty and uniquely named; the fourth is the flush
cycle produced when the profiler context closes, covering the last iteration
again. That confirms cycle firing, atomic publication and metadata before any GPU
use.

## 5. Tail ordering

Across the 56 full iterations, the last three kernels are:

| pattern | count |
|---|---:|
| `aten::silu_backward` -> `aten::mm` (GEMM) -> `aten::copy_` (bf16 to fp32 cast) | 46 |
| `aten::add` -> `aten::mul` -> `aten::add` | 10 |

The last full trace ends with:

```
E:aten::mul            elementwise (routing weight)
G:aten::mm             Cijk_Ailk_Bjlk_..._MT64x64x64_...   49.0 us
E:aten::copy_          bfloat16tofloat32_copy_kernel        2.8 us
```

So a normal iteration closes with a GEMM followed by exactly one kernel: a
**bf16-to-fp32 cast** (`at::native::bfloat16tofloat32_copy_kernel`, launched by
`aten::copy_`), which reads the GEMM's bf16 output. The 10 `add/mul/add` tails
contain no GEMM in their last three kernels and look like traces cut mid
iteration; they are reported but not used as evidence.

## 6. Buffer-boundary evidence

The fault page was matched against every hipBLASLt call's C pointer and extent in
the same run's log (23,044 parsed calls):

| item | value |
|---|---|
| fault page | `0x7fd7b5400000` |
| nearest C buffer | `0x7fd7b5000000` |
| extent | 4,194,300 bytes = 682 x 3075 x 2 |
| tensor end | `0x7fd7b53ffffc` |
| gap to fault page | **4 bytes**, i.e. the page starts exactly at the 4 MiB block end |
| last hipBLASLt call in the log | C `0x7fd815da4800`, 256 x 682 (the call after the boundary one) |

This is the third independent reproduction of the same geometry (PERF-5C
baseline, PERF-5C attribution, PERF-5D), each time with a different absolute
address and the same 4-byte gap.

## 7. Verdict

**Evidence level 2 of 4: strong operation-level correlation.** Not direct kernel
attribution: the trace carries no pointers or shapes, so no kernel can be tied to
`0x7fd7b5400000` itself.

- A **consumer** of the boundary buffer is better supported than the GEMM:
  - the fault is a read (kernel log `RW: 0x0`), and the GEMM writes that buffer;
  - the only kernel after the last GEMM in 46 of 56 traced iterations is a
    bf16-to-fp32 cast, which reads exactly that kind of bf16 GEMM output;
  - the boundary buffer is a bf16 GEMM output whose tensor end is 4 bytes short
    of the mapping end, which is the shape of a tail read crossing a page.
- The **GEMM itself** remains a weaker candidate: it would require a write fault,
  which the recorded `RW` flag does not support, and the fault page is 4 bytes
  past the tensor rather than inside it.
- **Candidate kernel family:** `bfloat16tofloat32_copy_kernel` (or a comparable
  vectorized elementwise reader) launched by `aten::copy_`; second, the routing
  weight multiply (`aten::mul`) that precedes it; third, the GEMM epilogue.
- The **historical 16E/top-4 K-tail hypothesis** is not supported or refuted
  here; this is an 8E/top-2 run whose last GEMM has a full N tile in the traced
  orientation.

## 8. Remaining uncertainty

- The faulting iteration's own trace is **not provably** among the 57 exports.
  With the step boundary at the fetch, the exported cycle at the moment of the
  abort covers the iteration that completed, and the abort happened in a worker
  thread during the next one. The fault may be in the covered iteration (its tail
  kernels) or in the lost one; the tail evidence is consistent in either case,
  but the classification stays at "strong correlation" rather than "identified".
- No shapes or pointers in the kernel events: the cast is the only kernel after
  the GEMM, but "the cast that read this exact buffer" is inferred from shape
  class and ordering, not observed.
- Per-cycle metadata was lost to the abort in this run; coverage is reconstructed
  from trace sizes.
- A vectorized cast is expected to mask its tail; why it would read past a page
  remains unproven, and the alternative (an unmasked epilogue store or a
  misreported `RW`) cannot be excluded without the kernel name.

## 9. Recommended next bounded experiment

One run, still no serialization:

1. Same rolling schedule and exporter, now with `record_shapes=True` so each
   `aten` event carries the tensor shapes; that lets the analysis distinguish the
   cast of a 682 x 3075 bf16 tensor from casts of other tensors by shape alone.
2. Add a hook that records, per iteration, the last `aten::copy_` input shape and
   stride set, so the boundary buffer's consumer can be named by shape.
3. Keep the address match as the independent cross-check, and keep the
   `cycles.jsonl` metadata append (already hardened) so coverage is recorded
   rather than reconstructed.

Success: an `aten::copy_` (or the GEMM) event whose input shape and ordering place
it at the boundary buffer in the last covered iteration, promoting the finding
from "strong correlation" to "direct attribution".
