# v3.1-PERF-5B hipBLASLt K-tail isolation

Status 2026-10-27. Bounded GPU diagnostic. No production change, no sparse
rollout, no checkpoint touched.

**Decision: option 2, fault reproduced with kernel attribution unresolved.**

The historical fault still reproduces on this environment, and this run captured
its kernel-log signature for the first time: a 2 MiB-aligned page fault from the
TCP client, permission fault, read flag clear, no GPU reset. The single-GEMM
form of the K-tail hypothesis is **not supported**: a call whose hipBLASLt
descriptors match the archived 16-expert capture exactly, with B ending 16 bytes
before a 6 MiB buffer end, completes cleanly. The mechanism is therefore not
confirmed and no mitigation should be derived from this evidence.

## 2. CPU-only preparation

### 2.1 Descriptors reconstructed

The archived 16E/top-4 capture shows `transA=N transB=T`, `Adesc rows=256
cols=4108 ld=256`, `Bdesc rows=682 cols=4108 ld=682`, `Cdesc rows=256 cols=682
ld=256`, bf16 in and out, `COMPUTE_32F`, alpha 1, beta 0, workspace 79,691,776
bytes.

From ATen's semantics that is not `mm(A_mk, B_nk.t())` with row-major inputs;
that call makes hipBLASLt compute the transposed problem with the 682-row
operand as A. The archived form is obtained when the 682-row controlled operand
is PyTorch's first argument:

```
C = torch.mm(b_operand_682x4108, a_operand_mk.t())    # "boundary-first"
```

Its descriptors were verified against the live log and match the archive:

```
Adesc=[type=R_16BF rows=256 cols=4108 ld=256] transA=OP_N
Bdesc=[type=R_16BF rows=682 cols=4108 ld=682] transB=OP_T
Cdesc=[type=R_16BF rows=256 cols=682 ld=256]
computeType=COMPUTE_32F alpha=1 beta=0 workSpaceSizeInBytes=79691776
```

The earlier `m-first` orientation does **not** match: there hipBLASLt receives
`Adesc rows=682`, `Bdesc rows=256`, so the kernel sees N=256 (mod 64 = 0) and
the controlled buffer is the bounds-checked A operand. That case is reported
below as uninformative rather than as evidence.

### 2.2 Boundary arithmetic

`2*(64 - N mod 64) = 44` bytes for N=682, K=4108 (`N mod 64 = 42`,
`K mod 64 = 12`). B occupies 5,603,312 bytes; the buffer is a whole 2 MiB
multiple (6,291,456) and B is placed at offset 688,128 (512-byte aligned) so that the
trailing slack is exactly **16 bytes**, matching the archived capture. The generous placement
leaves 688,144 bytes. For N=640 and K=4160 the model predicts zero over-read.

### 2.3 Attribution feasibility

`HIPBLASLT_LOG_MASK=10` with `HIPBLASLT_LOG_FILE` produces Trace lines with
descriptors and pointers in this build, but **no `sol-idx` lines**: the archived
solution identification relied on a newer hipBLASLt. Solution-level attribution
is therefore not available here, and a fault could not be tied to solution
107018 even if it had occurred.

### 2.4 Harness

`veylith/v3/perf/v31p5b_gemm_tail.py` builds one controlled GEMM in a fresh
process: warm the backend so the 76 MB workspace is allocated first, allocate
the operands, then allocate the controlled buffer **last** so nothing else is
placed after it, fill B, and run one or two GEMMs with a preallocated output.
`veylith/v3/perf/v31p5b_plan.py` runs the matrix with one process per case,
`ulimit -c 0`, a 120 s timeout, idle gates, per-case logs, a 3 s settle, and no
retries.

## 4. Kernel attribution

For case 6 the geometry is fully attributed at the descriptor level: A 256x4108
ld 256 (`OP_N`), B 682x4108 ld 682 (`OP_T`), C 256x682 ld 256, `COMPUTE_32F`,
workspace 79,691,776 B, and the controlled buffer is the kernel's B operand
(with `b_ptr` equal to the logged B pointer and 16 bytes of slack). It ran
clean, so there is no fault address and the predicted-versus-observed boundary
comparison is vacuous.

For case 5, the faulting process left a kernel-log record:

```
[gfxhub] page fault (src_id:0 ring:24 vmid:8 pasid:4619)
  Process python pid 2041819 ... in page starting at address 0x00007f5b88000000
GCVM_L2_PROTECTION_FAULT_STATUS:0x00801031
  Faulty UTCL2 client ID: TCP (0x8)
  PERMISSION_FAULTS: 0x3   MAPPING_ERROR: 0x0   RW: 0x0
```

- 4 page-fault records, all at `0x00007f5b88000000`, **2 MiB aligned**.
- Client TCP, permission fault, read/write flag 0. This is a *load* fault
  through the texture/global path, not an obvious scatter write.
- No reset line; `rocm-smi` responsive; no KFD process afterwards.

What is **not** available: the faulting kernel name (the runtime printed no HSA
fault block with `kernel: ...` in either the process stderr or the kernel log)
and the hipBLASLt solution (no `sol-idx` lines in this build). Attribution stops
at "a TCP-client global read at a 2 MiB-aligned unmapped page inside the
faulting python process".

## 5. The reproduced fault differs in manifestation from the historical one

Historically the same reproducer exited **134 / SIGABRT** with no traceback. Today
the same script, same iteration (last printed 25), faults the same way at the
same point but surfaces as a Python-visible `torch.AcceleratorError: CUDA error:
an illegal memory access was encountered` at the *next* H2D copy in `get_batch`,
exiting **1**. The asynchronous surfacing matches the v2 op-level traces exactly
(the traced iteration's backward completed; the fault appeared at the following
`get_batch` copy).

Consequence for method: classifying these faults by exit code alone undercounts
them. This stage's first classifier missed the positive control for exactly that
reason; it was corrected to treat `illegal memory access` /
`hipErrorIllegalAddress` / `AcceleratorError` as a fault, and the stored record
was re-derived from stderr rather than re-run.

## 6. What the faulting run actually dispatches

The positive control's own hipBLASLt log (23,091 parsed calls, 6,430 distinct
(M, N, K)) gives the shape set that the failing 8-expert/top-2 configuration
uses:

| dimension | values (calls) |
|---|---|
| K | 256 (10,304), 682 (6,006), 64 (376), 32 (530), 8 (188), 1000 (47) |
| N | 16384 (4,287), 682 (3,760), 256 (3,128), 4790 (30), 4233 (27), 32 (188) |

- **8,914 of 23,091 calls (38.6 percent)** satisfy the model's over-read
  precondition (`N mod 64 != 0` and `K mod 64 != 0`), including N=4233 and
  N=4790, which are routed-token counts produced by variable-size routing.
- **Zero calls** use the archived 16E geometry (M,N,K = 256,682,4108 or its
  transpose).

So the archive's single-GEMM geometry is *not* what the reproducing configuration
executes. The hypothesis is not contradicted by case 6; case 6 tests a shape the
failing run never issues.

## 7. Interpretation

| outcome class | verdict |
|---|---|
| Direct confirmation of a boundary-sensitive over-read | not obtained |
| Evidence for a hipBLASLt-specific failure | none direct; the TCP client is a shared load path, not a library identifier |
| Failure reproduced without kernel attribution | **yes**, case 5 |
| Clean synthetic test with positive model reproducer | **yes**, case 6 with case 5 as control |
| Environment drift | excluded: the reproducer still faults and the drift guard is clean |

The mechanism is not confirmed. Case 6 is a genuine negative for "a single bf16
GEMM at the archived geometry with 16 bytes of slack faults on this build", but
it cannot refute the over-read hypothesis, because (a) solution selection is
unknown and cannot be verified in this build, and (b) whether the page behind the
controlled buffer was unmapped is not observable from user space. A real
over-read landing in mapped neighbouring VA would produce exactly this clean
result.

## 8. The rocBLAS arm is not a clean control

The brief asks for a rocBLAS comparison once the positive case is established, so
the last execution ran the same reproducer with
`torch.backends.cuda.preferred_blas_library("hipblas")` (the rocBLAS backend in
this build; `"rocblas"` is not a valid value and caused the failed attempt 7).
It also faults, at the same iteration, but it cannot be read as "the fault is not
hipBLASLt-specific".

`ROCBLAS_LAYER=9` shows why: of the GEMMs in that run, **23,091 were routed by
rocBLAS to `rocblas_gemm_hipblaslt_backend`**, alongside 21,655
`rocblas_gemm_ex` records. rocBLAS delegates most calls back to hipBLASLt, so the
arm still exercised hipBLASLt kernels. It separates the PyTorch-to-library route
(for example, workspace and descriptor management) from nothing else, and this
build offers no way to force a rocBLAS-only Tensile path from that API.

The executed yet unused probe would have been the geometry the failing run
actually issues (variable N near 4233/4790, K=682), but a single GEMM in a fresh
process also lacks the failing run's allocation history, which is what decides
whether an over-read meets an unmapped page; the brief forbids a spacer sweep.
The budget is therefore fully spent at 8 of 8.

## 9. Final decision

**Option 2: fault reproduced, kernel attribution unresolved.**

- The historical fault reproduces with its signature intact (2 MiB-aligned TCP
  permission fault, no reset, same reproducer, same iteration, same asynchronous
  surfacing).
- Attribution stops at the client class; neither the kernel name nor the
  hipBLASLt solution is available in this environment.
- The single-GEMM form of the hypothesis is not supported, and the rocBLAS arm
  is not a discriminator because rocBLAS delegates to hipBLASLt. Option 1 is not
  warranted and no mitigation should be designed from this result.
- Option 3 is not warranted either: case 6 does not exercise the failing
  configuration's geometry and leaves the solution unverified.

A next stage, if authorized, should capture attribution rather than more shapes:
run the model reproducer with a tracer that records the dispatch immediately
preceding the fault (`rocprofv3` cannot finalize after a fault; the archive's
attempt hung), or use the runtime's HSA fault block if a build prints it, and
first establish whether this build's hipBLASLt can report solution indices at
all.

## 10. Limits and deviations

- Solution attribution was planned and found unavailable in this build; this was
  discovered from the first log, not assumed.
- The synthetic buffer's base was not 2 MiB-aligned (`end_2mib_aligned: false`
  in the prep record), so the synthetic mapping end is not a 2 MiB boundary; the
  reproduced fault, by contrast, was exactly 2 MiB-aligned.
- Case 4 was wasted on the wrong orientation. Its descriptors showed the
  mismatch, the corrected call was designed from them, and case 4 is recorded as
  uninformative rather than dropped.
- The classifier fix (accepting HIP illegal-address errors) re-derives the stored
  record from stderr; the faulting case was not re-run.
- Attempt 7 burned one execution on an invalid backend name before any kernel
  ran; it is recorded as a failed attempt, and the corrected arm became
  execution 8.
- No production file, checkpoint, package or ROCm setting changed; no GPU reset;
  no retry; no push.
