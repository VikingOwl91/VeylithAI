change, no package change, no reset, no retry, no serialization, no push.

## 2. Implementation

`torch.mul(..., out=)` refuses differentiable inputs, which the CPU gate
confirms: `direct_out_rejected_outside_function: true`. Inside an autograd
`Function` the inner ops run with autograd recording off, so the multiplication
can write straight into the padded view.

```python
class PaddedMul(torch.autograd.Function):
    @staticmethod
    def forward(ctx, a, b):
        ctx.save_for_backward(a, b)
        out = padded_like(a)          # same shape, contiguous, offset 0, +64 KiB
        torch.mul(a, b, out=out)      # no post-multiplication copy
        return out
    @staticmethod
    def backward(ctx, grad_output):
        a, b = ctx.saved_tensors
        return grad_output * b, grad_output * a
```

`SwiGLU.forward` is replaced per instance, so the module tree, the parameters and
the initialization path are unchanged:

```python
return self.drop(self.w3(PaddedMul.apply(F.silu(self.w1(x)), self.w2(x))))
```

Only the product's storage changes. The `w3` linear stays stock, so the PERF-5I
intervention (padding the `w3` input gradient) is not applied in this arm.

Graph change: the `MulBackward` node is replaced by `PaddedMulBackward`, and the
product's storage is allocated by the harness instead of by ATen. The gradients
are the same elementwise products.

### D, fault attribution

There was no fault, so there is no page to attribute. What the run does establish
about the operand class that faulted in 5I:

| read class, last byte within 64 B of a 2 MiB boundary | count |
|---|---|
| stock operand, tail 0 (end exactly on the boundary) | 4,038, no fault |
| stock operand, tail 4 (straddling class, the 5I geometry) | 1, no fault |
| padded product, tail 4 | 1, no fault |
| padded product, tail 8 | 1, no fault |

The single padded product read at tail 4 was a `w3` forward dispatch at
`0x7fdf54800000`, with 65,536 bytes of allocated slack behind it. That is the
same geometry and the same consumer that in 5I ended at the fault page.

The single stock tail-4 read is a different tensor: the *gradient* of the
product, consumed by a `w1`/`w2` backward GEMM. Mode 2 pads the product, not its
gradient, which stays a stock ATen allocation.

## 6. Interpretation

| class | verdict |
|---|---|
| 1, valid padded operand execution, clean | **yes** |
| 2, valid padded operand execution, faulted at another allocation | no |
| 3, valid padded operand execution, faulted at the protected operand | no |
| 4, invalid due to numerical or descriptor mismatch | no |
| 5, inconclusive due to insufficient pointer or storage evidence | no |

The configuration that faulted three times out of three is clean once with the
product's storage padded, all of its consumers verified, and the computation
bitwise unchanged.

What this supports: the fault in this configuration is associated with the
SwiGLU product's storage boundary. In 5I the fault page was page-exact with that
product's tail and two of its consumers read it in the faulting second; here both
consumers read a protected allocation at the same alignment and no fault
occurred.

What this does not establish:

1. It is one clean run of an intermittent fault. Stability is not shown.
2. Kernel identity is unknown, so "same consumer, same geometry, protected
   storage" is a descriptor-level statement.
3. A stock tail-4 operand read still existed and did not fault, so the 4-byte
   tail alone is not sufficient. The fault needs a particular consumer as well as
   a page-ending operand.
4. 4,038 stock reads with the tail exactly on a boundary did not fault, which
   rules out alignment by itself as the trigger.
5. The allocator layout changed, because 5,566 allocations are 64 KiB larger.

## 7. Confounders

1. Single clean run; the fault has been intermittent across the campaign.
2. The product's gradient remains stock and is read at tail 4 by a `w1`/`w2`
   backward GEMM without faulting, so an equally plausible reading of this run is
   that the faulting consumer is not the `w3` GEMM but something the padding
   moved by accident.
3. Address reuse makes pointer matching unsafe on its own; the analysis requires
   the recorded byte count to match as well.
4. Post-loop checks ran two extra forward and backward passes after `COMPLETED`.
   They cannot change the loop's outcome, and they are excluded from the loop
   analysis by timestamp.
5. Kernel identity and the exact over-reading instruction remain unobserved.

## 8. Recommended next bounded experiment

Two candidates, in this order:

1. **Repeat this arm once.** If it is clean again, the product hypothesis gains a
   second independent clean run at the same geometry, which is what an
   intermittent fault needs. A fault would immediately void it.
2. **Swap the intervention.** Pad only the product's *gradient* and leave the
   product stock. That covers the other tail-4 reader and leaves the product
   unprotected. A fault there would implicate the gradient consumer; a clean run
   would isolate the product further.

Either way the gates are the same as this stage: whole-model CPU bitwise gate,
descriptor equality for both consumers, verified padding on the targeted operand
with a matched dispatch, and a full-precision first loss.
