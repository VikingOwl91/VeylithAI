# v3.1-PERF-3A elementwise and dtype fusion audit

Status 2026-10-27. Read-only investigation. No GPU work, no benchmarks, no code
changes.

**Selected candidate for a bounded PERF-3B prototype: P1, a single BF16 cast at
the RMSNorm output (with the MoE accumulator kept in FP32).**

The audit found the structural cause behind the elementwise and copy cost: the
residual stream is FP32. The embedding returns FP32, RMSNorm multiplies by an
FP32 weight and returns FP32, and the dense MoE combine accumulates in FP32.
Autocast therefore re-casts the same FP32 activations to BF16 before every
Linear: 1,280 casts of (4088, 512) per update, part of the measured 21.8 ms of
FP32 to BF16 copy kernels. Casting once at the norm output, while keeping the
combine accumulator and residual in FP32, removes about 1,152 of those casts
without changing any value a GEMM or the combine sees.

## 2. Method and attribution limits

- The trace was recorded with `record_shapes=True` and no stacks. Every
  `aten::` CPU op was joined to its GPU kernel time through the profiler's
  External id, then grouped by (op, input dims, input dtypes).
- Phase (forward, backward, optimizer) comes from the `record_function`
  annotations around the training step.
- Kernel categories use the PERF-1 mapping: elementwise, copy, GEMM, attention,
  optimizer, reduction, softmax/CE, fill.
- **Attribution limit:** without stacks, op-to-source mapping is inferred from
  shape, dtype, frequency and model semantics. It is strong for the shapes that
  occur only in one place, weaker for generic 1-D and fill kernels. Unknown
  items are listed in section 8.

## 3. The central finding: an FP32 residual stream

The trace shows:

| evidence | observation |
|---|---|
| `aten::pow`, `aten::mean`, `aten::rsqrt` at (8, 511, 512) and (8, 511, 1) | executed in **float**, not bfloat16 |
| `aten::mul` (8, 511, 512) × (512,) float | the RMSNorm weight multiply runs in FP32 |
| `aten::embedding_dense_backward` output type | **float** |
| `aten::add` (8, 511, 512) with float, bfloat16 operands | residual add promotes to FP32 |
| `aten::copy_` (4088, 512) bf16 ← float | 1,400 calls/update, 21.83 ms |
| `aten::copy_` (4088, 512) float ← bf16 | 952 calls/update, 11.08 ms |

The model is built with FP32 parameters. `nn.Embedding` is not an autocast op,
so the token embedding returns FP32. `RMSNorm` multiplies by the FP32 weight
and therefore returns FP32 even when its input is BF16. The MoE dense combine
starts from `flat.new_zeros(...)` and adds FP32 contributions, so it stays
FP32. The residual add `x + mlp_out` then produces FP32 again. From the first
token onward the residual stream is FP32, and autocast casts it to BF16 before
every Linear.

Consumers of a norm output per block: q, k, v projections (3), the router gate
(1) and the eight experts' w1/w2 inputs (16), for 20 casts of (4088, 512) per
block. With 8 blocks and 8 microbatches that is **1,280 casts per update**,
which matches the measured 1,400 (about 120 remain unattributed).

## 5. What the six PERF-1 items actually are

| PERF-1 item | measured | what the trace shows | avoidable? |
|---|---:|---|---|
| FP32 gradient accumulation | 71.3 ms | a mixture: parameter adds 15-16 ms, activation-gradient adds about 35 ms, combine/residual FP32 adds about 24 ms | parameter-add launch overhead only; the adds themselves are required |
| BF16 expert-weight multiplication | 36.7 ms | the **SwiGLU** `silu(w1) * w2` mul at (4088, 960), not the router weighting | one intermediate, about 12-18 ms |
| FP32 binary operations | 32.8 ms | combine add 16.27, RMSNorm muls 7.9, RoPE/softmax muls, residual adds | sub-op dependent |
| BF16 copies | 35.4 ms | FP32→BF16 autocast casts 21.83, CE boundary 3.78, attention reshapes | about 18 ms from the norm casts |
| BF16→FP32 conversion | 27.4 ms | residual/combine promotion 11.08, weight-grad casts 8.4, CE 3.17 | only by changing the residual dtype (numerical change) |
| Manual-unroll operations | 27.5 ms | broadcast muls: router weights 19.05, RMSNorm weight 7.9, RoPE/attention | fusable with the combine/norm changes |

Two labels in the stage-1 category table were therefore misleading. The 36.7 ms
"expert-weight multiply" is the SwiGLU gate multiply, and "gradient
accumulation" covers three different FP32 add families.

## 6. Candidate analysis

Each candidate is assessed on measured cost, theoretical saving, complexity,
numerical and autograd risk, ROCm concerns, and the two minimal tests.

### P1. Single BF16 cast at the RMSNorm output (selected)

- **Measured cost:** 21.83 ms of (4088, 512) FP32→BF16 casts, of which 1,280
  calls/update are norm consumers; 952 residual/combine promotions at 11.08 ms
  and 7.9 ms of FP32 norm muls are adjacent but kept.
- **Maximum saving:** 1,152 fewer casts × 12.55 MB moved each = 14.4 GB/update,
  which at the measured 805 GB/s cast rate is **about 18.0 ms/update** (2.3
  percent of a 0.78 s update). Assumes the casts are on the critical elementwise
  stream and that the remaining 128 single casts cost what one consumer cast
  did.
- **Complexity:** low. `RMSNorm.forward` computes the same FP32 result and
  returns `result.to(torch.bfloat16)` once; the MoE combine allocates its
  accumulator explicitly in FP32 so the combine path is unchanged.
- **Numerical risk:** none expected. Every GEMM would consume the same BF16
  values that autocast produced from the same FP32 result; the residual stream
  and combine accumulator stay FP32. The cast round-to-nearest-even is the same
  operation autocast performs.
- **Autograd risk:** none. No graph structure, parameter dtype or in-place
  pattern changes.
- **ROCm:** none; no new kernels and no library dependence.
- **Minimal correctness test:** unit-level check that
  `rmsnorm(x).to(bf16)` equals the old consumer-side cast bitwise; then a
  2-update GPU comparison of loss and every gradient against the current code,
  target bitwise equality, with a documented tolerance only if a cast order
  differs.
- **Minimal performance test:** a 5-update profile counting
  `copy_ (4088, 512) bf16←float` and elementwise milliseconds.
- **Expected update impact:** **-18 ms, about -2.3 percent, hypothesis only.**

### P2. Fused MoE weighted aggregation

- **Measured cost:** 79.31 ms cluster: forward mul 6.77 and add 16.27, backward
  mul 33.69 and 12.28, reduction 10.30.
- **Maximum saving:** about 15 ms by removing the FP32 `contribution` and
  `d_weights` intermediates (roughly 7.5 GB/update each) and their launches,
  while keeping FP32 accumulation.
- **Complexity:** medium-high. Needs a custom autograd function or a Triton
  kernel that handles the forward combine and both gradient paths.
- **Numerical risk:** the d_weights reduction order and FMA versus separate
  multiply-add. A no-FMA implementation with the same reduction tree is
  required for bitwise equality; otherwise the change is an ulp-level gradient
  change that must be accepted explicitly.
- **Autograd risk:** the custom backward must reproduce three paths (d_expert,
  d_weights, d_out) exactly.
- **ROCm:** Triton 3.8 is installed; deterministic reductions, no atomics.
- **Minimal correctness test:** synthetic combine at the measured shapes against
  the reference outputs and both gradients, tolerance 0 or documented ulp.
- **Minimal performance test:** isolated 448-call combine microbenchmark, kernel
  count and ms/update.
- **Expected update impact:** -10 to -20 ms (about -1.3 to -2.6 percent),
  hypothesis.

### P3. SwiGLU activation fusion (silu + mul)

- **Measured cost:** 58.91 ms: mul 36.66, silu 7.80, silu backward 14.45, plus
  14.1 ms of expert dropout.
- **Maximum saving:** about 14 ms by removing the (4088, 960) BF16 silu
  intermediate from the forward and backward paths.
- **Complexity:** medium; a Triton kernel or a scoped `torch.compile`.
- **Numerical risk:** low if the fused kernel preserves silu-then-multiply and
  the exact backward expressions. Dropout must stay after w3, unchanged.
- **Autograd risk:** a custom backward for the silu and w2 paths.
- **ROCm:** Triton 3.8; deterministic.
- **Minimal correctness test:** SwiGLU forward and backward against the reference
  at (4088, 960), tolerance 0.
- **Minimal performance test:** isolated SwiGLU microbenchmark plus a 5-update
  profile.
- **Expected update impact:** -8 to -15 ms (about -1.0 to -1.9 percent),
  hypothesis.

### P4. Multi-tensor gradient accumulation

- **Measured cost:** about 24 ms of parameter-shaped FP32 adds plus the first
  microbatches' BF16→FP32 casts.
- **Maximum saving:** about 7 ms, from launch overhead only. The traffic is
  unchanged because the same bytes must be read and written.
- **Complexity:** medium, because autograd's `AccumulateGrad` is internal; it
  needs either a custom gradient buffer or a post-backward `foreach` pass.
- **Numerical risk:** low, if per-tensor add order is preserved.
- **Autograd risk:** moderate (ownership and timing of `.grad`).
- **ROCm:** foreach kernels are already used by AdamW.
- **Minimal correctness test:** two-microbatch gradient equality against the
  reference.
- **Minimal performance test:** count parameter-shaped `add_` launches and ms.
- **Expected update impact:** -5 to -7 ms (about -0.6 to -0.9 percent),
  hypothesis.

### P5. Scoped torch.compile / Inductor

- **Measured cost:** potentially all elementwise clusters, but no isolated
  measurement exists.
- **Maximum saving:** unknown. Topk, `one_hot`, `bincount`, `.cpu()` calls and
  in-place router counters create graph breaks; the training loop is not a
  single graph.
- **Complexity:** high; compile time, recompiles and a new determinism surface.
- **Numerical risk:** Inductor may reorder reductions.
- **Autograd risk:** moderate.
- **ROCm:** Triton-based Inductor on gfx1201 is unproven for this model.
- **Minimal correctness test:** 2-update bitwise/ulp comparison.
- **Minimal performance test:** 5-update profile after warm compilation.
- **Expected update impact:** not estimated; insufficient evidence.

### P6. Custom Triton kernels

Not a standalone candidate. It is the implementation vehicle for P2 or P3 if
their prototypes justify it. High complexity and a new numerical surface.

## 7. Ranking and selection

| rank | candidate | measured cluster | max saving | risk | verdict |
|---:|---|---:|---:|---|---|
| 1 | P1 single-cast norm output | 21.8 ms | 18 ms | very low | **selected** |
| 2 | P2 fused MoE aggregation | 79.3 ms | 15 ms | medium | second |
| 3 | P3 SwiGLU fusion | 58.9 ms | 14 ms | medium-low | third |
| 4 | P4 multi-tensor grad accumulation | 24 ms | 7 ms | low | later |
| 5 | P5 torch.compile | unknown | unknown | high | not yet |
| 6 | P6 Triton kernels | vehicle | vehicle | high | later |

P1 wins because it has the largest purely *avoidable* cluster with the smallest
numerical surface: the GEMM operands are unchanged BF16 values, the combine and
residual remain FP32, and no new kernels or dependencies are needed. P2 has the
largest measured cluster but most of it is required arithmetic; only about 15 ms
is removable and the gradient reduction order becomes a new risk.

## 8. Unknowns and unverified attribution

- About 120 of the 1,400 FP32→BF16 (4088, 512) casts are not explained by the 20
  norm consumers per block. They may be attention-output or CE-boundary casts.
- `aten::fill_` on (4088, 512) at 8.63 ms BF16 and 6.68 ms FP32 per update has
  no stack trace. It is likely autograd buffer zeroing or dropout masks, but it
  is not provable from this trace.
- The op-to-source map is inferred from shape, dtype and semantics; the trace
  has no Python stacks.
- The 309/82/245 category figures are PERF-1 kernel attributions; op-level sums
  can double count nested operations.
- Savings assume the elementwise stream is the critical path and that removing
  casts does not shift time into GEMMs or memory stalls.
- The FP32 residual hypothesis (that keeping the residual in BF16 would save the
  11.08 ms of promotion plus part of the FP32 adds) is a numerical change and
  was not selected.

## 10. PERF-3B proposal (bounded, not authorized here)

1. `RMSNorm.forward`: compute the same FP32 normalization, return
   `result.to(torch.bfloat16)`.
2. `MoE.forward`: allocate the dense accumulator explicitly as FP32
   (`flat.new_zeros(flat.shape, dtype=torch.float32)`), so the combine is
   unchanged.
3. Correctness gate: 2 GPU updates comparing loss and all gradients against the
   current code, expecting bitwise equality; abort on any difference or NaN.
4. Performance gate: 5-update profile; success if the (4088, 512) FP32→BF16
   cast count drops by at least 1,100 and elementwise time drops by at least
   12 ms/update.
5. No checkpoint format change, no optimizer change, no architecture change.
