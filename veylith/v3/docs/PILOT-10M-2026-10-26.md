# FineWeb-Edu 10M-token pilot (2026-10-26)

Scope: veylith v3.0 pretraining data infrastructure, CPU only. One
FineWeb-Edu pilot of about 10M training tokens at the pinned revision. No
model training, no GPU, no architecture change. This pilot does not measure
model quality.

Artifacts: `pilot-10m-manifest-2026-10-26.json`,
`tokenizer-comparison-10m-2026-10-26.json`,
`loader-benchmark-10m-2026-10-26.json`. The corpus itself lives at
`~/veylith-v3-data/fineweb-10m-20261026` and is not in git.

## 4. Tokenizer comparison

Both tokenizers were trained on the same 11,173 train documents only, with
identical normalization, byte fallback, special ids and single-threaded
deterministic training. Validation and test documents (226 documents,
809,138 chars, 131,031 words) were used for encoding measurements only.

| metric | 4096 | 8192 |
|---|---:|---:|
| chars/token (held-out) | 3.4663 | **3.9412** |
| fertility (tokens/word) | 1.7815 | **1.5668** |
| tokens/doc mean | 1032.9 | **908.4** |
| tokens/doc median | 733.5 | **659.5** |
| tokens/doc p95 | 3161.8 | **2783.3** |
| tokens/doc max | 5170 | **4693** |
| per-doc chunks at 256 | 1025 | **922** |
| concat sequences at 256 (held-out) | 912 | **802** |
| embedding + head params (n_embd 256) | 2,097,152 | 4,194,304 |
| total params, v2 shape, untied head | 27,187,456 | 29,284,608 |
| training time | 2.414 s | 2.558 s |
| peak child RSS | 444 MB | 453 MB |
| roundtrip failures | 0 | 0 |
| unknown-token uses (held-out) | 0 | 0 |

Special tokens are identical: `<unk>` 0, `<s>` 1, `</s>` 2, `<pad>` 3. Probes
(empty string, `<unk>`, emoji, CJK, combining mark, tabs/newlines) roundtrip
exactly with both sizes; byte fallback means no unknown pieces were needed.

**Preliminary default: 8192.** It produces 12 % fewer tokens per word and
10 % fewer document chunks at 256 tokens, for 2.1M more parameters in a
v2-shaped model. Training time and memory are essentially equal. This is a
data-side decision; it does not show that 8192 improves model quality.

## 5. Deduplication

- Exact: `sha256(normalized_text)`, global over the staged set, canonical
  keep is the smallest `doc_key`. One duplicate was removed.
- Near: 64-bit SimHash over word 5-grams, four 16-bit bands, Hamming <= 3,
  same canonical rule. No pair was found in this sample.
- Post-hoc check: `verify --near-dups` recomputed SimHashes over all 11,399
  kept documents, found 0 pairs and skipped 0 LSH buckets. No near-duplicate
  crosses a split.

The pilot sample has little duplicated boilerplate; the method is tested
synthetically with a shared-text pair (distance 0) and an unrelated control.

## 6. RAM and storage

- Prepare peak RSS 87.8 MB for 11.4k documents. The staging index is about
  319 KB per 1000 documents on disk (about 320 bytes per document); the
  in-memory representation is larger but still small at this scale.
- Scaling estimate: about 300 bytes/document on disk and a few hundred bytes
  in memory. 100,000 documents stay under 100 MB on disk and a few hundred
  MB in RAM. 10M documents would need roughly 3 GB on disk and several GB
  of RAM for the index alone, so a bucketed or disk-backed index is required
  before that scale. None is needed for this pilot.
- Root 194 MB: staging 48 MB, document text 41 MB, token shards 21 MB,
  tokenizer files and the two training texts about 80 MB.
- The 2 GiB pilot cap is not approached.

Mid-epoch resume is implemented: `iter_batches(..., start_epoch, start_batch)`
skips deterministically, and the benchmark compares the resumed batches with
the full run. The batch cache is bounded to 8 token shards.

Packing is non-overlapping and covers every train token exactly once
(10,333,164 = sum of sequence lengths). Concat mode may put two documents in
one window; EOS marks the boundary and each sequence records its document
keys. The document mode never crosses a boundary. A plan for one split only
reads that split's token shards; `verify_corpus` checks that each document's
shard matches its split policy.

## 8. Reproducibility evidence

- Offline suite: 36 passed, 1 skipped (network test opt-in). Full repository
  suite: 125 passed, 1 skipped (v2 and v3).
- The 8192 model trained in the comparison child and the model trained by
  the final `tokenize` process are byte-identical:
  `537afa0a4c64690bb5131db1f3d7e1c490f378a6647c35b57c7f73e252a61df6`.
- The first 100 document keys of this corpus equal the keys from an
  independent 100-document smoke at the same revision, in the same order.
- The pilot used `prepare --resume` from 11,139 to 11,400 documents. The
  offline test `test_resume_matches_an_uninterrupted_run` proves that resume
  yields the same manifest digest and shard hashes as one uninterrupted run.
- The loader order digest from two independent processes is identical.
- Manifest digest `e995fdead3a6bf57d6db5f768f19c4363515d44a9a0bdbf860539e454711dfdc`;
  all shard hashes are in the committed manifest.

A second full network materialization was not attempted. The earlier
2000-document pilot showed that an immediate second full run hits the
datasets-server rate limit (HTTP 429); the local manifest and the offline
determinism tests are the anchor. The 100-document prefix match covers
source-side order stability.

## 9. Network errors and limitations

- No 429 in this run. Pacing was 2.5 s between pages (119 pages). The adapter
  honors `Retry-After` for 429, otherwise waits 10 s and 20 s on the two
  retries, and stops with exit code 3 after three attempts. A failed run
  leaves the staging state and can be resumed later.
- The `datasets` backend is implemented but not installed in the system
  Python and no project environment with it exists; installing it is outside
  this task's boundaries. The missing-dependency path is tested. The HTTP
  backend is the pilot path; the `datasets` backend remains the scale path.
- HF streaming order is not a stable contract. The revision is pinned and
  the local materialized corpus is the reproducibility anchor.
- Near-duplicate detection targets shared boilerplate, not paraphrases; small
  edits in otherwise unique text can exceed Hamming 3.
- The validation and test splits have 125 and 101 documents. They are large
  enough for tokenizer measurements, not for model quality claims.
- The 4096 and 8192 tokenizers both write a 40 MB training text; this is the
  main reason the root is 194 MB instead of about 120 MB.
- No GPU, no model, no training, no v3.1 work in this pilot.

## 10. Recommendation

1. Use the 8192 tokenizer as the preliminary default for v3.1.
2. Keep the 10.33M-token corpus and its manifest as the v3.0 reference. Do
   not mutate it; new runs get new roots.
3. Plan v3.1 as a separate, explicitly approved step: choose model
   width/depth and compute budget, then one GPU run, and compare with the
   frozen v2 numbers using the bits/char protocol. No model quality is
   claimed before that run.
4. If more data is needed, the next controlled step is a 100M-token pilot
   with the `datasets` backend in a project environment, 1 % validation and
   test, and an explicit new budget. No automatic escalation from 10M to
   100M.
