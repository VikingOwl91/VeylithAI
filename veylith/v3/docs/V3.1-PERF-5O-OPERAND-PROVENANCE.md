# v3.1-PERF-5O operand provenance and fault reconciliation

Status 2026-10-27. CPU-only analysis. **No GPU execution was performed**, no
production change, no checkpoint or package change, no push.

This stage re-reads every raw artifact from PERF-5I to 5N, separates what was
observed from what was inferred, enumerates the tensors that can produce the
recurring `(M, 682)` BF16 geometry, designs provenance instrumentation that can
settle the question, and reassesses the four candidate hypotheses. It does not
rank one as confirmed.

## 2. What was observed, per run

Every tight-boundary tensor found in the series is a BF16 GEMM operand of
4,194,300 bytes, which is `(3075, 682)` at two bytes per element, 2 MiB aligned,
ending 4 bytes before a 2 MiB line.

| run | pointer | page dist | grid dist | reads | read shapes | fault | fault page |
|---|---|---|---|---|---|---|---|
| 5I | `0x7ff321000000` | 4 | 4 | 2 | `C 256x682 OP_T`, `C 256x3075 OP_N` | yes | same page |
| 5L | `0x7fcccde00000` | 4 | 4 | 2 | same pair | yes | same page |
| 5N | `0x7f505b200000` | 4 | 4 | 4 | same pair, twice | yes | same page |
| 5J | `0x7fdf79800000` | 4 | 4 | 1 | `C 256x682 OP_T` only | no | none |
| 5K | `0x7f594be00000` | 4 | 4 | 1 | `C 256x682 OP_T` only | no | none |

Directly observed in each case: the pointer, the byte count implied by the
descriptor (`rows x cols x 2`), the GEMM role and descriptor pair, the dispatch
timestamp, and the fault page when there was one. Also observed: the fault page
lies in **no** padded storage in 5I, 5L and 5N, and the 5N product allocations
all carry offset 2,097,152 with zero trailing bytes.

## 3. What is inferred, and what is unknown

**Inferred:** the tensor is one of the three `(M, 682)` BF16 tensors that can be
a GEMM operand in this model, listed in section 4. The descriptor pair
(`C 256xM` with `transB OP_N`, plus `C 256x682` with `transB OP_T`) is produced by
three different producer/consumer combinations with identical fields, so the log
cannot name which one it is.

**Unknown, and not resolvable from these artifacts:**

1. **No allocation record for the 5N fault tensor.** `0x7f505b200000` matches no
   `data_ptr` in the 5N geometry, so it was not created by the harness allocator.
   It is therefore an ATen allocation, which is consistent with a derivative but
   proves nothing about which one.
2. **Address reuse inside a recorded allocation.** That address falls inside a
   storage that the harness did record earlier, a `(3068, 682)` front-padded
   product whose view lived at `0x7f505affb800`. The records are per allocation
   and carry no free events, so a pointer-only match would wrongly claim that
   the fault tensor was that product. This is exactly the failure mode the
   mission warns about.
3. **The clean-run asymmetry.** In 5J and 5K the tail-4 tensor was read only by
   the `C 256x682 OP_T` shape, never by the `C 256xM OP_N` shape, while all three
   faulting runs show both. That is either a real role asymmetry or an artefact
   of what the engine chose to dispatch in those iterations. The records cannot
   distinguish these, and it is the single most useful observation in this stage.
4. **Producer identity.** No artifact records which op allocated these tensors,
   and none records tensor lifetimes.

## 4. Static graph: every `(M, 682)` BF16 tensor that can exist

`SwiGLU.forward` is `drop(w3(silu(w1(x)) * w2(x)))`, with `x` of shape `(M, 256)`
for an expert.

| # | tensor | producing op | phase | consumed by | GEMM operand |
|---|---|---|---|---|---|
| 1 | `w1_out` | `aten::linear` (mm) | forward | `silu` | no |
| 2 | `silu_out` | `aten::silu` | forward | `mul` | no |
| 3 | `w2_out` | `aten::linear` (mm) | forward | `mul` | no |
| 4 | `product` | `aten::mul` | forward | `w3` forward GEMM, `MulBackward` | **yes**, `w3` forward and weight-grad |
| 5 | `d_product` | `aten::mm` inside linear backward | backward | `MulBackward` | no, output only |
| 6 | `grad_gate` | `MulBackward` (`grad * w2_out`) | backward | `silu_backward` | no |
| 7 | `grad_up` | `MulBackward` (`grad * silu_out`) | backward | `w2` backward GEMMs | **yes** |
| 8 | `grad_silu` | `aten::silu_backward` | backward | `w1` backward GEMMs | **yes** |

So three tensors can be the tail-4 GEMM operand: 4, 7 and 8. Their consumer
descriptors coincide because `w1`, `w2` and `w3` all contract over 682 with an
output width of 256 or a weight of shape `(256, 682)`.

In 5I and 5L all three are candidates. In 5N the product is provably padded
(its one `(3075, 682)` record is at `0x7f4f9ef50000`), so the fault tensor there
must be 7 or 8, a derivative. In 5J and 5K the product is padded too, so their
clean tail-4 tensor is also 7 or 8.

## 5. Instrumentation design (not executed)

Two layers, both additive and both designed to leave storage, autograd and GEMM
dispatch untouched.

**Layer 1, allocation provenance, built in.** `torch.cuda.memory._record_memory_history`
records every allocator event with the Python stack that caused it, at C++ level
and without intercepting operators. A record per event:

| field | source |
|---|---|
| event id | monotonic counter assigned by the recorder |
| producer op | top frames of the recorded stack (`aten::mm`, `aten::mul`, `aten::silu_backward`, or the harness allocator) |
| phase | forward or backward, from the stack's autograd frames |
| shape, dtype, strides | harness registry, keyed by pointer at allocation time |
| storage base, data pointer, byte count | allocator event |
| lifetime | alloc and free events for the same block, including reuse |
| consumer op and GEMM role | joined from the hipBLASLt trace by `(pointer, byte count)` **within the recorded lifetime** |

**Layer 2, size-filtered tag registry.** A `TorchFunctionMode` that only inspects
operators producing a BF16 tensor of exactly 4,194,300 bytes, and only asks each
one for its output pointer and its inputs' producer tags. Everything else falls
through with a single `if`. This is the minimum interception that yields
producer-to-consumer edges, and it must be validated for numerical neutrality
first.

**Pointer reuse is handled explicitly** by keying on `(pointer, byte count,
lifetime id)` and by dropping any join where the consumer timestamp falls outside
the allocation's lifetime. Retrospective pointer-only matching is abandoned: the
5N case in section 3 shows it produces a wrong answer.

**Risk.** Instrumentation has suppressed this fault before: the PERF-5E profiler
prevented it. The allocator recorder is cheaper than a profiler and the tag
registry touches only one size class, but neither has been shown to be
transparent on this stack, so the first GPU run must be treated as an
instrumentation-validity test as much as a provenance test.

## 6. Hypothesis reassessment

### A. A BF16 GEMM reads past a tightly bounded operand

- Supporting: three faults, each page-exact with a 4-byte tail at a 2 MiB aligned
  end; the same page is where an unmapped page would begin; no fault when the
  tensor's own storage carried slack (5J, 5K, and the 5M/5N products).
- Contradictory: an identical tail-4, 2 MiB aligned tensor was read in 5J and 5K
  without a fault; the 4-byte tail alone is therefore not sufficient.
- Missing: the instruction and the kernel; whether the read that faulted is the
  one at the page end.
- Smallest discriminating experiment: provenance plus a role-targeted read, see
  section 7.

### B. A specific GEMM kernel or transpose formulation has an invalid access

- Supporting: only the runs that show a `C 256xM transB OP_N` read of the tail-4
  tensor faulted; the two clean runs show only the `C 256x682 transB OP_T` read.
  That split is 3 for 3 versus 0 for 2.
- Contradictory: the asymmetry is inferred from dispatch counts that the records
  cannot fully explain, and the same tensor is read by both formulations in the
  faulting runs, so the correlation may be incidental to which iterations ran.
- Missing: kernel identity, per-dispatch instruction-level evidence.
- Smallest discriminating experiment: a pinned-formulation arm, or provenance
  that names the consumer of the faulting read.

### C. Allocator reuse or lifetime corruption produces an invalid operand

- Supporting: the 5N fault pointer was reused; a stale record for the same
  address exists; the fault surfaces one iteration later, which is also what a
  late use of a freed buffer would look like.
- Contradictory: the faulting tensor is live in the dispatch record at the
  moment of the read, and the harness never frees a buffer it is about to use;
  no double free or use-after-free has been observed.
- Missing: free events and lifetimes, exactly what layer 1 provides.
- Smallest discriminating experiment: the same provenance run; a freed-before-use
  record would settle it.

### D. Another asynchronous kernel faults and the GEMM operand is only spatially correlated

- Supporting: the fault is reported asynchronously, one iteration later; in 5N a
  second page-exact candidate existed at the same page, an 8 MB stock activation
  ending exactly on the page, and it was touched 212 times.
- Contradictory: the 4-byte tail coincidence recurred in three independent runs
  at three different addresses, each time with a `(M, 682)` operand, and the
  faults stopped when that operand's storage had slack; a purely spatial
  correlation would have to be this specific by chance.
- Missing: the kernel that faulted, from the GPU's own report.
- Smallest discriminating experiment: a run that removes the tail-4 operand while
  leaving everything else identical, or provenance that shows the faulting
  dispatch.

No hypothesis is confirmed. A is the best supported on geometry, B has the only
clean separation in the data, C is untested, D cannot be excluded.

## 7. Recommended next experiment (one GPU run)

**Provenance-instrumented stock run.** Use the unmodified reproducer with no
padding of any kind, so the fault is expected, and enable layer 1 plus the
size-filtered layer 2. Dump the allocator history and tag registry from the
exception handler, which already runs after a catchable fault.

Why this over another padding arm: four padding arms have produced one clean
discrimination and then a contradiction. One run that names the producer and the
consumer of the faulting operand converts every hypothesis above from inference
to evidence.

**Validity gates**

1. CPU: the instrumentation is numerically neutral. Whole-model state, logits,
   loss and every gradient must be bitwise identical with instrumentation on.
2. GPU: the run must produce at least one tail-4 `(M, 682)` BF16 allocation with
   a producer stack, and at least one consumer dispatch whose pointer, byte count
   and lifetime match it.
3. The fault page must match that tensor's page within the same lifetime window.

**Required observations:** allocation id and stack for the fault tensor, its
phase, every consumer dispatch with role and descriptor, whether the block was
freed before the fault, and whether the address was reused after the record.

**Outcome classes**

| outcome | reading |
|---|---|
| live stock derivative, consumer is the `OP_N` formulation | B gains direct support, A remains the mechanism |
| live stock derivative, both formulations read it | A over B, and the clean-run asymmetry needs another explanation |
| allocation freed before the fault | C |
| fault recurs with no tail-4 operand at the page | D |
| no fault at all | instrumentation suppressed it; report and stop, do not retry |

**Stop conditions:** the fault does not occur, the provenance join is ambiguous
for the fault tensor, or the instrumentation changes the first loss. In each
case stop and report rather than reinterpret.

**Safety constraints:** idle GPU gate, no foreign KFD process, fresh process,
`ulimit -c 0`, 120 s timeout, no kernel serialization, no profiler, no retry, no
reset, one execution, and the same 100-iteration configuration.
