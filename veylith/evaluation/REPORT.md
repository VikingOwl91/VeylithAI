# Evaluation report: what veylith learned

Date: 2026-10-26. CPU-only. No training, no GPU, no optimizer steps.
Generated by `veylith/evaluate.py`; raw numbers in `results.json` (measured
sums versus derived metrics are separate blocks there).

## 1. Checkpoints that exist

All five load on CPU. v1 and v2 checkpoints are the legacy format: they carry
weights, config, tokenizer and a stored validation loss, but no step, no
metrics and no selection record. The temporary P1-1 checkpoint is format 2.

SHA256 values are in `results.json`. The v1 models carry a non-trainable

parameters only. The temporary checkpoint is volatile and is not part of the
repository; it is a diagnostic, not a quality reference.

`v1-bpe-5000it` has the same architecture and the same training arguments as
`v1-bpe` but a much worse stored loss (4.1756 vs 3.2903). Its origin is not
recorded in the checkpoint, so it is reported as an alternative run, not as a
reference.

## 2. Protocol

- Corpus: `veylith/v2/data/tinyshakespeare.txt`, 1,115,394 ASCII characters,
  sha256 in `results.json`. The v1 and v2 copies are byte-identical.
- Validation boundaries: the char tokenizer splits at character 1,003,854; the
  BPE tokenizer splits at token 443,556, which is character 1,008,119. To stay
  in the validation region of every model, all sections start at or after
  1,008,119.
- Sections: 6 fixed slices of 512 characters with 128-character gaps, at
  offsets 1008119 + i*640. No RNG. Each section hash is in `results.json`.
- Tokenization: each section is encoded with the checkpoint's own tokenizer.
  Evaluation uses non-overlapping chunks of up to `block_size` tokens inside
  the section. The first token of a chunk has no left context; the last token
  of a section is never predicted. No token uses text outside its section.
- Metric: main next-token cross-entropy only. For v1 that is the model's plain
  loss; for v2 the logits are scored directly, so neither the MTP term nor the
  MoE aux loss enters. No composite loss anywhere.
- Characters: bits/char uses the exact character span of the evaluated target
  tokens, computed by prefix decoding (`len(decode(ids[:k]))`), not a corpus
  average. The BPE decoder is lossless on the corpus (checked by roundtrip).
- Model state: `eval()` mode, float32, CPU only. The device environment is
  emptied before torch is imported.

## 4. Comparability and limits

- Per-token CE is not comparable across tokenizers. Bits/char is the common
  metric because it normalizes by the evaluated characters, not by tokens.
- Chunk boundaries differ per tokenizer (the same text gives 511 char tokens
  or about 230 BPE tokens per section). Context resets at each chunk start.
- Only 6 sections (3,067 characters) are evaluated. The paired BPE comparison
  is strong because both models see identical tokens, but the absolute values
  are section-specific: v1-bpe's stored random-window validation loss is
  3.2903, while these six sections give 2.9671. Do not compare numbers across
  protocols.
- The models were trained with bf16 autocast on the GPU; evaluation is float32
  on the CPU. Router decisions and logits can differ marginally from training
  time. The comparison between checkpoints is unaffected because all are
  scored the same way.
- v1 and v2 checkpoints store no step or metrics, so "best checkpoint" cannot
  be audited from the file beyond the stored loss.
- The temporary checkpoint disappears with `/tmp`.

## 5. Generated text

Configuration: 100 new tokens, temperature 0.8, top-k 40, seeds 1337/42/7,
plus a greedy run; no EOS handling, so every run fills the budget. Prompts:
`ROMEO:`, `JULIET:`, `To be, or not to be`, `The king`, `the the the`,
`?!3 $&',-.:;`. All prompts were encodable by every tokenizer; nothing was
skipped.

Representative continuations:

- v1-char, `ROMEO:`, sample seed 1337:
  `\nWhy, here's no citizens? What a mind\nThat thou talk'st to us, that ...`
- v1-bpe, `JULIET:`, sample seed 7:
  `\nHow will you come with him? I do thee, sir;\nYet had I dare my heart ...`
- v1-bpe, `ROMEO:`, greedy:
  `Then, by the crown of England,\nThe kingdom of England, the king,\n...`
- v2-bpe, `ROMEO:`, sample seed 7:
  `\nHow will my mother a whi I do thee,\nAnd I'll play the sembler of bl ...`
- v2-bpe, `?!3 $&',-.:;`, greedy:
  `And, by the king, the king, and the\nshows,\nAnd the kings, and the kings ...`
- v2-p1-1-temp, `ROMEO:`, greedy:
  `And, I, I, I, I, I, and,\nThere, I's, I's, and,...`

Qualitatively: v1 produces Shakespeare-shaped surface structure with speaker
labels, line breaks and mostly plausible words. v2 produces fewer repeated
token sequences but more broken words and missing word boundaries. The 120-step
checkpoint produces token soup. This is a description of the outputs, not a
claim about understanding.

repetitive but also less coherent. Greedy decoding loops more in every model,
most strongly in the undertrained checkpoint.

## 7. MoE router (v2-bpe)

1,377 tokens per layer, top-2, 8 experts. Uniform reference: 12.5% of the
expert slots (25% token coverage) per expert. Probability is the softmax over
all experts before top-k; selection is the top-k of the same distribution;
weights are the softmax over the top-k logits.

| layer | share range % | mean prob range | entropy (nats) | entropy norm | unused | rare | max section dev | mean TV |
|---|---|---|---|---|---|---|---|---|
| 1 | 10.68 .. 14.89 | 0.108 .. 0.143 | 1.700 | 0.818 | none | none | 4.89 pp | 0.060 |
| 2 | 9.59 .. 16.56 | 0.102 .. 0.150 | 1.660 | 0.798 | none | none | 6.78 pp | 0.070 |
| 3 | 10.31 .. 15.40 | 0.098 .. 0.152 | 1.748 | 0.841 | none | none | 5.40 pp | 0.058 |
| 4 | 9.22 .. 15.65 | 0.096 .. 0.148 | 1.646 | 0.791 | none | none | 6.59 pp | 0.079 |
| 5 | 9.51 .. 15.18 | 0.099 .. 0.187 | 1.587 | 0.763 | none | none | 7.75 pp | 0.081 |

- All experts are used; none is rare (threshold: below half the uniform slot
  share, 6.25%). Entropy is 0.76 to 0.84 of the maximum, so routing is
  moderately peaked, not uniform and not collapsed.
- Share and mean probability correlate strongly per layer (r = 0.66 to 0.92),
  but they are not the same thing: in layer 5, expert 7 has the highest mean
  probability (0.187) and the highest mean top-k weight (0.638) while expert 6
  is selected more often (15.2% vs 13.9% of slots).
- Selection differs between sections: the largest per-expert deviation from
  the overall share is 4.9 to 7.8 percentage points, with a mean total
  variation of 0.06 to 0.08. With about 230 tokens (460 slots) per section the
  binomial standard error at p=0.125 is about 1.5 points, so the largest
  deviations exceed sampling noise. This says routing depends on the text; it
  does not say what an expert represents.
- The 120-step checkpoint has entropy 0.95 to 0.99 and shares 9.2 to 16.3%:
  close to its random initialization, as expected after 120 steps.

## 8. Findings

Measured:

1. On identical tokens from six shared validation sections, v2-bpe is worse
   than v1-bpe by 0.213 nats/token (5.6 SE) and 0.138 bits/char (5.4 SE).
   The direction holds in every section.
2. v1-char and v1-bpe agree within 0.5% in bits/char, despite different
   tokenizers and parameter counts.
3. The v2 router is healthy: all 8 experts used in all 5 MoE layers, no
   collapse, entropy 0.76 to 0.84 normalized, and content-dependent selection.
4. v2's sampled text is less repetitive but less coherent than v1's; greedy
   decoding loops in both, strongly in the undertrained checkpoint.

Hypotheses (not established by this evaluation):

- Capacity/data mismatch: 25.6M parameters on 0.44M training tokens overfit;
  the training log (not in this repo) reports the best validation loss early
  in the run, and the extra parameters do not pay off on this corpus.
- The MTP objective (weight 0.5; the term measured 4.95 nats/token on a
  16-window sample in an earlier analysis) carries a large share of the
  training signal and may compete with the main next-token objective.
- Sliding-window attention (128 tokens on four of the six layers) limits the
  usable context compared with v1's full attention. The sections are about 230
  BPE tokens long, so this is a real difference on this protocol.
- Dense-combined MoE computes every expert for every token. The router is
  healthy, so the question is whether the extra parameters are useful at this
  data scale, not whether routing works.

## 9. Open questions

- Why is `v1-bpe-5000it` so much worse than `v1-bpe` with identical config and
  arguments? The legacy checkpoint does not record its history.
- Is the v2 deficit driven by capacity, MTP, attention scope or MoE? This needs
  controlled ablations at a fixed token budget.
- Are the section-level routing differences stable across a larger sample and
  across restarts? Six sections are a coarse signal.
- Do the bits/char values hold on a larger, less contiguous section set? The
  per-section spread is about 0.5 nats.

## 10. Recommendations for the next training phase

1. Match capacity to data before adding architecture: either shrink v2 (fewer
   layers or experts, or a dense FFN) or add data. The evaluation gives a fixed
   acceptance metric for that decision.
2. Ablate `mtp_weight` (0.0 / 0.2 / 0.5) at an identical token budget and score
   each arm with this protocol.
3. Compare sliding-window attention against full attention at this scale; v1's
   full attention is part of the quality gap and is cheap to test.
4. Keep the MoE, but compare it against a dense FFN with the same active
   parameters. The router is not the problem; the parameter return is.
5. Keep this protocol and the fixed evaluation mode for every future run, and
   store step, metrics and selection in every new checkpoint.

## Reproducing

```bash
python3 veylith/evaluate.py --out veylith/evaluation/results.json
python3 -m pytest veylith/v2/tests veylith/tests -q
```

Two independent runs produced byte-identical `results.json` files (checked by
diff; no timestamps are written).
